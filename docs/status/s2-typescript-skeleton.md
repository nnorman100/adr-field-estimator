Field database Firestore rules (`web/firestore.rules`, S3-6): deny by default, drafts only, checked in that emulator with two tenants; not deployed. Access records written by the server (S3-12, `web/src/lib/projection/`, migration `0005_access_projection`): an outbox run writes or removes each member's Firestore access record from the committed Postgres membership, marks a removal done only after a read shows the record gone, and repairs a crash on the next run; records last 7 days and `GET /api/me` renews them daily. The team routes project the changed member right after their change commits, so a disable whose projection succeeds removes the record before it answers; one that fails or finds the member busy still succeeds and leaves its outbox rows waiting for the cross-company pass. `POST /api/internal/access-projection` runs the cross-company pass for the scheduler service account only (`serviceRoute`); that account and its Cloud Scheduler job are an owner follow-up, so nothing schedules the run yet. Checked against a throwaway Postgres and the Firestore emulator only. Company roles and capability table ported to `web/src/lib/access/` (S3-1), tested against `docs/ACCESS.md`. Request identity (S3-7): `web/src/lib/auth/` checks the Firebase ID token on the project, finds the company from its signed tenant through `0004_sign_in_lookup`, checks it again with the revocation check on that tenant, requires a verified email and an active membership of an active company, and `GET /api/me` returns company, role and capabilities; every route declares `publicRoute`, `memberRoute`, `accountRoute`, `requireFlag`, `serviceRoute` or `operatorRoute`, enforced by a test. Per-company feature flags (S3-11a, `web/src/lib/flags/`): a fixed list of known flags (`price_books` only), all off unless the company has a stored row turned on, read at sign-in inside `withCompany`, so `prices_read`/`prices_manage` follow the company's switch; `requireFlag` makes a switched-off feature's routes answer 404. No route changes a flag yet: the operator-only change route, its database write path and its audit write come in S3-11b, after a database job and the operator identity of S3-9. `web/src/proxy.ts` refuses every `/api` route outside the public list (health, echo), the member list (`/api/me` and the team and invitation routes), the operator list (`/api/platform/...`) and the internal job list (`/api/internal/access-projection`, which checks the scheduler's service token itself) with 401 when signed out; `GET /api/health` answers 503 when a configured database refuses the service's login. Checked against the Auth emulator and a throwaway Postgres only, never a real Identity Platform tenant; reads the project from `GOOGLE_CLOUD_PROJECT` and the environment from `APP_ENVIRONMENT`, as the S3-5 Terraform sets them, and needs those identity permissions applied before it can run in `test`. Second-step and session rules (S3-8, `web/src/lib/auth/policy.ts`): owners need an authenticator-app second step (`second_step_required` on every route but enrolment), the sign-in must be newer than 14 days (owner, office) or 30 days (estimator), and a route declared as a team or second-step change needs a sign-in under 15 minutes old (`sign_in_again`); the accepted factor list is authenticator app only, fixed in code. Proved on token claims and on Auth emulator tokens (owner without a second step, a text-message factor refused, sign-in age read from `auth_time`); a real authenticator-app sign-in is proved only in S3-18. Team and invitations API (S3-10, `web/src/lib/team/`, routes under `/api/companies/{companyId}/` and `/api/invitations/{invitationId}`): the owner lists the team, invites an estimator or office user by email, resends, cancels and clears invitations, moves a member between estimator and office, and disables or re-enables a member; an office user lists only active estimators and an estimator is refused; the owner cannot be disabled, demoted or re-enabled there; changes need a sign-in under 15 minutes old; a company id in the path that is not the caller's own answers 404. An invitation is open for 7 days and, with no email service in the rebuilt app, the owner gets its link (the company's sign-in address) to copy; inviting makes the invitee a password-less, unverified account in the company's tenant. Accepting needs the invitation's verified email and creates the actor and one membership, once. Disabling revokes the member's sessions before the call returns. Each change writes one audit row and each membership change queues the member's Firestore access record. Platform operator API (S3-9, `web/src/lib/platform/`, routes under `/api/platform/`, migration `0006_platform_operator`): an operator from the operator-only tenant, with an authenticator-app second step and a sign-in under 12 hours old, lists and creates companies, suspends, reactivates and archives them (archive needs suspended), binds a company to its sign-in tenant once, invites or replaces the owner by link (replacing disables the old owner and revokes their sessions before answering), resets a member's second step (logged; D9 email waits for the email service (S9), so the answer says `tellByPhone` and the operator tells the person by phone), reads a company's team read-only, and takes the support actions (resend, cancel, switch role, re-enable; a company with no active owner keeps its pending owner invitation, `owner_invitation_required`); every other caller gets 403 `not_an_operator` on every operator route, each action writes one audit row naming the operator, and a refused one writes none. Operators are added only by the owner-run `npm run platform:add-operator`; tenants are created by the owner-run `npm run platform:create-tenant`, with the person's own Google credentials. Proved against a throwaway Postgres as the runtime role and, for the second-step reset and the account calls, the Auth emulator; no operator screens (S3-15). No enrolment route uses the route options yet. No product screens or sign-in screens. Not deployed to production.
