# S8 plan, step S8-2

Part of [the S8 plan](../S8.md), section 5, "Ordered steps".

**S8-2 Database connections per instance (S, High: the database client).** Kind: agent code.
- BE: `web/src/db/client.ts` opens up to **3** connections in the main pool, a constant in code with an idle timeout and the stale comment removed. The health probe keeps exactly one connection of its own (it no longer takes the main pool's size). Beside them, the sizing rule counts every pool an instance opens: the main pool (3), the access-renewal pool (`PROJECTION_CONNECTIONS`, 2) and the probe (1), so 6 per instance. The web app's maximum instances are 1 on test and 7 on live (`infra/dryscope/app/envs/*.tfvars`; an owner app-root apply, before the code is released). These numbers replace 5, 4 and 10 per instance, which fit neither database ([correction of 2026-11-17](2026-11-17-s8-2-connection-budget.md)). The maximum instances is set per revision, and during a canary or a traffic move the old and the new revision both run (Google: both scale during a rollout), so two revisions are budgeted: 2 times the maximum instances times 6, plus the migrator (1) and a reserve of 10, must stay under the instance's `max_connections`. Two holds because a new revision is staged only once every revision without traffic is at zero instances, or 15 minutes after the last traffic move (the drain precondition, S8.md section 3; S8-14, S8-18, S8-19). The test release enforces the 15-minute form now: its deploy job waits until 15 minutes after the service's last change before staging (`web/scripts/release-drain.ts`). No new setting (the S6 O4 precedent: a constant raised by a reviewed pull request). If an environment's measured limit does not fit, that environment's maximum instances come down or the owner picks a larger database tier; the reserve never shrinks.
- Tests: in the database suite, two requests hold transactions at the same moment on one instance (proved with advisory locks; fails at `max: 1`); the company-context test over reused connections still passes (`withCompany` sets the company per transaction, so a wider pool must not leak it); the health probe opens one connection whatever the main pool's size; a guard test sums the exported pool sizes (main, access renewal, probe), reads the maximum instances from both `tfvars` files (`api_scaling.max_instances`, parsed as HCL; a raised value fails it) and fails when two revisions (the drain precondition's bound) times the maximum instances times that sum, plus the migrator and the reserve, exceeds the documented limit for that environment (25 on test, 100 on live: Cloud SQL's defaults for the two tiers until the owner's reading); the test release stages only after the drain wait, run against the real step with fakes.
- Owner: read `max_connections` on test and on live once (`SELECT setting FROM pg_settings WHERE name = 'max_connections';`) and record both in the runbook (section 7, step K).
- Needs: nothing. Lands before S8-22.
- Note: Google's limit of 100 connections per Cloud SQL database applies to the built-in Cloud Run connection only, not to the Auth Proxy sidecar, language connectors or a direct address. The pull request states which method the web app and the migrator use; the sizing rule uses the database's own `max_connections` either way.
