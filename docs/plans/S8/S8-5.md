# S8 plan, step S8-5

Part of [the S8 plan](../S8.md), section 5, "Ordered steps".

**S8-5 Restore and rollback drill kit (M, High: a script the owner runs against cloud resources).** Kind: agent code; run in S8-21.
- Infra: `infra/dryscope/scripts/restore-drill.sh`, owner-run, timed phase by phase, with `--dry-run` printing every command and making no call. Phases: (1) note two marker records made through the app, one before and one after a chosen minute; (2) a point-in-time copy of `dryscope-<env>-pg` to that minute, into a new instance; (3) checks on the copy: the migration ledger is complete, the first marker is there and the second is not, row counts per table; for the repoint only (a lost instance), the owner then applies the data root with S8-6's `sql_instance_override` naming the copy (the admission only; the services stay on the original), and only after that apply the web app's own database account logs in to the copy; (4) backup salvage for a regional outage: the latest `us` backup restored into another region as a data copy (today's procedure), its age recorded, no repoint; (5) the field database's latest backup restored into a new database, one known draft compared, with a note that a restored database starts with deny-all rules and without its expiry policies; (6) one evidence object restored from soft delete and one from an earlier version; (7) the app root's repoint of S8-6, applied on test only after phase 3 passed; its fresh revision tagged `candidate` and checked there, then all traffic moved to it and the app's health read at `test.<domain>`; then put back: the recorded revision tagged `candidate` and checked there, all traffic moved to it and health read at `test.<domain>`, then the app root with the override emptied, then the data root; (8) the drill's own instances and database removed; (9) a result block (times, counts, pass or fail) to paste into the record. It runs against test only; a separate `--recovery` mode for a real incident on live never deletes: for damaged data it runs phases 2 and 3 without the admission and stops at the validated copy, printing the row copy-back steps of `backups.md`; `--recovery --lost-instance` for a zone outage runs phases 2 and 3 with the admission and ends by printing the app root's repoint and the tag, check and traffic commands for the owner to run once the checks pass; `--recovery --salvage` for a regional outage runs phase 4 only.
- Docs: `docs/runbook/backups.md` rewritten around one table: bad release (roll back), damaged rows (point-in-time copy, compare, copy back only the damaged rows by id, records check; never a repoint), zone outage (copy into another zone, repoint), region outage (backup salvage into another region; the app waits for Google's recovery, owner decision 2026-11-17, S8.md section 4.5), field database damage, a deleted file.
- Tests: the script runs in CI against a recording `gcloud` stub (the pattern of the old monitoring script's test): `--dry-run` makes no call; every command names its project; it deletes only resources whose names end in `-drill`; it refuses live without `--recovery`; the names it uses match the naming module's.
- Needs: nothing to write. S8-6 for phases 3 and 7 and for `--recovery --lost-instance`.
