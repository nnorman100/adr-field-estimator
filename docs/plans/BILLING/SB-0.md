# Billing plan, step SB-0

Part of [the billing plan](../BILLING.md), section 5, "Ordered steps".

**SB-0 Sandbox proof of the Stripe facts the design rests on (M, Medium).** Slice: documents, with one script. Test only, outside the main build, as S7-0 was.
- BE: `web/scripts/stripe-proof.ts`, run by hand against a Stripe sandbox with Stripe's simulated clock. It proves and records: (a) a last-value meter bills the last value stamped inside the month, including a value sent during the finalization window and a value lower than an earlier one; (b) a Checkout Session in subscription mode accepts one flat price and three metered prices, the first-of-month anchor and automatic tax, with `customer_update[address]=auto` so that the address entered is the one taxed and saved, and `customer_update[name]=auto` with tax id collection; (c) with "mark as unpaid" set, a failing card walks `active`, `past_due`, `unpaid`, and paying the open invoice returns `active`; which events arrive and in what order; and the same walk with "Pause the subscription" set: `active`, `past_due`, `paused`, then paying the open invoice resumes it; what the resumption invoice holds; (d) whether Stripe's thin event format carries the subscription and invoice events; (e) what the portal offers for this subscription; (f) what a draft invoice of an `unpaid` month holds, and whether paying the old invoice restores `active` once a newer draft exists; (g) the size of the largest event received; (h) a subscription started mid-month: the part-month company fee and what the meters bill for the first period; (i) a period in which no usage event is sent bills zero; (j) the last invoice after a cancellation at the period's end still takes usage sent in the finalization window; (k) two usage events with the same stamp; (l) usage events for a customer on a simulated clock: which stamps are accepted and which period they bill in (N1, section 13: run first, because SB-25 and the phone check rest on it); (m) after deactivating a meter, can a new meter take the same event name (N5).
- Plan follow-ups: the seven behaviours of section 13, N1 to N7, are this step's to prove or settle; the results entry answers each one.
- Docs: the results as a dated entry under Corrections, with every answer that differs from section 4 and the change it forces.
- Tests: the script's own checks run in CI against the stand-in of SB-2 (so the script cannot rot); CI makes no Stripe call.
- Needs: B4 (who may run it). SB-2 for the CI part. Its results gate SB-18 and the owner's Dashboard set-up (section 7, step C).
