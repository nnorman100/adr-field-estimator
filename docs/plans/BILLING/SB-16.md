# Billing plan, step SB-16

Part of [the billing plan](../BILLING.md), section 5, "Ordered steps".

**SB-16 Billable units, the allowance and the extra (M, High: pricing).** Slice: server.
- BE: the AI boundary (`web/src/lib/ai/call.ts`) settles a call that returns its checked result with the outcome `succeeded`, in the same write as its cost, and every other settlement as `not_billed`; the voice-note route stores the boundary's call id on the note it writes. Pure functions in `web/src/lib/billing/usage.ts`, each for one period (section 4.5): voice minutes from session lengths; credits by the credit table (versioned) from ledger rows settled `succeeded`, a voice note's from the length on the `voice_notes` row with its call id, in two readings: settled only (what is billed) and committed (settled plus calls still reserved or held at their feature's worst case, what the cap uses); active people in the period; the pooled allowance; the extras; the expected extra charge from the dated prices. `GET /api/billing/usage` (`billing_read`) answers the month so far.
- Tests: worked examples from this plan as fixtures; property tests: more use never lowers an extra, one more active user never raises one, the extras are never negative, the result does not depend on the order of rows; a failed AI call counts nothing in either reading and a call in progress counts in the committed reading only; a call Google answered whose output parsing, screening or server rules refuse is settled at its cost and counts no credit; a voice note's credits come from the length on the note linked by its call id (a 61-second note is 2 credits), and a succeeded voice-note call with no linked note counts none; use before the subscription's start is outside the period; a person last seen before the start is not active in a part month, and one who opened before and again after it is; the pool never falls below last month's; a month computed twice is identical; another company's rows never enter the sum (the isolation matrix row and a planted row).
