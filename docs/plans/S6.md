## 1. Summary

- S6 is **9 steps** (S6-1 to S6-9), each one pull request with a test that fails without it. **No database job**: nothing S6 adds lives in Postgres. The phone-side state is in the Firestore cache and small IndexedDB databases; the minimum app version is a constant in code (O4). The only server changes are one extra field on `GET /api/me` (S6-3) and the version check (S6-6). S6 therefore does not wait for the database lane.
- **Six of the nine steps can start before S5a-2 to S5a-8** (their first parts need only S5a-1, S3-12 and S3-13a, all merged), so they can run beside S5a-2 to S5a-7; their screens are components that mount in the `/field` shell and in S5a-6's screens when those exist (section 6). This is earlier than `S5.md` section 6 ("S6 may start once S5a-8 is merged"); the owner decided it as O7 on 2026-11-12. S6-7 (Submit from the phone) needs S5a-8, S6-8 needs S4-6 and S5a-10 (and does not hold the close-out), and the close-out needs S5a-12.
- **The promise:** a technician opens the app from the Home Screen with no signal, walks a job, takes photos, closes the app, comes back to signal, and every change and photo lands exactly once; nothing is lost silently and nothing is sent twice. "Exactly once" means one committed effect, not one network attempt (the replan's wording). It holds because every S5 write already carries a client-made id; S6 adds the phone side: a durable queue, a journal of unsent edits, and a gate that keeps unsent work from being sent into an access record that has run out.
- **What iOS decides (section 2):** there is no background upload on iPhone (Background Sync and Background Fetch are unsupported), so every retry happens while the app is open; there is no connection-type signal, so originals go on a tap, as the old app already does; Safari tabs lose all script-written storage after 7 days without use but an installed Home Screen app does not, and the two keep separate storage, so the plan asks the technician to install **at the start** (an install later starts empty and signed out) and warns when unsent work sits in a browser tab (superseded: offline capture on iPhone needs the installed app, D-025; see the 2026-11-12 G8 entry in section 12); IndexedDB in Safari has a history of "connection lost" and hangs, so every store has a reopen path and the Firestore cache falls back to memory with a visible warning.
- **Found while planning:**
  - A write queued offline for longer than the access record's 7 days (`docs/DATA.md`) would be sent the moment the phone reconnects, before `/api/me` has renewed the record; the rules would refuse it and the SDK would drop it. S6-3's sync gate (network off until `/api/me` has answered and says the record is current) closes this; `/api/me` renews with a call that can be skipped (`wait: false`, a busy actor or a row in back-off), so a bare 200 proves nothing and S6-3 adds the record's expiry to the answer.
  - The persistent cache does not tell the app that a write the server refused after a restart was lost (the write's promise is gone). S6-4's journal exists for that, as `data-ownership.md` asks ("preserve rejected optimistic edits locally").
  - Every phone store must be keyed by company and person, because several companies share one origin and the sign-in code keeps two companies signed in on purpose (`web/src/lib/firebase-client.ts:24-29`); otherwise one company's drainer meets another's entries, and signing out of one wipes the other's unsent work.
  - `S5a-6` will build the job screens before S6 exists; if they are server-rendered, no worker can cache them. Section 10 asks S5a-6's author to put them in one client-rendered shell route group, which S6-2 then caches.
  - The old worker lives at `/sw.js`. If the new app ever takes over the old origin (S8's choice), serving the new worker from the same URL lets it replace the old one, but only once every window of the old app is closed (the old worker has no `skipWaiting` at install); S6-2 tests that, and S8 plans the cutover around it.

## 3. Design rules every S6 step follows

- **The server and Firestore stay the owners** (`data-ownership.md`). Anything on the phone is a copy or a queue; an optimistic value is not an acknowledgement. The screen uses three words everywhere and nothing else: **Saved** (the server has it), **Saved on this phone** (waiting to send), **Can't save** (refused, with the reason and what to do).
- **Foreground only.** Nothing runs after the app closes. Retries start on open, on `online`, when the app becomes visible, on a tap, and on a timer while visible; one drainer at a time (the Web Locks API, supported since Safari 15.4, so two windows never both upload).
- **Replay is safe because ids are the phone's.** Every queued operation keeps its client id (S5: job, draft, room, photo, submission ids); a replay of the same id and body returns the same answer and a different body answers 409, which stops the retry loop and shows a reason. S6 adds no server-minted ids.
- **The cache holds the shell, never people.** The worker caches the static shell, build assets, manifest and icons only, and serves the shell from its own precache (never from the network when a precached copy exists), so a deployment cannot switch a running window onto new HTML before the person taps Update. It never stores `/api/*`, photo bytes, Identity Platform calls or any personalised HTML; authenticated routes stay `no-store` (S5 check). A test lists the cache after a full session and fails on any other URL.
- **Phone stores are keyed by company and person.** The Firestore cache (field documents; one Firebase app instance per sign-in tenant), `ds-journal` (unsent edits), `ds-queue` (photo bytes and entries), `ds-me` (the last online sign-in: role, capabilities, company name, and the browser settings the shell needs to boot offline: Firebase API key, auth domain, project id, field database id, tenant id; no email) and, from S6-8, `ds-prices` (item ids, names and room types; no prices, no totals). Every `ds-*` row carries (tenant id, uid); a drainer sends and a sign-out clears only the signed-in pair's rows, so company B never sends or deletes company A's. Names are fixed in `docs/DATA.md` by S6-9. Whether the SDK also keeps one person's queued writes from another person on the same app instance is checked in S6-1 (c); the plan does not rely on it.
- **Sync gate.** The Firestore network stays disabled from start-up until `/api/me` has answered 200 **and** its `fieldAccessExpiresAt` is in the future (a renewal that was skipped leaves it in the past: the phone waits, asks again after a few seconds, and shows "Waiting for access to renew"), then it is enabled. The codes `sign_in_required`, `sign_in_again`, `second_step_required`, `member_disabled` and `company_inactive` (`web/src/lib/sign-in/outcome.ts`) leave it disabled and the unsent work untouched and locked (D7: "unsynced work on the phone is kept through a re-sign-in"); the work is deleted only by an explicit Discard or under O5.
- **Never mid-job.** A new worker waits; the app says "Update ready" and applies it only when the person taps, never while the camera is open or a save or upload is running, and never by itself. A server that has raised the minimum app version answers 426 `update_required` before it touches any record.
- **No data in logs.** The phone keeps its own counters (waiting, sending, blocked); browser and phone **error reports** go to `/api/client-errors` (TC-2, required by Standard 2.5 Tier 1); there are no counters, analytics or other client telemetry until S9.
- **Same checks as S5:** every UI step uses the modern-web-guidance skill, phone width (390 px), Chromium and WebKit. Offline in tests means the network is cut at a small switchable proxy in front of the app and both emulators, not only `context.setOffline`, because Playwright does not report or route a service worker's requests outside Chromium (section 2).

## 4. The phone's side of the handoff

1. **Edit.** The phone writes the change to `ds-journal` (operation id, document path, the field values, time, state `pending`), then calls Firestore (`setDoc` with merge, or a batch, absolute values). The screen shows "Saved on this phone".
2. **Acknowledge.** While the page lives, each write's own promise says acknowledged or refused. After a restart (the promise is gone) the phone re-issues any entry still `pending` that never reached Firestore (a crash between the journal write and the call), waits for `waitForPendingWrites()`, then reads the documents from the server and compares **only the newest journal entry per document and key** with them. Equal: the entries become `acked` and the screen says "Saved". Refused by the rules (draft submitted or archived, access removed, field owner changed): `rejected` with that reason; the screen says "Can't save" and offers Save as new draft, Discard, or Try again where that is possible. Different with no refusal (the same person's other phone wrote later): "Changed on another device", not "Can't save", and the journal keeps the entry (section 5, S6-4).
3. **Photo.** Capture, resize the 2,560 px copy, SHA-256 of the bytes, then bytes and an entry (photo id, job, draft, room, shot tag, hash, stage) into `ds-queue` before the photo appears on screen. Stages: `queued`, `sent` (receipt hash equals the local hash), `referenced` (the reference document is written locally; its id is the photo id, so a replay is a no-op), `done` (that write acknowledged by the server; bytes deleted). A crash at any point resumes at the recorded stage. A lost response is settled by sending the same photo again: S5a-5's route is idempotent and returns the receipt (a resend costs at most one 2,560 px copy; a cheaper `GET` receipt route is left out unless S6-5's measurement shows the cost matters). Same id with different bytes is a 409: the entry stops at `blocked` and says why. The entry is `done`, and its bytes deleted, only after the reference document write is acknowledged by the server; if the fence or a refusal lands between the receipt and that acknowledgement, the bytes are still on the phone for Save as new draft.
4. **Originals** are entries of kind `original` that wait until the technician taps "Send originals now (use Wi-Fi)" (O2).
5. **Finish and review** needs a connection, no `photo` entries left in the queue (waiting originals do not count: S5a-5 lets an original arrive after signing), the journal clean and pending writes acknowledged. It makes the submission id once and keeps it (with the digest) in `ds-journal` before the call; every retry, including after the app was closed, sends the same id. On open the phone asks the server for that submission's status before it does anything else. The S5a-8 worker finishes or releases a stuck submission within 15 minutes (S6-7 checks the cadence).
6. **After the fence** every queued write is refused by the rules, stays `rejected: locked` and is never retried; nothing changes the submitted record. "Back to editing" (J4) and "Save as new draft" are the two ways forward.
7. **Update.** A newer worker waits; "Update ready" applies it on a tap; a 426 shows the same screen with the data kept.

### 2026-11-12: S6-1 results, the questions section 4 rests on

Run with `firebase` 13.1.0, Playwright 1.65.0 (Chromium 158.0.8127.18 and WebKit 27.2, the Linux build, which is not iOS Safari), the Auth and Firestore emulators (`firebase-tools` 15.31.0) and one switchable network lane per test (`web/tests/e2e/offline/lane.ts`). These are emulator results; the real backend and a real iPhone stay with S6-9. Every answer below is pinned by a test in `web/tests/e2e/offline/`, which now run in CI with the rest of the browser suite; a failing one after an SDK bump means the answer changed, so re-read it here first.

- **(a) Settled.** A write made with no signal stays queued through a reload and through closing and reopening the window; the cache shows it as pending, the server has nothing until the network is back, and it is then sent once (the probe was an increment: the server held +1, and still +1 three seconds later). One addition: the Firestore client does nothing until the app first uses it, so a client that is started and not used sends nothing; the field start-up must make a first call (a listener or `waitForPendingWrites()`).
- **(b) Matches section 4 step 2, with three additions.** After a restart a refused write is dropped from the queue and nothing tells the app: `waitForPendingWrites()` resolves normally, no error event reaches anyone, and the listener first shows the unsent edit as if saved (from cache, pending) and then the server's copy without it. While the page is still alive the write's promise rejects with `permission-denied`. So the journal's compare-with-the-server step is needed, as planned. Additions: (1) when the refusal is lost access (the record removed or run out) the person's read is refused as well, so the listener ends with a `permission-denied` error and the step 2 server read fails the same way; S6-4 must read that as "Can't save: access", and read a draft whose `state` is no longer `editing` as "This job was finished". (2) A refused write does not hold up the writes behind it. (3) A refused write queued ahead of an increment made the increment apply twice (both engines, with and without a restart).
