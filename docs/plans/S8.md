## 1. Summary

- **What S8 delivers.** The rebuilt app runs in its own live Google Cloud project, at its own web address, released there by the same path that releases test. Before any real record exists, a restore is rehearsed and timed, the app is load-tested, the security gates are recorded, and the old app is deleted for good. The stage ends on **switch-over day**: the first company (the owner's own) starts real jobs on live.
- **What S8 does not deliver.** Billing (its own stage after the pilot, owner 2026-11-16). Email through the company domain, the status page, the support channel and the backup person (S9). The public marketing site with search and AI-search work (its own plan, question L9). Terms and privacy pages in the app (they need the lawyer's text; "Later", section 12).
- **Size.** 25 steps (S8-1 to S8-24 and S8-13b), 28 pull requests. **No database job**, so S8 never waits for the database lane. Most steps are **High** risk (Terraform, IAM, workflows, cloud, release path); each pull request states its own rating.
- **Nothing is brought over from the old app, and the old project is deleted now** (owner, 2026-11-17: L1 and L2). That was already decided four times (D-006, D-012, D-017, and the owner's "export nothing" of 2026-11-10). The old app has been off since 2026-11-10 and held no signed record. The owner takes one last look at the two real-looking inspections, then runs the permanent steps (section 4.1, owner step B).
- **The order that matters.** Domain, then the live project, then DNS, then the front door on test, then the release checks through the front door, then the lock, then live built the same way, then drills and the load test on test, then the gates, then switch-over day.
- **Live never serves a real user from a `run.app` address.** A phone keeps its installed app and unsent work per web address, so live starts on its final address (`app.<domain>`) from the first day. Only test moves address, and test holds fake data.
- **Found while planning.**
  1. The Terraform roots, the naming module and the plan check accept only project `dryscope` and its number, so a separate live project (D-018) is a code change (S8-8).
  2. Once Cloud Run accepts only the load balancer, the release's candidate check and health check stop working: they call `run.app` addresses from the build server, outside Google. The candidate is routed through the load balancer by its revision tag (S8-12, S8-14).
  3. The scheduled job, the uptime check, the synthetic monitor, the reCAPTCHA key's domain list, `ALLOWED_ORIGINS` and the relay's `API_INTERNAL_URL` all name the `run.app` address. Google lists Cloud Scheduler and uptime checks among the callers that break when the default address is switched off. They move to the domain first (S8-13).
  4. The web app's main database pool is **one** connection per instance while each instance takes 40 requests at once. Beside it each instance opens a four-connection pool for access renewals and a health probe that takes the main pool's size, so widening the main pool widens the probe too (S8-2).
  5. A zonal Cloud SQL instance is not recovered from a zone outage automatically: it is restored by hand into a new instance with a new connection name, and "you must reconfigure any clients". No procedure or setting does that today (S8-5, S8-6).
  6. Sign-in tenants belong to one project and authenticator second steps cannot be imported, so nobody is copied from test to live.
  7. Standard 2.8 added "Cloud SQL retained and final backups" to Tier 1 after the TC plan was written; no plan holds it. S8-9 adds it.
  8. Things made "test only" because test and live shared a project (the scheduler account and job, the rules release role, the Model Armor floor setting, the deploy log line) can now exist in live safely: separate projects are the full fix that `infra/dryscope/README.md` names.
  9. The app shows no mark that tells a person they are on the test copy (S8-16).
  10. `docs/runbook/owner-cloud-steps.md` item 14 and `infra/dryscope/README.md` still describe live inside project `dryscope`; `docs/runbook/where-things-run.md` still describes the old app as serving; `docs/legacy-data-inventory.md` misses three collections.   11. Two per-caller limits (the public error-report route and the signing-link address limit) take the **last** address in `X-Forwarded-For` as the caller. Behind the load balancer the last address is the load balancer's own, so every caller would share one limit (S8-13b).

## 3. Design rules every S8 step follows

- **Test first, live second, the same code.** Every Terraform change is applied to test, proven there, then applied to live with only the environment's values changed. Nothing is built for live alone except the approval step in the release.
- **One project per environment, nothing shared** (D-018). The test accounts hold no role in the live project and the live accounts none in test. The plan check refuses a test plan that names the live project and a live plan that names `dryscope`. The one deliberate crossing is the release's image copy: the live deploy account reads the test image repository by digest and nothing else.
- **Build once, promote the same image.** Live runs the image test ran, copied by digest into live's own repository. A release reaches live only after test's checks passed on that digest.
- **Reversible before irreversible.** Each cloud change has its undo written next to it. The few steps with no undo (deleting the old project, the first real signature, HSTS for subdomains) are named in section 4.5 and wait for the owner's word.
- **The front door is the only way in.** Cloud Run accepts the load balancer and Google's own same-project callers only. Every caller the app controls (release checks, the scheduled job, the monitors, the relay) uses the public address.
- **Owner runs the cloud; agents write the code and the commands.** Agents never apply Terraform, change IAM, touch DNS at the registrar, run a drill against cloud resources or delete anything. A drill or load-test script is written and tested with a recording stub in CI, then run by the owner.
- **Live checks are read-only.** There is no hidden test company on live. The live smoke check sends only `GET` requests; the first real job is the first job.
- **A settings apply serves nobody until traffic moves.** Terraform ignores a service's traffic, so an app-root apply that changes a revision setting makes a fresh revision with no traffic. Its settings reach users only after that revision passes the smoke check at a tagged address and traffic is moved to it: by the next release (a manual run of the release workflow on `master` is enough), or, in a drill, an incident or the bypass, by the owner tagging the new revision `candidate`, checking it there, recording the serving revision and moving all traffic with `gcloud run services update-traffic`. Going back is the same move to the recorded revision: tagged `candidate` and checked there first, then all traffic moved to it and the serving address checked, all before any IAM admission the new settings needed is removed. Ingress and the default address are service settings and take effect at the apply.
- **At most two revisions hold database connections.** A new revision (a release or a settings rollout) is staged only once every revision without traffic is at zero instances, or 15 minutes after the last traffic move (Google: an idle instance can stay up to 15 minutes). A rollback to the revision the last move replaced runs at once, since it is one of the two; a rollback to any other revision waits the same way.
- **Live data never rolls back with a release.** An app rollback moves traffic; the database only moves forward. A restore is for data damage, into a new instance, and only damaged rows are copied back.
- **No new dependency where 200 lines do the job.** The load driver is plain Node (`fetch`, percentiles in the script), as the service worker was hand-written (S6, O6).
- **Certificates through Certificate Manager with per-project DNS authorization.** Adding a host later adds a resource; it never replaces one, which the plan check refuses. A DNS authorization covers a host and its first-level wildcard, so one authorization serves `test.<domain>` and `candidate.test.<domain>`.
- **No data in logs, tickets or drill records.** Drill and load-test write-ups hold times, counts and ids. The lawyer checklist holds questions, not customer data.
- **Multi-company wording.** The first company is "the first company (the owner's own)". Nothing in code, Terraform or these documents names a company.

### 4.2 The front door

1. **Names.** `app.<domain>` is live. `test.<domain>` is test. The bare domain and `www.` answer with a temporary redirect to `app.<domain>` until the public site exists (L9). `candidate.app.<domain>` and `candidate.test.<domain>` reach the version that is staged but not yet serving. `voice.app.<domain>` and `voice.test.<domain>` are held for the Live relay, and `voice-candidate.app.<domain>` and `voice-candidate.test.<domain>` reach the relay's staged revision, so its no-traffic check (S7-R) still works after the lock (S7 decides whether the relay uses the host or a path; with a path, its staged revision is that path under `candidate.`).
2. **DNS.** One public zone for `<domain>` in the live project, with DNSSEC, in the live data root. `test.<domain>` is delegated to its own zone in the test project, so each environment's Terraform writes only its own project. The registrar's name servers point at the live zone.
3. **Certificates.** Certificate Manager, Google-managed, with a per-project DNS authorization per host. Each authorization covers the host and its first-level wildcard, so `candidate.`, `voice.` and `voice-candidate.` need no extra authorization. The certificate is active before any address record points at the load balancer.
4. **Load balancer.** A global external Application Load Balancer in each project: one address, an HTTPS proxy with the certificate map, an HTTP proxy that only redirects to HTTPS, a URL map by host, and one backend service per target. Each target is a serverless network endpoint group in the same project and region as its Cloud Run service: the web app, the web app's `candidate` tag, the relay, and the relay's `candidate` tag.
5. **Lock.** After every caller uses the public address, both Cloud Run services move to "internal and Cloud Load Balancing". A direct internet request to `run.app` is then refused. The default address is switched off as well where the setting is generally available (L14).
6. **What changes for people.** Test moves from its `run.app` address to `test.<domain>`: testers send unsent work first, then install the app again from the new address (a phone keeps storage per address). Test links made on the old address stop working (fake data). Live starts on `app.<domain>`, so nobody on live ever moves.
7. **The caller's address.** The load balancer adds the client's address and then its own to the forwarding header. The app is told the load balancer's address and takes the entry before it; on the direct path it keeps today's rule (S8-13b).
8. **What does not change.** The sign-in helper stays at the project's default Hosting site address (`authDomain`, normally `<project>.firebaseapp.com`) with pop-up sign-in, which Google lists as a supported choice for an app not on Firebase Hosting. The pop-up therefore shows the project's `firebaseapp.com` name; a branded helper address is a later option, not needed to work.

### 4.3 The release path to live

1. A merge to `master` releases to test exactly as today (build, migrate, rules, candidate at no traffic, smoke, traffic, record).
2. **Promote.** A `live` job copies the released image by digest from the test repository into the live repository and checks the digest is unchanged.
3. **Approve.** GitHub offers required reviewers on a private repository only with GitHub Enterprise; Free, Pro and Team do not. Unless the owner holds Enterprise, the live leg is a `workflow_dispatch` run that only the owner starts by hand from GitHub Mobile, taking the version number as its input, and that manual start is the approval (L8). Every live release waits for the owner until three clean live releases and both drills have passed; after that a release goes automatically, except a release that changes the database, which always waits (L8).
4. **Migrate, rules, stage.** The job runs `dryscope-migrate-live` with the image, releases the field rules to `dryscope-field-live`, and stages the revision with no traffic under the tag `candidate`.
5. **Check.** The read-only live smoke check runs against `https://candidate.app.<domain>`: health reports `live`, the commit, the version and database `ok`; signed-out `GET` requests are refused; the shell, the worker and the manifest load.
6. **Canary, then all.** Before the move the job records the serving revision's commit and version. Ten percent of traffic for ten minutes. During it the read-only check passes again on `https://candidate.app.<domain>` for the candidate's commit and version, and on `https://app.<domain>`, where either revision may answer, for the candidate's pair or the recorded serving pair. If the error-rate alert stays quiet, all traffic; then the check on `https://app.<domain>` must report the candidate's commit and version only. A failure at any point puts the recorded traffic back and marks the release. The relay is released the same way at its own addresses: checked at `voice-candidate.app.<domain>` before it takes traffic.
7. **Record.** The same GitHub Release gains the live part of the manifest (live image digest, live revision, the traffic it replaced, the live rollback command) and stops being a pre-release.
8. **Roll back.** One manual run of the rollback workflow, from a phone, puts back the traffic a release replaced and runs the read-only check, because Cloud Run does not re-check health when traffic is moved back.

Cloud Deploy (canary and one-click rollback as a Google service) replaces steps 6 and 8 after the pilot, before the first paying customer (L7).

### 4.4 Switch-over day

Before the day, every gate in step S8-24 is ticked: both drills written up, the load test passed, the security audit's confirmed findings fixed or accepted, the security gates recorded, the lawyer's answers that gate real signatures recorded (L11), alerts proven on the owner's phone, and a version that has served test for at least a day.

1. **Morning: release.** Approve that version to live. Watch the candidate check, the canary and the record.
2. **Read-only proof.** `https://app.<domain>/api/health` reports `live` and the version. The live scheduler job has run once and the app logged its call as accepted. A test alert reaches the phone. The first on-demand database backup shows location `us`.
3. **Create the company.** The operator creates the first company and binds its sign-in tenant. The owner signs in at the company's link, sets the second step and a spare, fills Company settings (name, address, licence, sign-off, document settings) and enters or imports prices, then publishes them.
4. **Team.** Invite the office user and the estimators by link. Each installs the app to the Home Screen from `app.<domain>`.
5. **First job.** Walk one real job to the review screen on an iPhone, including a spell in Airplane mode. Signing waits for a real customer: a signed record can never be removed, so nobody signs for practice on live. An unsigned practice job is archived afterwards.
6. **Watch.** For 24 hours: the error-rate and uptime alerts, the repair job's runs, the next morning's automated database backup and field-database backup.
7. **Record.** The date, the version and what the owner saw on the phone go in `docs/status/` and `RELEASES.md`, apart from mock results.

### 4.5 Going back, and the points of no return

| Moment | How to go back | Cost |
| --- | --- | --- |
| Any Terraform apply | The plan deletes nothing; the earlier tag is re-applied after a plan that deletes nothing. | 10 to 30 minutes |
| The front door on test misbehaves | Leave ingress open (the lock is a separate apply); test keeps answering at `run.app`. | None |
