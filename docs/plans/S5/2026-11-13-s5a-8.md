# S5 plan correction: 2026-11-13, S5a-8

Part of [the S5 plan](../S5.md), section 12, "Corrections".

- **2026-11-13, S5a-8.** Submit and Back to editing (`web/src/lib/submissions/`, `docs/ACCESS.md` "Submit and Back to editing") use no new capability key and no migration, with these choices the plan left open. (a) Both are `scope` work (owner, estimator) through the one job-access function; the owner may finish an estimator's job. (b) An attempt's expiry is two minutes from its intent row (database clock), and a request closes no fence in the last 30 seconds of it, so a fence never lands after the worker may have given up on its row. While another attempt on the draft is pending and unexpired, a new one is 409 `submission_in_progress` (two phones: one record, one 409); an expired one is aborted in the new attempt's intent transaction, and a fence still held by an aborted row's epoch is replaced (only that exact epoch), so a stalled attempt never blocks the draft for good. (c) A failure to reach Firestore never aborts and never releases: the row stays pending, the same request continues it, and the worker aborts it after the expiry. A release is written only for a row that is aborted, a `submitted` marker only for one that is committed. (d) "Checks every photo reference against the evidence registry (same hash)": a photo reference holds no hash (field map v1), so the check is that every reference names a photo the registry holds for the job; the snapshot records the registry's hash, size and type for each. (e) Submit also aborts a draft that does not map to the engine's inspection (`draft_invalid`: a room with no name, a room order that does not list the rooms), so every record can be priced. (f) The snapshot is canonical JSON (`dryscope-submission-v1`): the draft's canonical form (`web/src/lib/field/canonical.ts`, the one form the phone and the server hash), the photos, the job's address, customer and claim. A commit moves the job to `submitted` (revision plus one); Back to editing moves it to the new draft id, `draft` again (revision plus one) and records the new draft id as its change id, which is how a retry is told from a second call. The new draft is made from the record, not the old draft, with the server keys `previous` (draft and submission) beside `fence` on the fenced draft (comment in `web/firestore.rules`; no rule changed). (g) The worker is the S3-12 scheduled route (`/api/internal/access-projection`): it runs the Submit repair after the access outbox and adds its counts to the answer (`submissions`), so no scheduler or IAM change; the request that decided a row writes its marker first, and the worker waits 60 seconds before writing a lost one. Its audit rows have no person. (h) The S7 correction's "ends any open live session for the draft" has nothing to end yet (no route opens a Live session); the S7 step that opens one adds it to the intent transaction. (i) The job screens (S5a-6) are being built beside this step, so Finish and review is a screen of its own at `/sign-in/{address}/jobs/{id}/finish` that S5a-6's Check Scope links to; it reads the draft from the field database's server (never a cache) after the phone's own writes are acknowledged. Its browser test plays the jobs API at the network boundary because the e2e server runs no Postgres; the Playwright server now passes the Firestore emulator to the browser.
