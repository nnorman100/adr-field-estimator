# S5 plan correction: 2026-11-12, S5a-7

Part of [the S5 plan](../S5.md), section 12, "Corrections".

- **2026-11-12, S5a-7.** Migration `0011_submissions_agreements` holds the four tables and the worker's lookup as planned, with these choices the plan left open. (a) The marker is `marker_state` (`pending`, `done`): `pending` from the start, `done` once the draft's Firestore marker (`submitted` after a commit, back to `editing` after an abort) is written, so the worker's "lost marker" is a decided row still `pending` after a grace period. The lookup is `job_submission_due_companies(max_companies, marker_grace_seconds)` and returns a company with a `pending` row past `expires_at` or such a decided row; the grace is a parameter so the worker, not a migration, sets it. (b) A submission can only be made `pending`; it moves once to `committed` or `aborted`, and the trigger takes `decided_at` from the database clock. The plan's "refuses changes to a committed or aborted row" has one exception, the marker going `pending` to `done`, because the marker is written after the decision. A pending row's identity (job, draft, epoch, digest, expiry, kind, parent, creator) never changes. The runtime's `UPDATE` is `status`, `snapshot_bytes`, `snapshot_sha256` and `marker_state`; the hash is checked against the bytes in the database. (c) There is no "one pending row per draft" key: two attempts on a draft differ by epoch, and the fence in Firestore, not a key, admits one; S5a-8 decides whether a second pending attempt answers 409 before it. A draft id is not checked against the job's `current_draft_id` in the database (a change order's draft is not the current one); that is the route's check. (d) `job_price_pins` takes a job's next sequence by trigger (as `price_table_versions` does), the first pin is `first_price` and later ones `owner_reprice`, and it names its version by `(company_id, version_id)`. (e) An estimate is made only from a committed submission and the job's current pin, and states that pin's version's hash and engine version; an agreement restates its estimate (proposal hash, priced result, version, content hash, engine version), is for the estimate's committed submission with its kind and parent, and is refused if the job's pin moved after the estimate, all by trigger, so S5a-11's route checks have a database backstop. One agreement per submission, estimate and signature object. (f) `agreements` also holds `request_digest` (the plan's section 1 rule: the same id and body is the same agreement, another body is 409) and `created_by_actor_id`, and `job_estimates` holds `created_by_actor_id`, so S5a-9 and S5a-11 need no second migration. (g) No `documents_sha256` column: the plan lists the agreement's proposal SHA-256 and the documents bytes, and the proposal's hash is checked against the estimate's. Sizes: snapshot and proposal 2 bytes to 8 MiB, documents 2 bytes to 16 MiB. (h) Not in this migration: a unique key on `parent_agreement_id` (S5b-9's "two change orders cannot both build on a stale parent" stays a row-lock rule under the job lock unless S5b-9 adds the key), and a bar on a new pin once a job is signed (the route's rule: reprice is refused on a signed job).
