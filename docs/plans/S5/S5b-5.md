# S5 plan, step S5b-5

Part of [the S5 plan](../S5.md), section 5, "Ordered steps".

**S5b-5 Support tools.** UI: the operator's read-only view of a company's jobs, agreements, photos and evidence; support archive and restore. BE: operator routes on S3-9's identity; each view audited; no edit control. DB no (S3-9 policies added in S5 migrations). Tests: each view writes one audit row; a refused request writes none; no customer-data write path exists. Needs: S3-9, S3-15, S5b-2. Scope per J8.

## Corrections

- **2026-11-19, owner decision B.** Support archive and restore leave this step: S5b-5 ships the operator's read-only, audited views only, with no migration. Every write policy on the job tables refuses an active platform operator (migrations 0010 to 0016), so an operator archive or restore would need a new policy. Instead the operator asks the company owner, who holds `jobs_archive`, to archive or restore the job. The views are three routes under `/api/platform/companies/{companyId}/`: `jobs` (every job of the company, archived ones included, in pages), `jobs/{jobId}` (the job's header, customer, claim, signed agreement as stored, and its evidence list: ids, kind, hash, size, type and time, never an object path) and `jobs/{jobId}/photos/{photoId}?kind=photo|original|signature` (the bytes). Each view writes one audit row naming the operator (`support_jobs_viewed`, `support_job_viewed`, `support_photo_viewed`) only after its read succeeds; a refused view writes none. An archived job is shown, not answered 410: the operator is not a company member and needs to see what the owner archived. The operator action is `support_jobs_view` (`docs/access/superadmin.md`). The screens follow in their own pull request.
