# S5 plan, step S5b-5

Part of [the S5 plan](../S5.md), section 5, "Ordered steps".

**S5b-5 Support tools.** UI: the operator's read-only view of a company's jobs, agreements, photos and evidence; support archive and restore. BE: operator routes on S3-9's identity; each view audited; no edit control. DB no (S3-9 policies added in S5 migrations). Tests: each view writes one audit row; a refused request writes none; no customer-data write path exists. Needs: S3-9, S3-15, S5b-2. Scope per J8.

## Corrections

- **2026-11-19, owner decision B.** Support archive and restore leave this step (and only those: the support screens stay in it): S5b-5 ships the operator's read-only, audited views, with no migration. Every write policy on the job tables refuses an active platform operator (migrations 0010 to 0016), so an operator archive or restore would need a new policy. Instead the operator asks the company owner, who holds `jobs_archive`, to archive or restore the job. The views are three routes under `/api/platform/companies/{companyId}/`: `jobs` (every job of the company, archived ones included, in pages), `jobs/{jobId}` (the job's header, customer, claim, signed agreement as stored, and its evidence list: ids, kind, hash, size, type and time, never an object path) and `jobs/{jobId}/photos/{photoId}?kind=photo|original|signature` (the bytes of exactly one `kind`; a missing or repeated `kind` is 400). A signature image is listed and served only when it belongs to a committed agreement of the job (the agreement's `signature_evidence_id`); a signature received for an agreement that never committed stays hidden from the list and the download (404, no audit row). The list and job views read one database snapshot and need no evidence bucket; the bucket is opened only for the bytes, which are read in full before the audit row is written. Each view writes one audit row naming the operator (`support_jobs_viewed`, `support_job_viewed`, `support_photo_viewed`) only after its read succeeds; a refused view writes none. An archived job is shown, not answered 410: the operator is not a company member and needs to see what the owner archived. The operator action is `support_jobs_view` (`docs/access/superadmin.md`). The first pull request of this step is the server slice (the routes above); the support screens, the operator's read-only view of a company's jobs, agreements, photos and evidence, are the next slice of S5b-5, not dropped.
- **2026-11-19, S5b-5 screens.** The second pull request of this step builds the support screens on the routes above, with no new route, key or migration: Manage company gains a Jobs section linking to `/operator/{tenantId}/companies/{companyId}/jobs` (the company's jobs, archived ones too, a page at a time on "Show more jobs") and each job's page (record, customer, claim, signed agreement as stored: its proposal, itemized claim, scope defense letter and photo audit log; and the evidence list). Every read is audited, so each page is read once per opening and an image only on its "Show" button. There is no edit, archive or restore control. The S3-15 rule that the company page shows no customer data now holds for everything on it except that one link ([operator-jobs.md](../../spec/screens/operator-jobs.md)).
