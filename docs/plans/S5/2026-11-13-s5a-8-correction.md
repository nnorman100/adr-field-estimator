# S5 plan correction: 2026-11-13, S5a-8 correction

Part of [the S5 plan](../S5.md), section 12, "Corrections".

- **2026-11-13, S5a-8 correction.** Two statements in the S5a-8 entry above were wrong. (a) Its item (b) says the 30-second margin means a fence never lands after the worker may have given up on its row. It does not: two requests with the same id share an epoch, and one could close the fence after the other had aborted the row, released the draft and written the marker, leaving an aborted row on a `submitting` draft that no one would release. The fence is now closed inside one Postgres transaction that holds the submission row's lock (`SELECT ... FOR UPDATE`) and closes it only while the row is still `pending`. Every abort and commit takes that lock, so no row is decided between the check and the fence, and an aborted row's release always comes after any fence of its epoch. A process that dies holding the lock is rolled back and leaves the row `pending` for the worker. This is the one Firestore call made inside a Postgres transaction. The margin stays, so an attempt does not start a fence its row is about to lose. As a backstop, the worker also writes the release again for an aborted row whose marker is written and whose expiry passed within the last 15 minutes. It does this only in companies that `job_submission_due_companies` returns for other work: a company with nothing else due is not visited, and changing that lookup needs a migration. (b) Its item (f) says a Back-to-editing retry is told from a second call by the job's change id. Other saves overwrite that id, so a retry is now recognized when the job's current draft is the new id and the job's latest committed submission is for the draft named as its source; the change id is still recorded.
