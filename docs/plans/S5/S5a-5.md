# S5 plan, step S5a-5

Part of [the S5 plan](../S5.md), section 5, "Ordered steps".

**S5a-5 Photo receipt and photo read.** BE: `PUT /api/jobs/{id}/photos/{photoId}?kind=photo|original` (raw image, size cap under Cloud Run's 32 MiB request limit): job access with `photos`; the state rule depends on the kind: a photo needs the draft `editing`, an original needs its photo already in the registry with that hash (it may arrive after signing, as in the old app), and a signature (S5a-11) needs a current unsigned estimate; compute SHA-256; create the object with `ifGenerationMatch=0`; on 412 compare the stored hash (same: success, different: 409); insert the registry row once; return the receipt. The phone then writes the reference document. `GET .../photos/{photoId}` streams bytes with `no-store`. Through the app server, so no signing-key IAM change. DB no. Tests: the same photo sent twice gives one object and one row; same id, different bytes 409; an upload to a `submitting` draft refused; **company B cannot fetch A's photo bytes or original** (closes the `spec.md` 4.1 gap). The bucket is replaced by a fake at its boundary in CI; the real precondition is checked in S5a-12. Needs: S5a-2.
