## 1. Summary

- **What S7 delivers**, each as one pull request with a test that fails without it:
  - the AI boundary in TypeScript;
  - the per-company AI budget;
  - five text AI features: findings summary draft (J1), fill scope from words, meter-photo reading, voice-note transcription and job summary;
  - the Live relay, with the walkthrough screen, Model Armor screening, transcript record, resumption, session cap and daily voice budget;
  - per-person voice choice;
  - evaluations with written pass marks;
  - a close-out gate.
- **Risk.** Every step is **High** risk (AI and money boundary, isolation, IAM or workflow), except S7-5 (tests and datasets, Medium) and S7-17 (docs and gate, Medium).
- **One database job, S7-3.** One migration holds every S7 table: AI settings, the spend ledger, AI results, live sessions, live usage, live turns, voice notes and voice settings. This follows the S3-3 precedent, so later steps say "DB: no". It takes the lane after S5a-7.
- **The relay is thin.** `dryscope-live-<env>` has no database access. It admits, records and settles through internal routes on `dryscope-api` with a relay-only route wrapper. At admit, company and member come only from the verified member token, and the job and draft are accepted only after the admission checks (section 4.1). Every later call takes company, member and job from the stored session, and a resume requires the fresh member token to match the stored session. The relay therefore needs no new database or Firestore IAM (V13).
- **Live follows Standard Module C:**
  - server relay only;
  - transparent resumption, with a replay buffer and GoAway reconnect;
  - compression always on;
  - the relay's screened transcript is the record;
  - session state outside the instance;
  - a hard session cap and a per-company daily voice budget;
  - transcription with the language set and a trade vocabulary;
  - μ-law audio (the spike's weak-signal fix);
  - no video by default (V7) and no Live tools in S7 (V2).
- **The text features follow Core generative AI rules:**
  - Gen AI SDK only (no step in S7 is multi-step, so no Genkit);
  - Model Armor floor settings as the fail-open baseline, plus explicit sanitize calls that fail closed;
  - Model Armor's own logging off;
  - budgets, timeouts and per-user quotas;
  - Zod-validated output;
  - human approval of everything a customer sees;
  - AI never prices.
- **Text location.** Text AI calls run on the `us` multi-region endpoint, because G9's regional choice is impossible (V4). Live runs on `us-central1`.
- **Start early.** Six steps can start now, before S5a-2 to S5a-12 and S6 finish: S7-0, S7-1, S7-2, S7-5, S7-11 and S7-15. S7-12 and S7-13 follow on fakes once S7-11 lands. Together they build libraries, Terraform, evals and the relay against fakes (V12). The features wait for their screens and routes (section 6).
- **No agent in S7.** The plan records where agents will run (Cloud Run, ADK TypeScript 2.x) and that A2UI is not adopted (V10).
- **Owner phone check.** One iPhone session after S7-16: earpiece, speaker echo, air-mover noise, lock screen, a Wi-Fi to LTE handover, a 25-minute walk across a GoAway, a relay release during a walk, and a voice change. Results are recorded apart from mock results.

## 3. Design rules every S7 step follows

**One AI boundary.**
- Every model call goes through `web/src/lib/ai/`, in this order:
  1. caller context (company, actor, job) from the verified sign-in;
  2. capability and feature flag;
  3. per-user quota;
  4. budget reservation;
  5. Model Armor screen of the input;
  6. model call with a deadline;
  7. Zod validation;
  8. Model Armor screen of the output;
  9. server rules (price sentences stripped, pre-1978 rules, exact quotes);
  10. settlement;
  11. one allowlisted log line and span.
- A test fails on any `@google/genai` import outside the boundary.

**Explicit screening fails closed.**
- A timeout, a Model Armor error, a skipped required filter or an unsupported payload is never an allow verdict. The call answers "AI not available, try again" and manual work continues.
- The project floor settings (INSPECT_AND_BLOCK) are a fail-open baseline, not the control.

**Model Armor's own logging stays off.**
- `log_sanitize_operations` and floor-setting `enable_cloud_logging` are false, held by a Terraform guard test.
- Template filter versions are pinned. A version bump is a reviewed pull request that re-runs the injection eval.

**AI never prices and never removes wording.**
- No price, total, sizing count or clause comes from a model.
- Server code strips price sentences, as the old `claims.py:417-445` did.
- Documents print only what a person accepted.

**A person approves anything a customer sees.**
- Every AI output is stored as a proposal (`ai_results`, status `proposed`).
- Only the technician's accept writes it into the draft. That is a Firestore field write by the field owner, so the S5 rules and fence apply unchanged.

**Prompts and models are versioned.**
- Prompts are files under `web/src/lib/ai/prompts/`. Their SHA-256 is the prompt version id.
- Each prompt puts its stable instruction first and the job's facts after it, so Google's automatic caching applies (Core: cost).
- `web/src/lib/ai/registry.ts` maps each feature to model, location, prompt version, output cap, deadline, quota, flag and eval suite.
- The TC-8 release manifest reads the registry. Ported prompts start from the old app's text unchanged, except where the input changed (no video frames). The Live walkthrough instructions are the one exception: they are rewritten for the rebuilt app, with the old text as the reference (owner decision 2026-11-16, Corrections).

**Locations.**
- Live runs on the `us-central1` regional endpoint.
- Text runs on the `us` multi-region endpoint (V4).
- The Model Armor text template is in `us-central1`; the image template is in `us` (V3).
- Durable data stays in `us-central1`: Postgres, the field database and the evidence bucket.

**No personal data leaves the process** (hard rule 6).
- No prompt, transcript, audio, image or model text in logs, spans or errors.
- Log lines carry feature, model, prompt version, token counts, latency, outcome code and verdict category only.
- Every step has a test that feeds a crafted email, address and coordinate pair through its path and scans the output.

**Budgets are reserved before work.**
- REST calls reserve a conservative bound (input bytes / 3 plus the output cap) before dispatch, and settle from `usage_metadata`.
- Live reserves the session ceiling plus one worst-case turn and the Finish summary at admission.
- A REST call that meets a quota error (429) retries with exponential backoff inside its deadline. Live fails fast: "busy, try again" (Core generative AI).
- A crash keeps its hold until the sweeper settles it.
- Ceilings are per company, per UTC day and per UTC month, both counting all AI (V5 B: $10 a day and $200 a month by default; a company's explicit ceilings, set by the operator, replace them). Walkthroughs draw most of the daily ceiling, so it is also Module C's daily voice budget.

**Feature switches.**
- Each AI feature has a company flag: `live_voice`, `ai_summary`, `ai_scope_fill`, `ai_meter_reading`, `ai_voice_notes`, `ai_job_summary`. All are off by default.
- Each has an owner, a purpose and a removal date in code (Standard: feature switches).
- The operator turns a flag on for a company only after that feature's eval passes on `test`.

**Offline.**
- Live and REST AI need a connection and say so.
- With no signal, the walkthrough falls back to voice notes (S6-5 queue) and manual entry.
- No AI request is queued silently.

**Same checks as S5 and S6.** Phone width (390 px), Chromium and WebKit, axe and a `screens.ts` entry for every page (TC-4), the modern-web-guidance skill for UI work, and real-service results recorded apart from mock results.

**New dependencies.** Each needs a reason, a publisher, download and repository check, reviewer approval, an exact pin and a release at least two weeks old. The expected ones are `@google/genai` (S7-1), `@google-cloud/modelarmor` (S7-1) and `ws` (S7-11; the spike used `ws@8.18.0`).

## 4. How a live walkthrough works

```
 phone (installed web app)                 dryscope-live-<env> (Cloud Run, TS)             Google, us-central1
 ───────────────────────────               ───────────────────────────────────             ───────────────────
 mic → AudioWorklet → μ-law 16 kHz ──WSS──► first message: start|resume + Firebase ID token
   seq-numbered 40 ms frames                  │  relayRoute call (relay's Google ID token)
   keeps unacked frames (≤ 30 s)              ├──► dryscope-api /api/internal/live/{admit,resume,
 ◄── μ-law reply audio, flush, acks           │      turns,state,heartbeat,quarantine,end}
 ◄── captions (screened text only)            │      (Postgres: live_sessions, live_usage, live_turns, ledger)
                                              ├──WSS──► Gemini Live gemini-3.8-live (ADC, regional)
                                              │          transparent resumption, compression 8k→4k
                                              └──gRPC──► Model Armor us-central1 template
                                                         (streaming sanitize, in parallel, never gating audio)
```

1. **Start.**
   - **Phone.** It opens a socket to the relay. The relay checks `Origin`. Within 10 s the phone sends one message of at most 16 KB: `start`, a fresh Firebase ID token, job and draft ids, a client-made session id, codec `mulaw16k` and protocol `1`. No upstream connection opens before admission. A socket with no valid first message is closed.
   - **Admission.** The relay calls `POST /api/internal/live/admit` through `relayRoute`. That wrapper checks the relay's Google ID token (audience `dryscope-{env}-live`, the relay account only) and then checks the member token with the same identity function as `memberRoute`: signature, tenant, revocation, verified email, and the S3-8 role session limits. **At admit, company and member come from that token only**, never from the relay or the message body; the job and draft ids in the first message are only accepted after the checks below. Every later relay route (`heartbeat`, `state`, `turns`, `quarantine`, `end`) takes company, member and job from the stored session and trusts nothing the relay sends about them; `resume` takes the job and draft from the stored session and requires the fresh member token's company and member to match it (section 4.10). The api then checks:
     - the `live` capability;
     - job access (own or assigned estimator);
     - job unsigned and the draft current and `editing`;
     - the company's `live_voice` flag;
     - the person's daily session count: 20 new sessions a day (V5); a resume does not count.
   - **Lease and reservation.** One open session per person, enforced by a partial unique key on the person's open session (`ended_at` null; S7-3). The admit transaction first takes a row lock on the person's membership row, so two admits by one person (two Start taps, or a retry) run one after the other. Under that lock, a new admit first ends the person's open session, if there is one, through the end path of section 4.12 (settled, hold released, epoch bumped), and only then inserts the new session and reserves. The unique key is the backstop: if an insert still collides, the admit fails with "try again" and reserves nothing. So two Start taps leave one open session and one hold. The api then reserves the session ceiling (V5) plus one worst-case turn plus the Finish summary against the company's daily and monthly AI ceilings. It stores the draft's scope fingerprint on the session.
   - **What the api returns:** a random session capability (stored only as SHA-256), the epoch, the voice (person, then company default, then code default; V6), language `en-US`, the trade vocabulary, the prompt version, and a system instruction built on the server from job facts with no customer name, address or coordinates. It also returns the caps and the next turn sequence number.
2. **Upstream.**
   - The relay screens the system instruction and context text with Model Armor before opening the session (R2 table). It then connects with its own ADC.
   - Settings: `AUDIO` responses; input and output transcription with `language_codes` and `custom_vocabulary`; `speech_config.voice_config.prebuilt_voice_config.voice_name`.
   - Compression `trigger_tokens` 8,000 and `target_tokens` 4,000. These come from the spike's measured cost; if S7-16's recall check fails, the fallback is 16,000 and 8,000.
   - `session_resumption { transparent: true }`. No tools (V2), no video (V7), default VAD (the spike showed tuning does not move latency).
3. **Audio.**
   - **Upload.** Each phone frame carries a sequence number. The relay converts μ-law to PCM16 and sends it upstream, keeping the upstream messages since the last stored handle in memory.
   - **Reply.** 24 kHz reply audio goes back as μ-law with a 150 to 250 ms playout cushion. On `interrupted`, the relay tells the phone to flush.
   - **Never gated.** Audio is never held for screening (R2: detect and contain, not prevent).
4. **Screening and the record.**
   - **Streaming screens.** Input and output transcription chunks go to Model Armor streaming sanitize in realtime mode, in parallel with the audio. A caption reaches the phone only after its chunk passes, about 150 ms late.
   - **Whole-turn screens.** At each turn end, the complete user utterance and the complete reply are screened again.
   - **Recording the turn.** The relay then posts `POST /api/internal/live/turns` with capability, epoch, turn sequence number, speaker, text and verdict.
   - **Verdicts.** `passed`, `blocked`, or `unscreened` (Model Armor unavailable or no transcript). Unscreened fails closed: the turn is kept out of the record, as if blocked.
   - **What the api checks before inserting.** The epoch is current. The session is open. No pending or committed submission exists for the draft (under the job row lock). The `(session, seq)` pair is new; a repeat counts as success.
   - **Downstream rule.** Only `passed` rows ever reach Submit, the summary, scope fill or a restart seed.
5. **A bad verdict.**
   - The relay stops forwarding, tells the phone to flush and plays a fixed line from the phone's assets.
   - It marks the offending turn blocked. After a blocked input, the model's reply to it is blocked too.
   - It closes the upstream connection and calls `/api/internal/live/quarantine`. In one transaction, that closes the current connection at the final cumulative the relay sends with the call (section 4.6), clears the stored handle (the handle counter stays), bumps the epoch and records the verdict category, never the text. It returns the new epoch to the calling relay, which keeps its capability and uses that epoch for every later call.
   - It then starts a clean session seeded with the job context and the last N passed turns. Restarts are capped at 3 per session; the fourth ends the session (section 4.12).
6. **Usage.**
   - The relay sums `usage_metadata` per upstream connection, priced from the registry in Decimal. Connections are numbered from 1 within an epoch, and every upstream connection the relay opens takes the next number: the first, each GoAway reconnect (section 4.8) and each clean restart. A resume or quarantine starts a new epoch, so numbering starts again at 1 there.
   - It posts cumulative totals per (epoch, connection) with each heartbeat and at the end. The api stores the maximum per key in `live_usage` (S7-3), so a retried post never double-settles. The session's cost is the sum of those per-key maxima over every connection and epoch.
   - **Closing a connection.** Each (epoch, connection) is closed exactly once: at the final cumulative when the closing call carries one (GoAway's next post for the old connection, quarantine, `end`), otherwise at its last posted total plus the time floor for its unreported tail. Resume and quarantine close the connection they replace in that call, before the epoch bump; the end path closes only a connection still open.
   - The relay also enforces the session cost cap on its own running estimate, because reported usage arrives late. The estimate starts from the session total the api returns (zero at admit, the summed total at resume) and adds every upstream connection the relay opens, so neither a GoAway nor a resume resets the cap.
7. **Heartbeat, every 20 s.**
   - **What it checks:** membership and company still active; the member's revocation time (Admin SDK) against the stored sign-in time; the S3-8 role session limit; job unsigned; draft `editing`; daily and monthly ceilings; the 45-minute cap measured from the api's `started_at`, not relay memory; and the draft's scope fingerprint against the one stored at admission (the old `scope_fingerprint`: a SHA-256 of the draft without the technician and assistant transcripts, capture metadata, `scope_confirmed`, coordinates and the room shot fields; a change ends the session: "Scope changed. Restart the walkthrough.").
   - **What it does:** renews the 60-second lease and answers `continue`, `warn` (80%) or `end` with a reason.
   - **Only while the phone is there.** The relay sends a heartbeat only while the phone socket is live: open, and the phone has answered the relay's ping (or sent a frame) within the last heartbeat interval. When the phone socket closes or goes silent, the relay stops heartbeating and closes its upstream connection, and calls nothing else. A heartbeat skipped for that reason is not a failed heartbeat. The lease is therefore not renewed for a dead phone, it lapses within 60 s, and the sweeper ends and settles the session (sections 4.11 and 4.14). A phone that reconnects inside the lease is a resume (section 4.10).
   - **Failure:** two missed or failed heartbeats (calls that error or time out while the phone is live) end the session. No token is refreshed over the socket.
8. **GoAway** (relay alive).
   - The relay opens a new upstream connection with the latest handle and replays its in-memory buffer from `last_consumed_client_message_index + 1`; the index resets to 1 on the new connection.
   - **Same epoch, new connection number.** A GoAway does not change the epoch, but the new upstream connection takes the next connection number (n + 1; section 4.6). Its usage posts are keyed `(epoch, n + 1)`. The old connection n is closed by the relay's next post, at its final cumulative. So the first leg stays in the sum of per-connection maxima. If the new leg reused n, its cumulative would start again from zero under the stored maximum for n, and its cost would not be counted until it passed the first leg's.
   - The phone notices nothing.
9. **Stored handle and phone acks** (Standard Module C: "state lives outside the instance").
   - On each `SessionResumptionUpdate` with a new handle, the relay posts `/api/internal/live/state`: capability, epoch, a rising handle counter, the handle, and the highest phone sequence number that handle's snapshot covers. The api stores it only if the epoch is current and the counter is higher than the stored one. The counter belongs to the session, not the relay: it survives GoAway, quarantine and resume, and `resume` returns the stored value (section 4.10), so a new relay's first handle post uses the next number and is accepted. A relay that began counting at 1 again would have every handle post refused as not higher, the stored handle would go stale, and the next resume would start from it.
   - Only after the api confirms does the relay ack that sequence number to the phone. The phone then drops frames up to it.
   - So the phone always holds every frame the stored handle does not cover. The buffer is capped at 30 s (about 480 KB); on overflow the phone marks a gap.
10. **Relay loss** (SIGTERM on release or scale-in, crash, or the 60-minute socket cap, which the relay pre-empts at 55 minutes).
    - **Inside the 10 s.** On SIGTERM, the relay tells the phone to reconnect and posts its final cumulative usage.
    - **Reconnect.** The phone reconnects to any instance with `resume`, a fresh ID token, the session id and its last acked sequence number.
    - **Re-admission.** The new relay calls `/api/internal/live/resume`. That runs every admit check on the fresh token against the stored session's job and draft, and requires the token's company and member to match the stored session. It fails if the session has ended. Otherwise it closes the previous epoch's open connection (no final cumulative can arrive, so last posted plus the tail floor, section 4.6), bumps the epoch and replaces the stored capability hash with a new one, so the old relay's next call gets 409 and it closes its upstream connection. It returns the new capability and epoch, the handle, the stored handle counter, the covered sequence number, the next turn sequence number, the stored voice and language, the trade vocabulary, the system instruction (rebuilt with the admit function; if the draft's scope fingerprint no longer matches the stored one, resume ends the session instead, through the end path of section 4.12: "Scope changed. Restart the walkthrough."), the last N passed turns for a restart seed, and the session's cost so far (the summed total of section 4.6).
    - **Resume.** The relay resumes upstream with the handle, the phone replays the frames after the covered number, and a gap-marker row records the seam.
    - **Fallback.** If there is no handle, Google refuses it, or the phone has a gap, the session restarts clean with the seed, and the assistant says "I missed the last few seconds, please say that again".
11. **Phone drop.**
    - Any reconnect is treated as a resume (epoch bump), whether it lands on the same instance or another.
    - The relay stops heartbeating as soon as the phone socket is gone (section 4.7), so the lease is not renewed while the phone is away. With no reconnect within the 60-second lease, the sweeper ends the session.
12. **Finish.**
    - The phone sends `finish`. The relay sends `audioStreamEnd`, waits up to 3 s for final transcripts, screens and records them, closes upstream and calls `/api/internal/live/end`.
    - **One end path.** Finish, the cost cap, a heartbeat `end`, two missed heartbeats (the relay calls `end`; if it cannot, the lease lapses and the sweeper does), a phone that is gone (no heartbeats, so the lease lapses and the sweeper does), the idle-mic timeout, the fourth restart, a resume refused for a scope change, a new admit by the same person, Submit and the sweeper all end a session the same way, in one transaction: close the connection still open, if any (section 4.6); settle at the sum of the stored per-key maxima; release the unused hold and the lease; bump the epoch; clear the handle; mark the session ended.
    - The phone then offers "Fill scope from walkthrough" (S7-7) and "Draft the summary" (S7-6). Both read passed rows only.
13. **Submit** (S5a-8).
    - The Submit intent-row transaction (under the job row lock) ends any open live session for the draft through the S7 end path (settled, hold released) and bumps its epoch.
    - The snapshot joins only that draft's `passed` turns.
14. **Crash path.**
    - The outbox worker (S3-12, extended by S5a-8) also ends sessions whose lease expired.
    - It ends them through the end path of section 4.12; with no caller, the tail floor applies.
    - `live` has no scheduler until S8 (S6 O8). Until then, holds in `live` wait for S8's wiring; `live` has no users before S8.
15. **Caps.**
    - At the daily ceiling, no new session starts.
    - A session with no speech for 5 minutes ends (idle-mic timeout).
    - The session caps are 45 minutes or $2.50, and a person starts at most 20 sessions a day (V5).
    - At either session cap (time or cost) or the daily ceiling, an open session ends gracefully: a spoken and written notice, the transcript kept, and the Finish summary still possible because its cost was reserved.
