# S3 "Sign-in and company separation": stage plan

Approved plan for stage S3 of the rebuild (the TypeScript app in `web/` and `infra/dryscope/`). Planned 2026-11-09 on `master` at `766f756`; owner decisions D1 to D12 taken 2026-11-10; corrections are in the last section. Reviewers: check each S3 pull request against this file. A step that does something this plan does not name, or leaves out something it does, needs a note in the pull request or a new entry under Corrections here. Plan changes go in this file, in the same pull request as the work that needs them (see [README](README.md)).

## 1. Summary

- S3 splits into **18 steps**, each one agent session. At planning only S3-3 and S3-4 changed the database; the 2026-11-10 corrections make S3-7, S3-9, S3-11b and S3-12 database jobs too. Database jobs run one at a time.
- No step needs the cloud until S3-18, except the owner-run steps in section 6, which the runbook lists in order ([Owner cloud steps, in order](../runbook/owner-cloud-steps.md)).
- **Found in the emulator's own code:** the Firebase Auth emulator (firebase-tools 15.35.0) has no authenticator-app (TOTP) support. It only emulates text-message codes. The real second step can therefore only be proved against the real `test` environment.
- **Not proven yet:** that a `test` service account can be limited to `test` sign-in tenants only. Both environments share project `dryscope`, so Identity Platform is shared. The docs say tenants have their own IAM policy, but whether user-admin calls honour it is unconfirmed. S3-18 must prove it; section 7 gives the fallback.
- The clean start (no old accounts move) removes the old-to-new account mapping. What remains of the rebuild plan's recovery question is enrolment timing and recovery (D8 and D9).

## 3. Ordered steps

Each step is one pull request with a test that fails without it. "DB" means it adds a migration. All steps are High risk (sign-in, isolation, rules).

Design rules every step follows:

- The company always comes from the verified sign-in token (tenant, then company). A company id in a URL, header or body never grants access.
- Every business query runs inside `withCompany(...)`, which opens a transaction and sets the company for that transaction only.
- Each API route declares its access rule beside its own code. A test finds every route by file search and fails on one with no rule. This keeps parallel steps from editing one shared list.
- No emails, tokens or passwords in logs.

### S3-3 Identity tables (migration `0002`)
- **Status:** merged, https://github.com/nnorman100/adr-field-estimator/pull/272
- **Goal:** all S3 tables in one additive migration: new `companies` columns (name, sign-in address, status, `auth_tenant_id`), `actors`, `memberships`, `invitations`, `platform_admins`, `audit_events`, `company_feature_flags`, `access_projection_outbox`.
- **Files:** `web/migrations/0002_*.sql`, `web/src/db/schema.ts`, `web/tests/db/`.
- **Checks:** a second active owner in one company is refused; a second active membership for one actor is refused; `(auth_tenant_id, uid)` is unique; a membership cannot point at an actor or invitation of another company (composite keys); the migration applies on a database that already holds `0001` with a company row.
- **Depends on:** nothing. **DB: yes.**

### S3-4 Runtime role and row-level security (migration `0003`)
- **Status:** merged, https://github.com/nnorman100/adr-field-estimator/pull/285
- **Goal:** the second lock. A non-owner role without `BYPASSRLS`, forced row-level security and a policy on every table, `withCompany`, append-only audit rows.
- **Files:** `web/migrations/0003_*.sql`, `web/src/db/tenant.ts`, `web/tests/db/`.
- **Checks:** as the runtime role, a query outside `withCompany` returns no rows; inside company A it never returns company B's rows, by read, insert, update or delete; one pooled connection used for A, then B, then nothing leaks nothing (including the empty-string value Postgres leaves after a transaction-local setting); the runtime role cannot update or delete `audit_events`, cannot switch role, cannot turn row-level security off; **a guard test fails when any table lacks forced row-level security or a policy**, so later stages cannot add an unprotected table.
- **Depends on:** S3-3. **DB: yes.**
- **Note:** the migration must be identical in every environment, so it grants the role to the environment's IAM database user by pattern and does nothing where none exists (CI).

### S3-6 Firestore rules for the field database
- **Status:** merged, https://github.com/nnorman100/adr-field-estimator/pull/288
- **Goal:** deny by default. Allow only `companies/{companyId}/drafts/...` when the token's tenant matches the company, the caller has an unexpired server-written access record, is the field owner, and the draft is still `editing`. Field-by-field validation comes in S5.
- **Files:** `web/firestore.rules`, `web/tests/emu/rules/`.
- **Checks (emulator, two tenants):** a user of B cannot read or write anything of A; an expired or missing access record is refused; a client cannot write its own access record or any server-owned field; a submitted draft refuses writes; every path not named is refused; an office user can read but not write field data.
- **Depends on:** S3-2. **DB:** no.

### S3-7 Request identity and `/api/me`
- **Status:** merged, https://github.com/nnorman100/adr-field-estimator/pull/290, with migration `0004_sign_in_lookup` (`sign_in_company(tenant)`). **DB: yes, not "no"** (see Corrections).
- **Goal:** one function every route uses: verify the token, read the tenant, find the company, re-verify with the revocation check on that tenant, require a verified email, load the actor and membership, return role and capabilities. Plus the route-rule test described above.
- **Files:** `web/src/lib/auth/`, `web/src/app/api/me/`, `web/src/lib/config.ts`, `web/tests/`.
- **Checks:** a token from tenant B never resolves company A; an unknown tenant, a token with no tenant, a revoked token and an unverified email are each refused; a disabled member and a member of a suspended company are refused; a company id sent by the browser changes nothing; a refused request writes nothing; a route file with no access rule fails the build.
- **Depends on:** S3-1, S3-2, S3-4. **DB:** yes, `0004_sign_in_lookup` (see Corrections).

### S3-8 Second step and session rules on the server
- **Goal:** refuse a role that needs the second step when the token lacks it; refuse a sign-in older than the role's limit; require a fresh sign-in for sensitive actions.
- **Files:** `web/src/lib/auth/policy.ts`, tests.
- **Checks:** an owner token without a second factor gets `second_step_required` on every route except enrolment; an old `auth_time` gets `sign_in_again`; a team change with a stale sign-in is refused; the accepted factor list in production is authenticator app only and cannot be widened by an environment variable.
- **Depends on:** S3-7; D1, D2, D7, D8. **DB:** no.

### S3-9 Platform operator API
- **Status:** built, with migration `0006_platform_operator`. **DB: yes, not "no"** (see Corrections).
- **Goal:** list, create, suspend, reactivate and archive companies (archive needs suspended); invite or replace the owner; bind a company to its sign-in tenant; reset a second step; read-only support view of a company's team; an audit row in the same transaction as every action. Includes the owner-run commands that create a tenant and add an operator.
- **Files:** `web/src/app/api/platform/`, `web/src/lib/platform/`, `web/scripts/`.
- **Checks:** an owner, estimator or office user gets a refusal on every operator route; each action writes exactly one audit row and a refused one writes none; the support view runs read-only and cannot write; no API route can add an operator; replacing an owner disables the old owner and revokes their sessions.
- **Depends on:** S3-7, S3-8; D4, D6, D9, D11. **DB:** yes, a later migration (see Corrections).

### S3-10 Team and invitations API
- **Status:** built; the operator's support routes come with S3-9 (see Corrections).
- **Goal:** owner lists the team, invites by email and role, resends, cancels, clears; changes a member between estimator and office; disables and re-enables. Accepting an invitation creates the actor and membership once. Operator support actions on the same records.
- **Files:** `web/src/app/api/companies/`, `web/src/lib/team/`.
- **Checks:** an account whose verified email differs from the invitation cannot read or accept it; accepting twice makes one membership; an estimator or office user cannot open team routes (office sees only active estimators); the owner cannot be disabled or demoted here; disabling a member revokes their sessions before the call returns; an invitation expires after 7 days; with no email service set up the owner gets a link to copy.
- **Depends on:** S3-7, S3-8; D11. **DB:** no.

### S3-11 Per-company feature flags
- **Status:** splits into S3-11a (built) and S3-11b (the operator's flag route, a database job, built with migration `0008_feature_flag_writes`); see Corrections.

### S3-12 Firestore access records written by the server
- **Status:** **DB: yes, not "no"** (see Corrections).
- **Goal:** after a membership change commits in Postgres, write or remove the Firestore access record through the outbox. Removal blocks server access first and is reported complete only after the Firestore record is confirmed gone. Records are short-lived and renewed while the user is active.
- **Files:** `web/src/lib/projection/`, tests with both emulators.
- **Checks:** a crash between the SQL commit and the Firestore write is repaired by the next run; a removed member's queued offline write is refused by the rules; a grant never appears before its SQL commit; running the outbox twice changes nothing.
- **Depends on:** S3-6, S3-7, and S3-11b (the database job before it). **DB:** yes, a later migration (see Corrections).

### S3-17 Company-isolation gate
- **Goal:** the standard's required test as one named suite and a required check. It seeds two companies in two tenants and, as company B's owner, estimator and office user, calls every registered route with company A's ids. It also checks SQL directly as the runtime role and the Firestore rules. Adds the "A cannot read B" smoke test for the `test` environment.
- **Checks:** every call answers 401, 403 or 404; no list contains A's rows; the operator's view of A writes an audit row; adding a route without adding it to the matrix fails the suite.
- **Depends on:** S3-9 to S3-12. **DB:** no.

### S3-18 Real-service check and close-out
- **Goal:** prove on the real `test` environment what mocks cannot, and update the docs.
- **Checks, recorded apart from mock results:** sign in to a real tenant; enrol and pass a real TOTP second step (the script computes the code from a test-only secret); a revoked session is refused; a tenant-A token is refused for company B; **the `test` app account is refused when it tries to read or change a user in a tenant it is not bound to**; second-step reset then re-enrolment works. Updates `docs/status/` (in the batch after merges), `HANDOFF.md`, `ACCESS.md`, `SECURITY.md`, `DATA.md`, `docs/runbook/` and the phone checklist (sign-in and authenticator on a real iPhone).
- **Depends on:** all above, the owner's cloud steps (section 6), and the S2 keyless release to `test`. **DB:** no.

**Left out on purpose:** company single sign-on (SAML) is set up when a company asks; office customer and assignment data arrive with jobs in S5; the "auth and budget context at every AI entry" rule is delivered by S7's first step, which uses the request context from S3-7. Building any of these now would be code with no user.

## 6. Owner-run cloud steps in project `dryscope`

Agents run none of these. `test` first; near launch repeat the per-environment steps for `live` (runbook item 14); steps 2 and 3 are once per project. The runbook lists these in order with the other owner-only steps and how to check each ([Owner cloud steps, in order](../runbook/owner-cloud-steps.md)); the commands stay here. Lines marked **confirm** use field or flag names taken from the reference but not run. `TOKEN` is `$(gcloud auth print-access-token)`. The two APIs (step 1) and the custom role (step 6) come only from the data-root apply of `infra/dryscope/` (S3-5, https://github.com/nnorman100/adr-field-estimator/pull/289; runbook item 2). Never make either by hand: a role made by hand under the same id makes the apply fail.

1. **Turn on the APIs** `identitytoolkit.googleapis.com` and `firebaserules.googleapis.com`: the data-root apply does this (runbook item 2). No command by hand.
2. **Turn on Identity Platform** (once per project; the project has billing):
   `curl -X POST -H "Authorization: Bearer $TOKEN" -H "X-Goog-User-Project: dryscope" -H "Content-Type: application/json" -d '{}' "https://identitytoolkit.googleapis.com/v2/projects/dryscope/identityPlatform:initializeAuth"`
3. **Project settings: allow tenants, no public sign-up, hide which emails exist** (**confirm** the first and third field names with a `GET` on the same URL first):
   `curl -X PATCH -H "Authorization: Bearer $TOKEN" -H "X-Goog-User-Project: dryscope" -H "Content-Type: application/json" -d '{"multiTenant":{"allowTenants":true},"emailPrivacyConfig":{"enableImprovedEmailPrivacy":true},"client":{"permissions":{"disabledUserSignup":true,"disabledUserDeletion":true}}}' "https://identitytoolkit.googleapis.com/admin/v2/projects/dryscope/config?updateMask=multiTenant.allowTenants,emailPrivacyConfig,client.permissions"`
4. **Add the test app's address** to Identity Platform's authorized domains (Console: Identity Platform, Settings, Security), so sign-in pop-ups and email links work there.
5. **Create the test tenants** (one for operators, two smoke-test companies), each with password sign-in, no public sign-up and TOTP on:
   `curl -X POST -H "Authorization: Bearer $TOKEN" -H "X-Goog-User-Project: dryscope" -H "Content-Type: application/json" -d '{"displayName":"test-operators","allowPasswordSignup":true,"client":{"permissions":{"disabledUserSignup":true,"disabledUserDeletion":true}},"mfaConfig":{"state":"ENABLED","providerConfigs":[{"state":"ENABLED","totpProviderConfig":{"adjacentIntervals":1}}]}}' "https://identitytoolkit.googleapis.com/v2/projects/dryscope/tenants"`
   Repeat with `test-company-a` and `test-company-b`. Note each returned tenant id. After S3-9 merges, its command does this step: `npm run platform:create-tenant -- --project dryscope --name test-operators` from `web/` (the same body).
6. **Custom role for the app's user management:** the data-root apply creates `dryscopeIdentityTest` (output `identity_users_role`) holding only `firebaseauth.users.get`, `firebaseauth.users.create`, `firebaseauth.users.update` and `firebaseauth.users.sendEmail` (runbook item 2). No `users.delete`, no `configs.update`, no tenant create or delete. No command by hand.
7. **Bind that role on each test tenant only, never on the project** (**confirm**: this is the unproven part; S3-18 tests it):
   `curl -X POST -H "Authorization: Bearer $TOKEN" -H "X-Goog-User-Project: dryscope" -H "Content-Type: application/json" -d '{"policy":{"bindings":[{"role":"projects/dryscope/roles/dryscopeIdentityTest","members":["serviceAccount:dryscope-api-test@dryscope.iam.gserviceaccount.com"]}]}}' "https://identitytoolkit.googleapis.com/admin/v2/projects/dryscope/tenants/TENANT_ID:setIamPolicy"`
8. **Browser settings for the web app.** Check whether Firebase is already on the project (`firebase projects:list`). If not: `firebase projects:addfirebase dryscope`. Then `firebase apps:create WEB "DryScope test" --project dryscope` and `firebase apps:sdkconfig WEB APP_ID --project dryscope`. The values are public but restrict the API key to the app's address.
9. **Google sign-in (if D10 is A).** Create one OAuth web client in the Console, then switch Google on for each tenant (Identity Platform, pick the tenant, Providers). The client secret goes in by hand, never in git or chat.
10. **Database bootstrap.** Nothing new. Confirm runbook item 5 was done for `test`: the migrator has `CREATEROLE` and no `BYPASSRLS`, and the owner ran `npm run db:migrate` as `dryscope-migrate-test` until `migration_ledger` holds every file in `web/migrations` (today `0001` to `0006`, including `0004_sign_in_lookup`, which sign-in calls, and `0006_platform_operator`, which the operator routes and commands need). No release or service start runs migrations.
11. **First operator.** Create the user in the `test-operators` tenant (Console), then run the owner-only command from S3-9 to add the operator row: `npm run platform:add-operator -- --tenant TENANT_ID --uid UID --email EMAIL` from `web/`, connected to the database as the migrator itself (migration `0006`'s `add_platform_operator` accepts only the table owner signed in as itself). The rule uses the account's own factor list, so it survives a reload and a retried `GET /api/me`.
