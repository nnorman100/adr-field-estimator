# S6 plan correction: 2026-11-13: S6-3 results and where it differs from the paragraph above

Part of [the S6 plan](../S6.md), section 12, "Corrections".

Built as written (the trusted-device question, the window lock, the persistent single-window cache with its watchdog and memory fallback, the sync gate with the TC-7 App Check step, the offline `me` read, keep-or-discard at sign-out, the O5 limit, `persist()`, `fieldAccessExpiresAt` on `GET /api/me`), with these choices the paragraph and the S6-1 results left open. Each is pinned by a test.

- **One cache per person, by app instance.** S6-1 (c) found the SDK keeps cached documents per app instance, not per person. `web/src/lib/field-db.ts` gives each (company tenant, person) a Firebase app of its own (`dryscope-<tenant>-field-<uid>`); the SDK names its IndexedDB database after the app, so a person's cache and queue are a database no other person's client opens. The company's sign-in stays on the company app (`firebase-client.ts`); the person app's Auth holds an in-memory copy of that user (`updateCurrentUser`, documented for any Auth instance of the same project: `documents/firebase.google.com/docs/reference/js/auth.auth`), made at each start, so nothing new is kept on the phone. This keeps D7 (the same person's unsent work survives a sign-out and is sent at the next sign-in) without the journal, and keeps a second person out of the first person's cached documents.
- **"Unsent work" before the journal.** The watchdog and the sign-out question need to know whether a person has unsent work when the cache cannot be asked (stalled, or not started on the sign-in pages). Until S6-4's journal, `web/src/lib/field/unsent.ts` keeps a mark per (tenant, person) in localStorage (which still answers when IndexedDB hangs): every field write goes through `fieldWrite()`, which sets it first, and it clears once `waitForPendingWrites` resolves with the network on. A mark left behind only costs one extra question or "Reopen the app". The same mark holds when refusals began, for O5's 30 days. S5a-6's writes must go through `fieldWrite()` when it lands.
- **The sync gate** (`web/src/lib/field/sync-gate.ts`) also closes the network when the signal goes, so a long gap cannot let queued writes out before `/api/me` has answered again, and asks again a minute before the record's expiry. A disabled member or inactive company is asked again every 15 seconds while the app is open, which is how an owner's re-enable unlocks the work; the other refusals wait for a new sign-in. App Check is not set up yet (TC-5), so the seam in `field-db.ts` is empty in the app and the tests fill it.
  - *Correction (2026-11-13, owner decision in review):* disabling a member also revokes their sessions (`web/src/lib/team/service.ts`), and that revocation stays: re-enabling restores membership, not the old sign-in. So a disabled member's phone shows "sign in again"; once the owner has turned them back on, they sign in again and the kept work is sent once. A person who signed in again while still turned off sees "access turned off", and that phone is unlocked by the 15-second check when the owner turns them back on. Every refusal is saved on the phone, so a start with no signal stays locked. A check overtaken by a lost signal, a sign-out or a stop never opens the network or reports open.
- **`ds-me`.** The shell adds the company id, role, capabilities and sign-in time to the row at each online check that opens the gate; the sign-in page's row is unchanged. A row without a role or sign-in time does not stand in offline, so a phone signed in and taken offline before the shell ever opened online says "Open the app once online to continue".
  - *Correction (2026-11-13, owner decision in review):* every online sign-in writes the full row, the sign-in page included (company id, role, capabilities and sign-in time from its `GET /api/me`), merged into the saved row so a fact an answer lacks keeps its saved value; the shell's update never brings back a row a sign-out removed. A phone signed in and taken offline before the shell opens works offline. The role's session limit applies always: on every gate decision, every minute while the shell is open, and before any field content shows while the first check is pending. A browser without Web Locks (or one that refuses the lock) gets no field client and says it cannot keep work offline. Work made only in a memory cache (Online only, an iPhone browser tab, the fallback) is not promised as kept: the shell asks before the window is left with such work unsent, and sign-out does not offer Keep for it.
  - *Correction (2026-11-13, second owner decision in review):* the session limit is one check, `sessionValid` in `web/src/lib/field/sync-gate.ts`, on the person's ds-me row (read again before each `GET /api/me`). It gates what the shell shows and what the gate sends in every state: after each answer, before the network goes on, every minute and when the page is shown again. Past it the gate is `expired` (network off, nothing shown, "sign in again"). The sign-in page also registers the field worker, so its install keeps the shell while there is signal. Every "stays on this phone" line has a wording for a cache that keeps nothing, saying the work is lost if the window is left. A revoked sign-in is its own refusal (`session-revoked`), removed after 30 days like a disabled member's, and a saved lock at an offline start goes through the same handling. The network also goes off while the page is hidden or the browser says it is offline, and `GET /api/me` and an enforced App Check token are waited for 15 and 10 seconds at most.
  - *Correction (2026-11-13, final owner decision in review):* the sign-in page shows "Getting DryScope ready to work with no signal…" until the field worker is activated with the shell in its cache, and says the field app is not ready to open with no signal when that fails or takes over 20 seconds. Every "sign in again" lock counts for the 30-day removal, because a revoked sign-in often reaches the phone as no sign-in at all once Firebase ends it; a lock saved at an offline start goes through the same handling. A gate started while the page is hidden asks nothing until the page is shown.
  - *Correction (2026-11-14, S6-3b, owner-approved follow-up, rebuilt as one routine on the owner's decision of the same day, with the removal rule of owner decisions 010 and 011):* locks and the 30-day limit (O5) are one routine, `evaluate(now, event)` in `web/src/lib/field/retention.ts`, and nothing else saves or lifts a lock or removes locked work (the web ESLint config refuses its steps anywhere else, and the raw sign-out and the removal of the saved sign-in in screens). A person is `none`, `locked` (since the first refusal, with its reason) or `hidden` (locked more than 30 days under a refusal O5 applies to). `hidden` is only ever read, from the saved lock and the phone's clock; nothing is written to hide, so any tab may judge it again in any order. Hidden work is neither shown nor sent, and the field app does not open for it offline: the shell shows a short notice in place of the field content, and none of the person's field screens (jobs, scope, customer, photos, and what is typed in them) stays mounted. **Locked work is removed only when the phone is online and the server itself, in the operation that removes, says the person or the company is refused or removed, while they are hidden** (decisions 010, 011): `company_inactive`, `member_disabled`, `not_a_member` or `account_disabled`, from the sync gate's `GET /api/me` or in the answer that makes a screen end the sign-in. The server's other refusals (`sign_in_again`, `sign_in_revoked`, `invalid_token`, `second_step_required`, `email_unverified`, `no_tenant`, `unknown_tenant`) only lock and, after 30 days, hide. A refusal the phone makes itself (no sign-in to ask with, a saved sign-in past its limit, another company's sign-in, an authenticator check, a fresh sign-in Firebase asks for), a "Try again", a retry or a replay never removes anything, and neither does opening the shell or the sign-in page. The removal asks again, once the person's field client has stopped and right before anything is erased, whether the work is still hidden; a let-in meanwhile (another tab) keeps everything. A removal that stops the person's field client and cannot finish, or finds the person let in meanwhile, asks for the app to be opened again. Whether a person's field content may show is one answer of the routine (`contentHidden`: a saved lock or a refusal the page holds, more than 30 days old), asked by the shell, its store and the job screens. A screen keeps the sign-in it sends a request for, and the sign-out a refusal of that request makes ends that sign-in only, never a newer one of the same person. The server letting the person in lifts their own lock however old, so their work shows and is sent again; it changes nothing for anyone else. The state is kept apart from the saved sign-in: the lock in the unsent-work mark (`web/src/lib/field/unsent.ts`), saved only after the company's public browser settings (no email, token or field values). Three events reach it: `refused` (the server's refusal at the sync gate, a sign-out the app makes on the sign-in, Team, Prices, Company and finish screens through `signOutOnRefusal`, and a saved sign-in the gate finds past its role's limit, with or without signal), `let-in` (the gate about to turn the network on, and the sign-in page once it has saved the new row) and `entry` (the field shell and the sign-in page as they open, each time they are shown again and every minute while they stay shown, whatever the shell shows; every other check of the gate). A hidden page runs none of it. After the event every call judges every saved sign-in: one past its role's limit is locked out from then (saved as `sign-in-expired`, shown as "sign in again"), so the clock starts though no server refused it; a lock that only the sign-in's age made is lifted when a newer saved sign-in counts again, which no refusal's lock is. The gate keeps asking the server for hidden work whenever there is signal, because the answer decides: a refusal removes it (the shell says so), "signed in" shows it again. A refusal the phone cannot save is `unsaved`: the sign-out does not happen, the screen says "We couldn't secure your saved work", and "Try again" makes that same sign-out again (it does not reload the page); the gate stays shut and asks again every 15 seconds until it is saved. The page also holds it, with the time it was given, keeps the person's work closed meanwhile, and saves it with that time at the next call that can, so hiding starts on day 30 of the refusal; held or replayed, it only ever locks and hides. The server letting the person in drops what the page holds for them. A sign-out whose saved sign-in cannot be read within 3 seconds does not happen either, but it is the ordinary failure ("Sign-in did not work. Try again."): the person stays signed in with the row and work untouched, and the "couldn't secure" screen stays for a lock that could not be saved. No wait of the gate is open-ended: a poke (the signal back, the page shown again, a new sign-in) calls off the `GET /api/me` or App Check token wait in progress and asks at once, a check with no answer is retried after 10 seconds, an enforced token after 3 seconds, and an enforced token that fails while the network is on turns it off. Random sequences of these events, days passing, storage that refuses and two tabs are checked against the two rules (after 30 days locked, the next entry point shows none of that person's work offline; work is never removed without a fresh refusal from the server, in that operation, saying the person or the company is refused or removed) in `web/tests/unit/retention-property.test.ts` and `web/tests/unit/sync-gate-retention.test.ts` (fast-check), with the examples in `web/tests/unit/retention-machine.test.ts`.
- **Sign-out.** The person's own Sign out asks Keep or Discard only with unsent work; with none, or on Discard, that person's cache for that company is removed (the consent says sign-out removes it), unless a field window is open, which holds it. Every sign-out the app makes itself keeps the work (D7, O5).
- **The consent** is a card in the shell, not a modal, asked before anything is stored; "Online only" uses the memory cache. An iPhone browser tab is not asked and uses the memory cache (G8).
