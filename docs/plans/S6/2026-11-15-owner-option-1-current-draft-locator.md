# S6 plan correction: 2026-11-15: owner option 1, current-draft locator

Part of [the S6 plan](../S6.md), section 12, "Corrections".

The owner approved `companies/{companyId}/jobs/{jobId}` with only `currentDraftId` and the SQL job revision. The server writes it after creating a job/draft and after Back to editing materializes the new draft. Authorized job reads also write it, which populates pre-existing jobs without a bulk database job and repairs missing writes on the next online open. A Firestore transaction refuses regression to an older revision and leaves identical retries unchanged. No client may create, change, remove or list locators; a direct read requires permission on the referenced draft, with the existing tenant/access/second-step checks. This is a rules change, to be reviewed and released by the owner through the existing release workflow; no new API route, capability or SQL migration is added.

`JobScreens` reads the locator itself into the person-scoped cache while online; with no signal it reads that locator and its field maps from the cache. It shows a generic "Saved field work" heading and field inputs, never a fabricated SQL header/customer/claim. SQL edits remain online-only. Newer online locators win over an older response still in flight; a server change never observed by this phone cannot be known offline. The existing retention boundary hides this entire subtree, including the locator-based offline screen. Scope-list copies across reloads remain S6-8.

Tests add real-emulator locator reads/denials, anonymous and foreign-company refusals, owner changes/expired grants, denied collection queries and all client writes, monotonic revision/idempotency checks, database service projection and Back to editing retry tests, plus actual Chromium/WebKit job-URL reopening from the phone cache and a refreshed locator opening the newer draft. The eight checks above still apply; the rules/index check now includes this narrow server-owned projection (no index), and the phone check must include closing/reloading the job while still offline, editing it again and reconnecting. [Firestore granular operations](https://firebase.google.com/docs/firestore/security/rules-structure#granular_operations) informed the single-document read with no list permission.
