# S6 plan correction: 2026-11-15: job screens use the phone's field client

Part of [the S6 plan](../S6.md), section 12, "Corrections".

The job screens mount inside `FieldStore` and its retention boundary. They take the person-scoped client and the online or saved sign-in facts from `useFieldClient()`; `session.ts` no longer starts another Firestore instance or asks `/api/me` independently. Scope, room creation/removal, room inputs, findings, prep tasks and photo references write through `fieldWrite()`. Room-order writes use absolute arrays in the same batch as the room document. A form's local receipt (`local-edit.ts`) waits for the SDK's local transaction, then reads the draft from the cache; it releases the form with **Saved on this phone** only for a persistent cache. A memory cache says the change is lost if the window is left. The write's own promise alone reports the server acknowledgement. The recovery journal and conflict states remain S6-4.

Customer, claim and job creation stay SQL-owned (`data-ownership.md`) and online-only: **Needs a connection**, no offline API queue and no saved API responses. An already open job can still change its field draft without signal. The owner chose a server-written locator on 2026-11-15 (below), so the existing job-only URL can reopen its field draft offline after an online open has cached it. No API response or SQL customer/claim record is cached. Item lists and room-type templates across reloads remain S6-8.

Photo bytes keep the current upload path and page-memory retry, until S6-5 supplies the durable queue. IDs of pending in-memory photos are included in the person's unsent mark before upload; a field acknowledgement cannot clear them. They clear after both the byte receipt and reference acknowledgement, and leaving with any such photo asks first. No bytes or field values go in the mark. The app does not capture photos offline yet; it says a connection is needed. The existing routine alone controls locked-work visibility and server-confirmed removal; this wiring adds no cache deletion.

Regression tests: `tests/e2e/offline/job-edits.spec.ts` drives the actual screens through the network lane in Chromium and WebKit (scope, room inputs/findings/prep, unsent marks, reconnect without replay, edit persistence through reload and reconnect, refused local marks, SQL controls offline, 30-day hidden work). `tests/unit/field-local-edit.test.ts` separates local receipt from acknowledgement and refusal; `field-photo-mark.test.ts` checks photo marks across retries and field acknowledgements. Existing job, room, shell and storage specs continue to cover their user flows; storage specs now inspect the actual Jobs heading instead of the old placeholder.

Eight checks: a narrow read-only locator rule (below), no index/migration or API route change; no old/signed records changed; offline behavior as above; the same capabilities and rules decide access; the worker still caches only the shell/assets; help states explain connection and memory limits; marks contain only IDs/counts/times, with no new logs; real phone checks remain with the owner. Phone check: open a job online, lose signal, save scope, add and edit rooms/findings/prep, restore signal and check the server once; verify customer/claim/new job need a connection and photo uploads warn before leaving. Offline job reopening uses the cached server locator; a job never opened online on this phone asks for one connected open.

References used: [Firebase offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline) (cache reads, local mutations and disabled-network writes), [Chrome's application shell model](https://developer.chrome.com/docs/workbox/app-shell-model) (shell and dynamic content remain separate).
