# S6 plan, step S6-6

Part of [the S6 plan](../S6.md), section 5, "Ordered steps".

**S6-6 Update ready and minimum app version (M).** UI: an "Update ready" banner with **Update now** (disabled, with the reason, while the camera is open or a save or upload is running), and a full-screen "Update needed" for a 426 that keeps the data and offers the same button. FE: the worker waits (no `skipWaiting()` at install), the page watches `registration.waiting`, checks for a new worker on open, when visible and hourly, applies on a tap through a message and reloads once on `controllerchange`; the client sends its epoch in `x-dryscope-client-epoch` on every `/api` write and shows the 426 screen. BE: `web/src/lib/app-version.ts` (`CLIENT_EPOCH` the code was built with, `MIN_CLIENT_EPOCH` the server accepts; O4), `requireCurrentClient()`, called by every non-GET route under `/api/jobs` (create, photo, submissions, estimate, agreements, drafts) and answering 426 `{ "error": "update_required" }` before any record is touched; a unit test finds every such route by file search and fails on one without the call, so later S5 steps cannot forget it (as `route-rules.test.ts` does for access rules). `GET` routes and sign-in routes are exempt, so an old phone can always read and sign in. DB, FS: none. Tests: each write route refuses a stale or missing epoch and writes nothing (no audit row, no submission row); an old phone's queued photos wait, with the data kept, and send after the update; the waiting worker is not activated by a navigation; Update now is refused while capture is open; the worker activates by itself only when every window of the app is closed; the cached shell of the old build still loads its own chunks until then. Needs: S6-2; each S5a route as it lands (the guard test makes the later ones fail until wired). **Helper, guard test and worker flow can start now.**
