# S6 plan, step S6-3

Part of [the S6 plan](../S6.md), section 5, "Ordered steps".

**S6-3 Firestore cache, sync gate and trusted device (L).** UI: "Keep jobs on this phone?" consent shown once per phone and company (what is kept, that it cannot be erased remotely, that sign-out removes it); the offline `me` read; sign-out asks to keep or discard unsent work (only this person's, in this company); "Open the app once online to continue" when the offline sign-in is older than the role's limit. FE: `web/src/lib/field-db.ts` (the one browser Firestore client; S5a-6 imports it, or, if S5a-6 lands first, creates a plain client in this file for S6-3 to change): `initializeFirestore` for the named field database with `persistentLocalCache` and the single-tab manager (O3), a start-up watchdog (S6-1 (e) decides whether it can fall back to the memory cache; with unsent journal entries it shows "Reopen the app" and takes no edits instead, because edits made in memory would be overtaken by the older queued values when the persistent queue replays), the sync gate of section 3, `ds-me` written at each online sign-in and read for the role while offline (valid until the role's session limit, D7; the rules and server still decide), locking on the codes of section 3 and the clear-on-sign-out and O5 rules, `navigator.storage.persist()`, and a second window of the same storage shows "Open DryScope in one window" (a Safari tab and the installed app do not share storage and never see each other). BE: `GET /api/me` also returns `fieldAccessExpiresAt` (the access record's expiry, from the access store in `web/src/lib/projection/`; no email, no uid), and a renewal skipped because the actor was busy is retried by the next call; no new route. DB: none. FS: none (the existing rules already refuse an expired record; S6-3 tests it). Tests: an offline edit survives close and reopen and is sent once; an access record past its 7 days does not drop a queued write because the gate waits until `/api/me` reports a future expiry (a test makes the renewal skip once); a removed or disabled member's phone sends nothing and keeps the work locked (an owner re-enabling the person unlocks it, as the enable route allows); company B's sign-out leaves company A's unsent work alone; a re-sign-in of the same person keeps unsent work (D7, the check S3 left for S6); a different person on the same phone does not see or send the first person's work; the memory fallback shows its banner; sign-out with unsent work asks. Needs: S6-1, S6-2 (the shell it runs in), S3-12, S5a-1, S3-13a. **Can start now.**
