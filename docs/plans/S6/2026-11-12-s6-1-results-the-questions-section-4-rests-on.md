# S6 plan correction: 2026-11-12: S6-1 results, the questions section 4 rests on

Part of [the S6 plan](../S6.md), section 12, "Corrections".

Run with `firebase` 13.1.0, Playwright 1.65.0 (Chromium 158.0.8127.18 and WebKit 27.2, the Linux build, which is not iOS Safari), the Auth and Firestore emulators (`firebase-tools` 15.31.0) and one switchable network lane per test (`web/tests/e2e/offline/lane.ts`). These are emulator results; the real backend and a real iPhone stay with S6-9. Every answer below is pinned by a test in `web/tests/e2e/offline/`, which now run in CI with the rest of the browser suite; a failing one after an SDK bump means the answer changed, so re-read it here first.

- **(a) Settled.** A write made with no signal stays queued through a reload and through closing and reopening the window; the cache shows it as pending, the server has nothing until the network is back, and it is then sent once (the probe was an increment: the server held +1, and still +1 three seconds later). One addition: the Firestore client does nothing until the app first uses it, so a client that is started and not used sends nothing; the field start-up must make a first call (a listener or `waitForPendingWrites()`).
- **(b) Matches section 4 step 2, with three additions.** After a restart a refused write is dropped from the queue and nothing tells the app: `waitForPendingWrites()` resolves normally, no error event reaches anyone, and the listener first shows the unsent edit as if saved (from cache, pending) and then the server's copy without it. While the page is still alive the write's promise rejects with `permission-denied`. So the journal's compare-with-the-server step is needed, as planned. Additions: (1) when the refusal is lost access (the record removed or run out) the person's read is refused as well, so the listener ends with a `permission-denied` error and the step 2 server read fails the same way; S6-4 must read that as "Can't save: access", and read a draft whose `state` is no longer `editing` as "This job was finished". (2) A refused write does not hold up the writes behind it. (3) A refused write queued ahead of an increment made the increment apply twice (both engines, with and without a restart). Field edits are absolute values, as planned, so a repeat is harmless; no field write may use `increment`, `arrayUnion` or any other transform, and S6-4's review checks for that.
- **(c) Differs from section 3 in one point: the cache is not keyed by person.** The queue is: the same person signing out and in again on the same app instance finds the unsent write still queued and sent once; another person signing in on that instance has it withheld (not sent, and not shown to them as pending) until the first person signs in again. Two companies' app instances on one phone keep separate databases and separate queues, and signing out of one leaves the other's queue sending. But cached documents belong to the app instance: a person the rules refuse the read (the server answers `permission-denied`) still reads another person's cached draft, signed in or signed out, offline. Emptying the cache (end the client, then `clearIndexedDbPersistence`) removes it, and removes that person's unsent writes with it, because the queue is in the same database.
- **(d) Single-window manager: no signal, and the second window's offline write is lost.** The second window starts with no error and shows data; if both windows write while offline, only the first window's edit is left after the app is reopened, and only it is sent. The first window's unsent write is not seen by the second window and is not sent while only the second window is open. The multi-window manager keeps both windows' edits, shows one window's unsent edit in the other, and the window that stays open sends it once. So the SDK cannot say "Open DryScope in one window": S6-3 must take its own lock (Web Locks, Safari 15.4 and later) before it creates the Firestore client, and a second window must not create one at all.
- **(e) Not reproduced, and the fallback works on the same app.** 25 reloads and close-and-reopens of a persistent client in WebKit under a Safari 16 desktop identity and under a Safari 26 desktop identity, and in Chromium: every start answered from the cache inside the 5 second watchdog (slowest: 200 ms in Chromium, 524 ms in WebKit under the Safari 16 identity, 199 ms under the Safari 26 one). The hang the SDK issues describe needs the owner's iPhone (S6-9). The stall itself was made with a Firestore database that never opens: the SDK is silent (no error, no snapshot; `getDocFromCache` and `waitForPendingWrites` never answer), so the watchdog is "no cache answer in N seconds". Starting again with the memory cache on the same Firebase app is refused (`failed-precondition`) while the stalled client exists. `terminate()` never finishes on a stalled client, but calling it, without waiting for it, frees the app, and `initializeFirestore` with the memory cache then works at once with the person still signed in, and reads and writes (acknowledged) as normal. So the fallback uses the same app, not a separate instance. Limits: the stalled client's queue stays out of reach (so, as S6-3 says, with unsent journal entries the screen shows "Reopen the app" and takes no edits), and a stall in Auth's own storage is not helped by this.
- **(f) Settled.** A client started with the network switched off in the same tick sends nothing, including writes queued before a restart, while the network itself is up; `waitForPendingWrites()` stays pending; `enableNetwork` sends them. The sync gate of section 3 works as written.

Changes this makes before S6-3 and S6-4 start:

- **S6-3:** the cache does not separate people, so section 3's "a different person on the same phone does not see or send the first person's work" holds for sending only. Before S6-3 starts it must choose how a second person is kept from reading the first person's cached documents; clearing the SDK's persistence at sign-out also removes that person's queued writes (the queue lives in the same database; a test pins it), so S6-4's journal has to hold and re-issue them when the same person signs in again (D7). S6-3 also takes the window lock described in (d) and starts its client with a first call as in (a).
- **S6-4:** the "Can't save" reasons come from the server read, as in (b) (a `permission-denied` read means access, a draft no longer `editing` means finished), and the review checks that no field write is a transform.
