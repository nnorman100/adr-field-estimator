## 1. Summary

- S5 splits into **S5a, 12 steps** (core records and the exactly-once handoff; must land before S7) and **S5b, 12 steps** (the remaining workflows). Each step is one pull request with a test that fails without it. Every step is **High** risk (isolation, pricing, signing or rules).
- **One extra step, S5a-R** (the field-rules release to `test`, automated in the release workflow; J10) sits beside S5a-1 to S5a-12; it is a workflow and IAM change, High risk, and the owner approves it once.
- **Six database jobs** in S5 (S5a-2, S5a-7, S5b-1, S5b-3, S5b-8, S5b-10), one at a time, after the four still ahead of them in the lane (S3-9, S3-11b, S3-12, S4-5). Each migration holds every table its steps already know they need (the S3-3 precedent), so later steps carry "DB: no".
- **The handoff** follows `docs/data-ownership.md` exactly: field work lives in the Firestore field database until **Submit**; Submit closes a fence on the draft, writes one immutable submission record in Postgres, and marks the draft submitted. Pricing, the four documents, review and signing then work only on that record.
- **Retries never mint ids on the server.** Every retryable create carries a client-made uuid and the server stores a SHA-256 of the request beside the record: the same id and body returns the same answer, the same id with a different body answers 409. Every update carries the revision it was based on plus a change id, so a retry after a lost response is not reported as a conflict. This closes the `spec.md` 4.3 drying-reading gap; the old autosave false-conflict case does not arise, because field edits become direct Firestore writes.
- **The pricing plan's S5 steps are adopted and renumbered** (section 10): its pin table joins S5a-7's migration, so S5 saves one database job.
- **Owner hands-on check** sits after S5a-6, the first usable job screens (section 7). Before it, the owner's cloud steps for `test` must be done (the field-rules release, item 12, is replaced by S5a-R, J10); today none is ticked (`docs/runbook/owner-cloud-steps.md`).
- Found while planning: the documents need a written **summary** (`web/src/engine/documents.ts:161`, 1 to 6,000 characters) that today comes from AI, which is S7; and they need the **company profile** (address, licence, sign-off), which the `companies` table does not hold and the runtime cannot write (`web/migrations/0003_runtime_role.sql:124`). J1 and S5a-4 handle both.

## 3. Design rules every S5 step follows

- The company comes only from the verified sign-in; every query runs in `withCompany`; a company or job id in the request never grants access. One job-access function (company, then estimator's own or assigned job, then archived answers 410, then the capability) is used by every job route, as in the old app.
- **Client ids and stored digests** as in section 1. Ids are uuids made on the phone; the server checks the format and that the id is unused or matches.
- **Who owns what** (`docs/data-ownership.md`): field work (year built, rooms, quantities, notes, photo references) in Firestore under `companies/{c}/drafts/{d}`, written by the field owner only; everything official (job header, customer, claim, submissions, estimates, pins, agreements, evidence registry, readings, closes) in Postgres; bytes in the evidence bucket under `companies/{c}/jobs/{j}/...` (no uid or name in the path), created with `ifGenerationMatch=0`.
- **Draft layout:** job-level facts in the draft's `field`; each room in `drafts/{d}/rooms/{roomId}` and each photo reference in `drafts/{d}/photos/{photoId}`, each holding only `field`. Nested documents let the rules check each room (rules cannot loop over a list), keep writes small, and are read as one stable manifest after the fence closes. One Zod schema in `web/src/lib/field/` serves the phone, the server and the rules tests.
- Every write adds one audit row in its transaction (ids and counts only); every new table gets forced row-level security, a company policy, composite company keys, no `DELETE` for the runtime, and, once S3-9 has merged, the read-only operator policy S3-9 defines (so S5b-5 needs no migration). Every new route joins the S3-17 company-isolation matrix.
- Online only in S5: create, save, upload, submit, estimate and sign need a connection. S6 adds the phone queue; client ids make every S5 write safe to replay from it.
- No emails, names, addresses, tokens or photo contents in logs.

## 4. The handoff in this codebase

1. **Finish and review** on the phone waits for its Firestore writes to be acknowledged, computes a SHA-256 over one shared canonical form of what it shows (draft, rooms, photo references), and sends `POST /api/jobs/{id}/submissions` with a new submission id and that digest.
2. **Intent row first.** Under the job row lock the server checks access and that the draft is the job's current draft (`jobs.current_draft_id`), then inserts a `pending` row in `job_submissions` (submission id, draft, server-random epoch, request digest, `expiresAt`). So Postgres knows every fence, and the worker finds stuck ones without a Firestore index. The same submission id with the same digest continues that row; with a different digest it answers 409; an id whose row was `aborted` answers 409 "start again".
3. **Fence.** In a Firestore transaction the server checks the draft is `editing` (or already fenced by this epoch) and sets `state: submitting` with `{submissionId, epoch, expiresAt}`. The rules already refuse every client write from here (`firestore.rules:53`); server writers check the same state in their own transaction.
4. **Snapshot.** It reads the nested manifest, recomputes the digest, checks every photo reference against the evidence registry (same hash), and joins the job header, customer and claim. The snapshot records its own photo ids and hashes; documents list photos from the snapshot, never from the registry by job, so bytes uploaded during the fence change nothing.
5. **Commit or abort, one row decides.** Success: one transaction moves the row `pending` to `committed` with the canonical snapshot bytes and SHA-256. Failure (digest differs, a photo missing): it moves the row to `aborted`. Both are conditional updates on a `pending` row, so whichever lands first wins; a trigger refuses any change to a `committed` or `aborted` row. **Unique `(company_id, draft_id, epoch)`, and one `committed` row per draft: one record per draft.** Idempotent lookups read committed rows only.
6. **Marker or release.** After commit the server marks the draft `submitted` with the record id. After an abort, or when the worker (the S3-12 outbox worker, extended in S5a-8) finds a `pending` row past `expiresAt` and aborts it, the draft goes back to `editing` in a Firestore transaction that requires `state == submitting` and the same epoch, so a stale release never unlocks a newer fence. The worker also writes lost `submitted` markers. Nothing is released by the clock alone, and nothing is released while its row could still commit.
7. Estimate, documents, review and signing read only the committed submission. **Back to editing** (J4) makes a new draft version from the snapshot with its provenance, under the job lock, only from the job's current draft (a second call with another new id answers 409); the old review is void. A signed job changes only through a change order (S5b-9).

## 12. Corrections

Later changes to this plan, newest last.

- **2026-11-12, S5a-2.** Migration `0010_core_job_tables` holds the four tables and the profile columns as planned, with these choices the plan left open. (a) `jobs` is keyed `(company_id, id)` with a client-made `id` and no server default, so a company posting another company's job id collides with nothing and learns nothing; the other tables name a job by the same composite key. The field owner is an actor id (the Firestore uid is looked up from it), empty until someone owns the field work. (b) `revision` rises by exactly one on every change to the job row, status changes and Submit included, and a job starts as a `draft`; `request_digest` covers the create request only, and `last_change_id` is empty until a change carries one. (c) `job_claims` also holds `loss_cause` (the documents print it, `web/src/engine/documents.ts`), adjuster email and phone, so S5a-3 and S5a-9 need no second migration; `date_of_loss` is a `date`, empty when unknown, and that it is a real past date is the Zod schema's check. (d) `evidence_objects` checks that `object_name` sits under its own `companies/<company>/jobs/<job>/` path and holds only letters, digits and `. _ - /`; it has a surrogate `id` with a composite key `(company_id, id)` so S5a-7's agreement can name its signature object. A photo and its full-size original share `object_id` and differ in `kind` (and so in name). (e) The profile columns are `profile_address`, `profile_phone`, `profile_email`, `profile_license`, `profile_signoff`, empty until set. Column rights cannot tell a company's own transaction from an operator's, so a trigger holds the split: a company's own transaction changes the profile only, never `status` or `auth_tenant_id`, and an operator never changes the profile. Two assertions in `platform-operator.test.ts` that a company's status or tenant update "finds no row" now expect the trigger's refusal (check violation) instead; the row stays unchanged in both. (f) No signed-job freeze on `jobs`, `job_customers` or `job_claims` is in this migration (the plan lists none; `a signed job's customer cannot be edited` is S5a-3's route rule, corrections are S5b-4's rows); a restore (S5b-2) finds the status to return to from the job's submissions, because `status` holds `archived` while archived.
- **2026-11-12, S5a-3.** The jobs routes (`web/src/lib/jobs/`, `docs/ACCESS.md` "Jobs routes") use no new capability key and no migration, with these choices the plan left open. (a) J3's "estimator who owns the field work, owner and office" is `scope` or `coordination`, either one suffices (the claim rule of `docs/ACCESS.md` extended to the customer, where the table had only `scope`), and an estimator reaches only a job they made or own in the field (assignment arrives with S5b-1). (b) `PUT .../customer` carries the property address with the customer; both saves replace the whole record (every field required, empty text clears) with `revision` and `changeId`; the same `changeId` with the stored values is the same change and answers the saved job, with other values it is 409. (c) A create whose id is taken answers 201 the first time, 200 for the same body from someone who may see the job, and 409 for another body, another estimator's job or a draft id another job holds. (d) An office user may create a job (`jobs_create`); it has no field owner and its draft has no `fieldOwnerUid` until S5b-1. (e) The list leaves archived jobs out (S5b-2 lists them) and an estimator asking for `scope=company` is refused (403), not narrowed.
- **2026-11-12, S5a-5.** The photo routes (`web/src/lib/photos/`, `docs/ACCESS.md` "Photo routes") use no new capability key and no migration, with these choices the plan left open. (a) One path, `PUT` and `GET /api/jobs/{id}/photos/{photoId}`; `kind` is required on `PUT` (`photo` or `original`; `signature` joins in S5a-11) and defaults to `photo` on `GET`. Sending needs `photos`; reading needs only `jobs_read`, so office sees a job's photos read-only. (b) The plan's "an original needs its photo already in the registry with that hash" is read as: the original names the photo it belongs to with `X-Photo-Sha256` (the hash of the registered 2,560 px copy), because the registry holds no promised hash of the original to compare against; a missing photo is 409 `photo_missing`, another hash 409 `photo_conflict`. (c) Object names are `companies/{c}/jobs/{j}/photos/{id}` and `.../originals/{id}`: no hash or extension, so a second upload of the same id meets `ifGenerationMatch=0` whatever its bytes or type; the object carries its own `sha256` in metadata so the 412 path can compare it, and a retry that finds the bytes already stored (the registry row never made) registers them. (d) The image type comes from the bytes (JPEG, PNG, WebP, as in the old app), never from the request's Content-Type; the cap is 30 MiB and a body is read only after access is settled. (e) A photo already registered answers its receipt, and other bytes 409, whatever the draft's state, so a lost answer is settled by sending again; only a new photo is refused by a locked draft (`draft_locked`), checked on the job's status under its row lock and on the field draft's `state` read from Firestore before the bytes are stored. A fence that lands between that read and the row changes nothing, because the submission's snapshot lists its own photo ids and hashes (section 4, step 4). (f) `EVIDENCE_BUCKET` (already set by Terraform) is now read by the app (`parseEvidenceConfig`); the app account already holds create and view on the bucket, so there is no IAM change. The bucket adapter uses `firebase-admin/storage`, so there is no new dependency.
