Each migration holds every table its steps already know they need (the S3-3 precedent), so later steps carry "DB: no".
- **The handoff** follows `docs/data-ownership.md` exactly: field work lives in the Firestore field database until **Submit**; Submit closes a fence on the draft, writes one immutable submission record in Postgres, and marks the draft submitted. Pricing, the four documents, review and signing then work only on that record.
- **Retries never mint ids on the server.** Every retryable create carries a client-made uuid and the server stores a SHA-256 of the request beside the record: the same id and body returns the same answer, the same id with a different body answers 409. Every update carries the revision it was based on plus a change id, so a retry after a lost response is not reported as a conflict. This closes the `spec.md` 4.3 drying-reading gap; the old autosave false-conflict case does not arise, because field edits become direct Firestore writes.
- **The pricing plan's S5 steps are adopted and renumbered** (section 10): its pin table joins S5a-7's migration, so S5 saves one database job.
- **Owner hands-on check** sits after S5a-6, the first usable job screens (section 7). Before it, the owner's cloud steps for `test` must be done (the field-rules release, item 12, is replaced by S5a-R, J10); today none is ticked (`docs/runbook/owner-cloud-steps.md`).
- Found while planning: the documents need a written **summary** (`web/src/engine/documents.ts:161`, 1 to 6,000 characters) that today comes from AI, which is S7; and they need the **company profile** (address, licence, sign-off), which the `companies` table does not hold and the runtime cannot write (`web/migrations/0003_runtime_role.sql:124`). ## 3. Design rules every S5 step follows

- The company comes only from the verified sign-in; every query runs in `withCompany`; a company or job id in the request never grants access. One job-access function (company, then estimator's own or assigned job, then archived answers 410, then the capability) is used by every job route, as in the old app.
- **Client ids and stored digests** as in section 1. Ids are uuids made on the phone; the server checks the format and that the id is unused or matches.
- **Who owns what** (`docs/data-ownership.md`): field work (year built, rooms, quantities, notes, photo references) in Firestore under `companies/{c}/drafts/{d}`, written by the field owner only; everything official (job header, customer, claim, submissions, estimates, pins, agreements, evidence registry, readings, closes) in Postgres; bytes in the evidence bucket under `companies/{c}/jobs/{j}/...` (no uid or name in the path), created with `ifGenerationMatch=0`.
- **Draft layout:** job-level facts in the draft's `field`; each room in `drafts/{d}/rooms/{roomId}` and each photo reference in `drafts/{d}/photos/{photoId}`, each holding only `field`. Nested documents let the rules check each room (rules cannot loop over a list), keep writes small, and are read as one stable manifest after the fence closes. One Zod schema in `web/src/lib/field/` serves the phone, the server and the rules tests.
- Every write adds one audit row in its transaction (ids and counts only); every new table gets forced row-level security, a company policy, composite company keys, no `DELETE` for the runtime, and, once S3-9 has merged, the read-only operator policy S3-9 defines (so S5b-5 needs no migration). Every new route joins the S3-17 company-isolation matrix.
- Online only in S5: create, save, upload, submit, estimate and sign need a connection. S6 adds the phone queue; client ids make every S5 write safe to replay from it.
- No emails, names, addresses, tokens or photo contents in logs.

## 4. The handoff in this codebase

1. **Finish and review** on the phone waits for its Firestore writes to be acknowledged, computes a SHA-256 over one shared canonical form of what it shows (draft, rooms, photo references), and sends `POST /api/jobs/{id}/submissions` with a new submission id and that digest.
2. **Intent row first.** Under the job row lock the server checks access and that the draft is the job's current draft (`jobs.current_draft_id`), then inserts a `pending` row in `job_submissions` (submission id, draft, server-random epoch, request digest, `expiresAt`). So Postgres knows every fence, and the worker finds stuck ones without a Firestore index. The same submission id with the same digest continues that row; with a different digest it answers 409; an id whose row was `aborted` answers 409 "start again".
3. **Fence.** In a Firestore transaction the server checks the draft is `editing` (or already fenced by this epoch) and sets `state: submitting` with `{submissionId, epoch, expiresAt}`. The rules already refuse every client write from here (`firestore.rules:53`); server writers check the same state in their own transaction.
4. **Snapshot.** It reads the nested manifest, recomputes the digest, checks every photo reference against the evidence registry (same hash), and joins the job header, customer and claim. The snapshot records its own photo ids and hashes; documents list photos from the snapshot, never from the registry by job, so bytes uploaded during the fence change nothing.
5. **Commit or abort, one row decides.** Success: one transaction moves the row `pending` to `committed` with the canonical snapshot bytes and SHA-256. Failure (digest differs, a photo missing): it moves the row to `aborted`. Both are conditional updates on a `pending` row, so whichever lands first wins; a trigger refuses any change to a `committed` or `aborted` row. **Unique `(company_id, draft_id, epoch)`, and one `committed` row per draft: one record per draft.** Idempotent lookups read committed rows only.
6. **Marker or release.** After commit the server marks the draft `submitted` with the record id. After an abort, or when the worker (the S3-12 outbox worker, extended in S5a-8) finds a `pending` row past `expiresAt` and aborts it, the draft goes back to `editing` in a Firestore transaction that requires `state == submitting` and the same epoch, so a stale release never unlocks a newer fence. The worker also writes lost `submitted` markers. Nothing is released by the clock alone, and nothing is released while its row could still commit.
7. Estimate, documents, review and signing read only the committed submission. **Back to editing** (J4) makes a new draft version from the snapshot with its provenance, under the job lock, only from the job's current draft (a second call with another new id answers 409); the old review is void. A signed job changes only through a change order (S5b-9).
