# Owner cloud steps, in order

The one list of steps only the owner runs for the rebuilt app: test in project `dryscope`, live in its own project `dryscope-live` (item 14). Agents never run them. Do **test** first and tick each box only after its check passes; repeat the per-environment items for **live**, in the live project, as item 14 and the [S8 plan](../plans/S8.md) say. Nothing in this repository records any of them as done: `infra/dryscope/` has not been applied, so every box starts empty. This list links to the detail instead of repeating it; the sign-in commands are in the [S3 plan, section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) (**confirm** marks there are fields not yet run). When a stage adds an owner step, add it here in its place in the order.

- [ ] **1. Project bootstrap.** Link billing, enable the bootstrap APIs, create the state bucket `gs://dryscope-tfstate` ([Apply the central Terraform](terraform-apply.md#apply-the-central-terraform), step 2). Needs: the project and the owner's identity. Verify: `gcloud services list --enabled --project=dryscope` lists them; the bucket is private and versioned.
- [ ] **2. Sign-in plan and apply (data root, test).** Run `infra/dryscope/scripts/check.sh`, then plan, run `check-plan.js` and apply the `data` root ([step 3 and 4](terraform-apply.md#apply-the-central-terraform)). This also turns on the two sign-in APIs and creates the unbound role `dryscopeIdentityTest` ([sign-in user role](terraform-apply.md#sign-in-user-role)); do not create either by hand. Needs: item 1. Verify: `check-plan.js` exits 0, the plan deletes nothing except the four named grants on a re-apply, and, on an instance applied before the backup location moved to the US multi-region, shows one in-place update of `settings.backup_configuration.location` to `us` (no replace, no destroy; the plan check accepts that one change and refuses a regional location), and after the apply a second plan shows no changes. The new location applies only to backups taken after the apply; earlier ones stay in `us-central1`. So after the apply take one on-demand backup as a location check only (`gcloud sql backups create --instance=dryscope-<env>-pg --project=dryscope`) and confirm `gcloud sql backups list --instance=dryscope-<env>-pg --project=dryscope --format="table(id,status,location,windowStartTime)"` shows it `SUCCESSFUL` with location `us`.
- [ ] **3. Secret values.** Add a value to each `dryscope-test-*` secret ([step 4](terraform-apply.md#apply-the-central-terraform)), never through Terraform or chat. Needs: item 2. Verify: `gcloud secrets versions list dryscope-test-<name> --project=dryscope` shows an enabled version for each.
- [ ] **4. Keyless deploy pool.** Create the workload identity pool `dryscope-test` (its own pool, one provider), then re-plan and apply the data root with `-var workload_identity_principal_set=...` ([step 9](terraform-apply.md#apply-the-central-terraform)). Needs: item 2. Verify: the plan check accepts the principal set; the principal set names `dryscope-test` and one repository id; `gcloud iam workload-identity-pools describe dryscope-test --location=global --project=dryscope` returns it.
- [ ] **5. Database setup grants.** As a privileged Cloud SQL user through the Auth Proxy, from Cloud Shell or any machine that reaches the instance (the build server does not), give the migrator `CREATEROLE` and `CREATE` on the database and `USAGE, CREATE` on schema `public` (never `cloudsqlsuperuser` or `BYPASSRLS`); no migration runs here ([step 5](terraform-apply.md#apply-the-central-terraform); [Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test), part B). Needs: item 2 (the instance and IAM users exist). Verify: `\du "dryscope-migrate-test@dryscope.iam"` shows `Create role`. The migrations themselves run in item 9.
- [ ] **6. Identity Platform on, project settings, authorized domains.** [S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) steps 2 to 4: `initializeAuth`, allow tenants, no public sign-up, hide which emails exist, add the test app's address. Needs: item 2 (the APIs are on). Verify: a `GET` on the project config returns the settings; sign-in settings are shared by `test` and `live`, so this is owner-run only.
- [ ] **7. Test tenants and the per-tenant role binding.** Create `test-operators`, `test-company-a` and `test-company-b` (one `npm run platform:create-tenant -- --project dryscope --name <name>` each, from `web/`, with your own `gcloud auth application-default login`), then bind `dryscopeIdentityTest` to `dryscope-api-test` on each tenant only, never on the project ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) steps 5 and 7; [sign-in user role](terraform-apply.md#sign-in-user-role)). Since 2026-11-14 (D-030) the command also gives each new tenant a 12-character password rule and email enumeration protection; for any tenant made before that, run `npm run platform:secure-tenants -- --project dryscope` (it only reads), check the list, then run it again with `--apply` ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) step 5). Since TC-6 it also sets sign-in reCAPTCHA to audit mode; tenants made before that are set by `npm run platform:recaptcha -- --tenant <id> --mode audit` (the project comes from your gcloud default project, or `--project dryscope`) once the reCAPTCHA Enterprise API and the Identity Platform service identity are in place ([TC plan section 7](../plans/TC.md) steps C and E). Needs: items 2 and 6. Verify: each tenant's IAM policy shows the one binding, and the project's policy shows none for this role; `npm run platform:secure-tenants -- --project dryscope` reports every tenant as `already set`. That the binding limits the account to those tenants is not yet proven; S3-18 proves it (item 13).
- [ ] **8. Web app config and Google sign-in.** Register the Firebase web app, restrict its API key to the test app's address, create the Google OAuth client and switch Google on per tenant ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) steps 8 and 9). Needs: items 6 and 7. Verify: the sdk config prints; Google appears under each tenant's providers; the client secret is in no file or chat.
- [ ] **9. First test deploy.** Build and push the first images by digest, then plan, run `check-plan.js` and apply the `app` root ([step 6](terraform-apply.md#apply-the-central-terraform)), with `ALLOWED_ORIGINS` set from `envs/test.tfvars`. Needs: items 3 to 5. Verify: `GET /api/health` on the test service answers; the plan check passes; test services scale to zero ([step 7](terraform-apply.md#apply-the-central-terraform)); the release run started after the apply (part D) passes its migrate step, so `migration_ledger` holds every file in `web/migrations` ([Postgres migrations](migrations.md#postgres-migrations-for-the-rebuilt-app)), and a second `gcloud run jobs execute dryscope-migrate-test --region=us-central1 --project=dryscope --wait` applies nothing, and the Cloud Scheduler job `dryscope-access-projection-test` runs ([scheduled job calls](terraform-apply.md#scheduled-job-calls): `gcloud scheduler jobs run` it once and the web app's request log shows `POST /api/internal/access-projection` answered 200). Then take an on-demand backup of the migrated database (`gcloud sql backups create --instance=dryscope-test-pg --project=dryscope`) and confirm it is `SUCCESSFUL` with location `us`, so a restore does not depend on the next 09:00 UTC automated backup.
- [ ] **10. Runtime-role check after the deploy.** Run the check query in [step 5](terraform-apply.md#apply-the-central-terraform): `dryscope-api-test@dryscope.iam` must hold one membership, `dryscope_runtime`, with inherit `t` and set `f`. If the IAM user was created after `0003` ran, run the `GRANT` that step names first. Needs: items 5 and 9. Verify: exactly that one row.
- [ ] **11. First operator.** Create the user in the `test-operators` tenant (Console), then, from `web/`, run `npm run platform:add-operator -- --tenant <test-operators tenant id> --uid <the user's uid> --email <their email>` signed in to the database as the migrator itself (`dryscope-migrate-test`, through the Auth Proxy, as for item 5; the command refuses anyone else, including a superuser who has switched role) ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) step 11). It registers the tenant as the operator tenant, adds the operator and one audit row, and prints the operator's id; running it again changes nothing. Then the operator creates each test company and binds it to its tenant (`POST /api/platform/companies`, then `.../tenant`). Needs: items 7 and 10 and S3-9 merged. Verify: the operator opens `/operator/<test-operators tenant id>` on the test app, signs in with a second step and sees the Companies screen; no API adds operators.
- [ ] **12. Field-database rules (test): automated.** The owner no longer releases them by hand for `test` (S5 decision J10, option B). Every test release run releases `web/firestore.rules` to `dryscope-field-test` itself, in the deploy job before any traffic moves, and creates nothing when the file is unchanged ([Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test), the deploy job). The owner's only part is the data-root re-apply in item 4 (or item 2 on a first apply), which creates the role `dryscopeRulesReleaseTest` and grants it to `dryscope-deploy-test` ([field rules release role](terraform-apply.md#field-rules-release-role)). Needs: items 2 and 4, and S3-6 merged (https://github.com/nnorman100/adr-field-estimator/pull/288). Verify: the first release run after item 9 shows the `Release the field-database rules` step printing `released projects/dryscope/rulesets/<id> to projects/dryscope/releases/cloud.firestore/dryscope-field-test (first release)` (or `, was <earlier ruleset>` if the database already had a release), a later run with the same file prints `unchanged`, and a signed-in user of company B is refused on company A's path in `test`.
- [ ] **13. Real-service sign-in check (S3-18).** Run the checks S3-18 lists, recorded apart from mock results, including that the `test` app account is refused on a tenant it is not bound to. Needs: items 7 to 12. Verify: the S3-18 record exists; if the tenant-only refusal fails, stop before any live tenant and decide the separate-test-project fallback ([S3 plan section 7](../plans/S3.md#7-risks)).
- [ ] **13a. Restore drill (test).** Run steps 1 to 3 of [Restore into another region](backups.md#restore-into-another-region) against `dryscope-test-pg`, restoring into a region other than `us-central1`, using a backup whose `backupInterval.startTime` is after item 9's migrations, then delete the drill instance by hand. Needs: item 9 (there is data to restore, and its post-migration backup) and the data root applied with the backup location at `us` (item 2). Verify: the restored copy shows every `migration_ledger` file, and the date and result are in `RELEASES.md`. Repeat each quarter.
- [ ] **14. Live, in its own project.** Live is not more resources in project `dryscope`: it is project `dryscope-live` (D-018; S8 decision L5), created by the owner with no organization and the `dryscope` billing account. Repeat items 1 and 6 **in the live project** (project bootstrap with its own state bucket; Identity Platform on, with live's own tenants and authorized domains) and every per-environment item with `envs/live.tfvars`: 2 (data root), 3 (`dryscope-live-*` secrets), 4 (the keyless pool `dryscope-live`, tied to the GitHub environment `live`), 5 (`dryscope-migrate-live` grants), 7 (live tenants, binding `dryscopeIdentityLive` to `dryscope-api-live` on each live tenant only), 8 (live web app, key restricted to the live address, Google on for each live tenant), 9 (app root), 10 (runtime-role check) and 11 (live operator). The live field rules are released by the live leg of the release workflow once S8-18 exists. Nobody is copied from test to live: the first company is created fresh. The Terraform for the live project, the domain and the front door is code first (S8-8 to S8-15), so this item is rewritten as `docs/runbook/live-project.md` in S8-20; the order, checks and gates are in the [S8 plan](../plans/S8.md), section 7.
