# Owner cloud steps, in order

The one list of steps only the owner runs for the rebuilt app in project `dryscope`. Agents never run them. Do **test** first and tick each box only after its check passes; repeat the per-environment items for **live** only when the owner decides (item 14). Nothing in this repository records any of them as done: `infra/dryscope/` has not been applied, so every box starts empty. This list links to the detail instead of repeating it; the sign-in commands are in the [S3 plan, section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) (**confirm** marks there are fields not yet run). When a stage adds an owner step, add it here in its place in the order.

- [ ] **1. Project bootstrap.** Link billing, enable the bootstrap APIs, create the state bucket `gs://dryscope-tfstate` ([Apply the central Terraform](terraform-apply.md#apply-the-central-terraform), step 2). Needs: the project and the owner's identity. Verify: `gcloud services list --enabled --project=dryscope` lists them; the bucket is private and versioned.
- [ ] **2. Sign-in plan and apply (data root, test).** Run `infra/dryscope/scripts/check.sh`, then plan, run `check-plan.js` and apply the `data` root ([step 3 and 4](terraform-apply.md#apply-the-central-terraform)). This also turns on the two sign-in APIs and creates the unbound role `dryscopeIdentityTest` ([sign-in user role](terraform-apply.md#sign-in-user-role)); do not create either by hand. Needs: item 1. Verify: `check-plan.js` exits 0, the plan deletes nothing except the four named grants on a re-apply, and after the apply a second plan shows no changes.
- [ ] **3. Secret values.** Add a value to each `dryscope-test-*` secret ([step 4](terraform-apply.md#apply-the-central-terraform)), never through Terraform or chat. Needs: item 2. Verify: `gcloud secrets versions list dryscope-test-<name> --project=dryscope` shows an enabled version for each.
- [ ] **4. Keyless deploy pool.** Create the workload identity pool `dryscope-test` (its own pool, one provider), then re-plan and apply the data root with `-var workload_identity_principal_set=...` ([step 9](terraform-apply.md#apply-the-central-terraform)). Needs: item 2. Verify: the plan check accepts the principal set; the principal set names `dryscope-test` and one repository id; `gcloud iam workload-identity-pools describe dryscope-test --location=global --project=dryscope` returns it.
- [ ] **5. Database setup grants.** As a privileged Cloud SQL user through the Auth Proxy, from Cloud Shell or any machine that reaches the instance (the build server does not), give the migrator `CREATEROLE` and `CREATE` on the database and `USAGE, CREATE` on schema `public` (never `cloudsqlsuperuser` or `BYPASSRLS`); no migration runs here ([step 5](terraform-apply.md#apply-the-central-terraform); [Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test), part B). Needs: item 2 (the instance and IAM users exist). Verify: `\du "dryscope-migrate-test@dryscope.iam"` shows `Create role`. The migrations themselves run in item 9.
- [ ] **6. Identity Platform on, project settings, authorized domains.** [S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) steps 2 to 4: `initializeAuth`, allow tenants, no public sign-up, hide which emails exist, add the test app's address. Needs: item 2 (the APIs are on). Verify: a `GET` on the project config returns the settings; sign-in settings are shared by `test` and `live`, so this is owner-run only.
- [ ] **7. Test tenants and the per-tenant role binding.** Create `test-operators`, `test-company-a` and `test-company-b`, then bind `dryscopeIdentityTest` to `dryscope-api-test` on each tenant only, never on the project ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) steps 5 and 7; [sign-in user role](terraform-apply.md#sign-in-user-role)). Needs: items 2 and 6. Verify: each tenant's IAM policy shows the one binding, and the project's policy shows none for this role. That the binding limits the account to those tenants is not yet proven; S3-18 proves it (item 13).
- [ ] **8. Web app config and Google sign-in.** Register the Firebase web app, restrict its API key to the test app's address, create the Google OAuth client and switch Google on per tenant ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) steps 8 and 9). Needs: items 6 and 7. Verify: the sdk config prints; Google appears under each tenant's providers; the client secret is in no file or chat.
- [ ] **9. First test deploy.** Build and push the first images by digest, then plan, run `check-plan.js` and apply the `app` root ([step 6](terraform-apply.md#apply-the-central-terraform)), with `ALLOWED_ORIGINS` set from `envs/test.tfvars`. Needs: items 3 to 5. Verify: `GET /api/health` on the test service answers; the plan check passes; test services scale to zero ([step 7](terraform-apply.md#apply-the-central-terraform)); the release run started after the apply (part D) passes its migrate step, so `migration_ledger` holds every file in `web/migrations` ([Postgres migrations](migrations.md#postgres-migrations-for-the-rebuilt-app)), and a second `gcloud run jobs execute dryscope-migrate-test --region=us-central1 --project=dryscope --wait` applies nothing.
- [ ] **10. Runtime-role check after the deploy.** Run the check query in [step 5](terraform-apply.md#apply-the-central-terraform): `dryscope-api-test@dryscope.iam` must hold one membership, `dryscope_runtime`, with inherit `t` and set `f`. If the IAM user was created after `0003` ran, run the `GRANT` that step names first. Needs: items 5 and 9. Verify: exactly that one row.
- [ ] **11. First operator.** Create the user in the `test-operators` tenant (Console), then run the owner-only command from S3-9 to add the operator row ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) step 11). Needs: items 7 and 10 and S3-9 merged. Verify: the operator signs in with a second step and sees the Companies screen; no API adds operators.
- [ ] **12. Field-database rules (test).** After the rules change merges, deploy them to `dryscope-field-test` only, through the rules REST API release `cloud.firestore/dryscope-field-test` ([S3 plan section 6](../plans/S3.md#6-owner-run-cloud-steps-in-project-dryscope) step 12; creating the ruleset first is the dry run). Needs: S3-6 merged (https://github.com/nnorman100/adr-field-estimator/pull/288). Verify: the emulator rules tests pass against the same file, and a signed-in user of company B is refused on company A's path in `test`.
- [ ] **13. Real-service sign-in check (S3-18).** Run the checks S3-18 lists, recorded apart from mock results, including that the `test` app account is refused on a tenant it is not bound to. Needs: items 7 to 12. Verify: the S3-18 record exists; if the tenant-only refusal fails, stop before any live tenant and decide the separate-test-project fallback ([S3 plan section 7](../plans/S3.md#7-risks)).
- [ ] **14. Live.** Only after item 13 is clean and the owner approves: repeat only the per-environment items for live, with `envs/live.tfvars` and the live backend files ([step 8](terraform-apply.md#apply-the-central-terraform)): item 2 (data root), 3 (`dryscope-live-*` secrets), 4 (pool `dryscope-live` with its attribute condition), 5 (`dryscope-migrate-live` grants; its migrations run from the `dryscope-migrate-live` job once item 9 creates it), 7 (live tenants, binding `dryscopeIdentityLive` to `dryscope-api-live` on each live tenant only), 8 (live web app, API key restricted to the live address, Google on for each live tenant), 9 (app root), 10 (runtime-role check for `dryscope-api-live@dryscope.iam`), 11 (live operator) and 12 (rules release `cloud.firestore/dryscope-field-live`). Items 1 and 6 are once per project and are not repeated; the only live change there is adding the live app's address to the authorized domains (S3 plan section 6 step 4). Then, in the owner's own timing and each its own approval: the public address and front door, and the later retirement of the old app in `alert-disaster-field-2026` (deletions are owner-only). Needs: item 13. Verify: each item's check, against live resources only.
