# Backups

Daily copies of logins and evidence photos go to a separate vault bucket (7-day soft delete, 90-day lifecycle). Last restore test: [not recorded — schedule one].

The rebuilt app's Cloud SQL instances (`dryscope-<env>-pg`) keep their automated backups in the US multi-region (`us`, set in `infra/dryscope/data/sql.tf`), so a regional outage in `us-central1` does not take the backups with it. There is no separate export, replica or extra bucket. Point-in-time recovery needs the instance's own region, so it is lost in a regional outage: recovery then loses up to one day (the last daily backup). Firestore stays in its own region with point-in-time recovery, which field work offline depends on.

## Restore into another region

Use this when `us-central1` is down, and for the quarterly drill. Owner-run; the instance and its backups are never deleted. During a `us-central1` outage the restored instance is the data copy only: the `api` and `live` services run in `us-central1`, so the app stays down until that region returns. Owner decision, 2026-11-17: "for the pilot, a us-central1 regional outage is accepted as waiting for Google's recovery, with up to about 24 hours of data at risk from the last daily backup. The 15-minute recovery target covers a bad change, damaged data and a zone outage only. Cross-region protection is decided together with high availability before the first paying customer."

1. List backups at project level, without `--instance` (that flag lists backup runs, which have no name, and fails while the instance's region is down): `gcloud sql backups list --project=dryscope --filter="instance=dryscope-<env>-pg" --format="table(name,state,location,backupInterval.startTime)"`. Take the newest row whose state is `SUCCESSFUL` and whose location is `us`, and note its name (`projects/dryscope/backups/...`). Never use one whose location is `us-central1`: backups taken before the location moved stay there and are lost with the region.
2. Restore it into a new instance in another region. The restore creates the instance from the backup's settings: `gcloud sql backups restore <backup name> --restore-instance=dryscope-<env>-pg-restore --region=us-east1 --project=dryscope`. Pass the backup name, not the numeric id (an id restores only onto an existing instance), and confirm the flags with `gcloud sql backups restore --help` first. Use `us-east1` or any region other than the failed one.
3. Check it: start the Auth Proxy against the restored copy, never the source (`cloud-sql-proxy --port=5433 dryscope:<restore region>:dryscope-<env>-pg-restore`), and confirm the restored instance opens and `migration_ledger` holds every file in `web/migrations`. The one-day bound is the backup chosen in step 1, not the age of any row.
4. Record the restored instance's name, region and the backup used in `RELEASES.md`. Leave Terraform alone until the original region is back: the data root still names the old instance. Importing the new one or rebuilding in `us-central1` is a separate owner decision.

**Quarterly restore drill.** Once a quarter, run steps 1 to 3 against `test`, restoring into a region other than `us-central1`, then delete only the drill instance by hand once the check passes. The restore copies the source's deletion protection, so turn it off on the drill instance only, then delete it (`gcloud sql instances patch dryscope-test-pg-restore --no-deletion-protection --project=dryscope`, then `gcloud sql instances delete dryscope-test-pg-restore --project=dryscope`; it is the one deletion this procedure allows, and it names that instance only). Record the date, the backup used and the result in `RELEASES.md`. Cross-region protection, which would change the one-day loss and the app staying down, is decided together with high availability before the first paying customer.
