# Backups

What to do when something goes wrong with the rebuilt app's data, in one table. Every procedure is owner-run; agents never run it against Google Cloud. The commands are in `infra/dryscope/scripts/restore-drill.sh` (S8-5): run it with `--dry-run` first to see every command it would run, with no call made. The drill rehearses all of it on test (S8-21). Last restore drill: [not recorded — run the drill on test].

| What happened                        | What to do                                                                                                                                                                                              | Where                                                       | Never                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------- |
| A bad release                        | Roll back: move traffic to the recorded earlier revision (the release record's command; S8-19's rollback workflow once it exists). The database stays as it is: it only moves forward.                  | [Releases](test-release.md)                                 | Restore the database for a bad release                                    |
| Damaged rows                         | A point-in-time copy into a new instance, to the minute before the damage; compare; copy back only the damaged rows, by company and id (the full primary key); then the records check for each company. | [Damaged rows](#damaged-rows)                               | Repoint the app at the copy: rows written since that minute would be lost |
| A zone outage (the instance is lost) | A point-in-time copy into another zone of `us-central1`, checked, then the recovery repoint (S8-6).                                                                                                     | [Zone outage](#zone-outage)                                 | Delete the original instance                                              |
| A `us-central1` region outage        | Backup salvage only: the latest automated daily backup (location `us`) restored into another region as a data copy. The app waits for Google's recovery; there is no repoint.                           | [Restore into another region](#restore-into-another-region) | Point the app at the salvage copy                                         |
| Field database damage                | Restore its latest backup into a new database and compare; copy back only the damaged documents.                                                                                                        | [Field database](#field-database)                           | Restore over the live database                                            |
| A deleted or overwritten file        | Restore the object from soft delete, or copy an earlier version back over it. A restore gives the object a new generation, so a deleted registered photo or signature stays unreadable in the app.      | [A deleted file](#a-deleted-file)                           | Change the bucket's lifecycle or soft-delete settings by hand             |

Where the copies live: the Cloud SQL instances (`dryscope-<env>-pg`) keep automated backups in the US multi-region (`us`, set in `infra/dryscope/data/sql.tf`) and seven days (test: three) of point-in-time recovery, which needs the instance's own region. The field database (`dryscope-field-<env>`) has point-in-time recovery and a daily backup kept 14 days. The evidence bucket (`dryscope-evidence-<env>`) keeps earlier versions for 28 days, then 7 days of soft delete.

Owner decision, 2026-11-17: "for the pilot, a us-central1 regional outage is accepted as waiting for Google's recovery, with up to about 24 hours of data at risk from the last daily backup. The 15-minute recovery target covers a bad change, damaged data and a zone outage only. Cross-region protection is decided together with high availability before the first paying customer."

## The drill (test only)

**Before you start the drill, tell everyone using test to stop writing there until it ends.** Anything written on test during the drill (a job, a draft, a photo, a signature) is discarded: traffic goes back to the original and the copy holding it is deleted. Your own two marker jobs are the only writes the drill needs. The script asks you to confirm this first, and tells you when test may be written again. The incident modes below run on live only; the drill is how test rehearses them.

`infra/dryscope/scripts/restore-drill.sh --env test --domain <domain> --zone <a us-central1 zone other than the database's>` runs nine timed phases against test: two different marker jobs made in one company through the app around a chosen minute; a point-in-time copy to that minute, in that other zone (the script reads the original's zone from Cloud SQL, stops if it cannot, refuses that zone and checks where the copy landed); checks on the copy (migration ledger complete, first marker there, second not, row counts per table), then the data root applied with `sql_instance_override` naming the copy and the web app's own database account logging in to it, and both markers read on the original as that account (read only, in the first marker's company: the first made by the chosen minute, the second after it); backup salvage into another region from the latest automated daily backup, with the backup's age; the field database's latest backup restored and one draft compared with its rooms and photo references, by id; one evidence object restored from soft delete and one from an earlier version; the S8-6 app-root repoint and its put-back; removal of the drill's own instances, database and objects; and a result block to paste into `docs/drills/<date>-restore.md`. It deletes only names ending in `-drill`, refuses live, and waits for you at each Terraform apply. Each printed Terraform block is one command, to paste as it is, that applies only when the plan check accepts the plan. Every copy gets a new name stamped to the second, and the script refuses a destination instance that already exists, so a run never restores over an earlier copy. After the data-root admission the script retries the web app's login every 30 seconds for up to 10 minutes, because a new IAM grant can take minutes to apply. Phase 7 waits before each app-root apply until 15 minutes have passed since the service last changed (the release's drain rule: a revision that lost traffic can hold database connections that long), and checks that each revision it moves names the right instance (`SQL_CONNECTION_NAME`) and runs the recorded revision's images, and that the candidate tag and all traffic reach it. It reads health at `candidate.test.<domain>`, the load-balanced candidate host (never a `run.app` address: the ingress lock refuses those), and at `test.<domain>`. If the drill stops after the admission or the repoint, it prints the put-back as one command to paste as it is: it stops at the first check that fails, and it clears neither override until the recorded revision serves and the serving address answers. Run it before anything else, and delete the drill's copies only afterwards. Every run that starts prints its result block, a failed one too.

Before you start: `gcloud auth login` and `gcloud auth application-default login`, as the same account; `cloud-sql-proxy` (v2), `psql`, `curl` and `jq` installed; every Terraform variable you pass to the data and app roots besides the env file exported as `TF_VAR_<name>` (at least `TF_VAR_api_image`, `TF_VAR_live_image` and `TF_VAR_alert_email`, plus `TF_VAR_workload_identity_principal_set` and any other you set), because the printed blocks pass only the env file and the override; Service Account Token Creator on `dryscope-api-<env>` for the app's login check. No test release may run during the drill: pause test releases ([Releases](test-release.md), "To pause test releases") and set the variable back afterwards. The checks add your account to each copy only, with `gcloud sql users create <you> --instance=<the copy> --type=cloud_iam_user --database-roles=<the migrator> --project=<project>` (no IAM change, so nothing admits the app early). That access is temporary: the script removes the user (`gcloud sql users delete`) as soon as the checks end and on every exit; if the removal fails, it prints the command to run by hand and the run fails. If the create itself fails or is interrupted, the script cannot tell whether the user was there before, so it removes nothing, prints the check to make and the removal, and the run fails. Messages from the commands that act as or on your account are printed with your account's name masked, and the script turns off the Cloud SDK's own log files for its commands (`CLOUDSDK_CORE_DISABLE_FILE_LOGGING=1`), so no token or account name is kept there. Meanwhile, through an Auth Proxy listening on a socket in the script's own private directory (never a proxy left from another runbook), read every table as the migrator inside one transaction that is rolled back, so the copy's data stays exactly as restored. The migration ledger rows (id and checksum, the SHA-256 of each file) must be the first migrations of `web/migrations`, with no gap, nothing unknown and no checksum that differs: a copy can predate a release, and your checkout can hold migrations not yet released (pull it if the check names an unknown one). For damaged rows the ledger must be exactly the original's own ledger as it stood at the point in time (every migration applied by then, with its checksum), read from the original as the migrator (Service Account Token Creator on it) in a read-only transaction. In the drill and a zone recovery the copy must also hold every migration of the release serving at the restore point (the commit its health reports), with the same checksums; that commit must be in your checkout (`git fetch`). Before any repoint the serving revision must be no newer than the copy's point in time, so the copy holds the migrations it needs, and the fresh revision must run the serving revision's images: Terraform keeps the service template's image, which can be a later release staged without traffic. The chosen point in time must be recoverable (`gcloud sql instances get-latest-recovery-time`): the drill waits for it, and an incident run stops and prints the latest recoverable time.

## Damaged rows

`restore-drill.sh --env live --recovery --point-in-time <UTC minute before the damage>` makes the copy `dryscope-live-pg-<stamp>`, checks it (its ledger must match the original's ledger at that minute), stops there and prints these steps. A ledger row records when its migration started, not when it committed. So if the copy lacks only the newest migration and that one started within 15 minutes before the minute, the script stops and says the migration may still have been committing then: choose a minute when no migration ran. It never repoints and never deletes.

Row-level security is forced on every table and no policy names the migrator (apart from the migration ledger), so a plain read or `UPDATE` by the migrator sees no rows: an `UPDATE` would report `UPDATE 0` and change nothing. Every read and write below therefore lifts `FORCE` inside its own transaction. The script prints these steps with the copy's and the original's names filled in.

1. Read the damaged rows from the copy by the table's full primary key, as `\d <table>` shows it: on a company's table it includes `company_id` (`company_id` and `id`; `job_customers` and `job_claims`: `company_id` and `job_id`). Never read or write by `id` alone: two companies can hold the same id. Add yourself to the copy for this read only, and remove yourself afterwards: `gcloud sql users create "$(gcloud config get-value account --project=<project>)" --instance=<the copy> --type=cloud_iam_user --database-roles=<the migrator> --project=<project>`, and go on only if that create succeeded, then through the Auth Proxy (`--auto-iam-authn`, on a socket in a fresh private directory made by `mktemp -d` in your own shell first; only the proxy goes in the background, its process id kept, and `psql` starts once the proxy's socket is there) with `psql -X -v HISTFILE=/dev/null` (so nothing you type, such as a customer's details, is kept in a history file) `BEGIN; SET LOCAL ROLE "<the migrator>"; ALTER TABLE <table> NO FORCE ROW LEVEL SECURITY; SELECT * FROM <table> WHERE (<primary key columns>) IN ((<a damaged row's key>), ...); ROLLBACK;`, then stop that proxy by its process id, remove its directory, and `gcloud sql users delete "$(gcloud config get-value account --project=<project>)" --instance=<the copy> --project=<project> --quiet`, only if your create succeeded. If it failed or you stopped it, your account may have been there before: check `gcloud sql users list --instance=<the copy> --project=<project>` and remove it only if this session added it. The script prints these commands with that guard.
2. Read the same rows on the original as the migrator itself (Auth Proxy with `--impersonate-service-account=dryscope-migrate-<env>@<project>.iam.gserviceaccount.com`; you need Service Account Token Creator on it; again a fresh private directory made first, only the proxy in the background with its process id kept, `psql -X -v HISTFILE=/dev/null` once its socket is there): `BEGIN; ALTER TABLE <table> NO FORCE ROW LEVEL SECURITY; SELECT * FROM <table> WHERE (<primary key columns>) IN ((<a damaged row's key>), ...); ROLLBACK;`. For a row of a job (`jobs`, or a table with `job_id`), read its job in that same transaction, first, with `FORCE` lifted on `jobs` before the row's table (the app locks `jobs` first too): `BEGIN; ALTER TABLE jobs NO FORCE ROW LEVEL SECURITY; SELECT status, revision FROM jobs WHERE (company_id, id) = (<company>, <job id>);` and then the row's read. Compare the two reads.
3. Never write a signed record or another guarded table's rows: the guard triggers refuse it, and a trigger is never disabled. A damaged signed record is an owner decision, recorded in a sidecar; the record itself stays as it is.
4. In that same session on the original, one transaction per table and one statement per damaged row, by its full primary key, writing only while the whole row (every column, `updated_at` and `revision` too, so a row changed and changed back still differs) is still exactly as you read it in step 2:
   ```sql
   BEGIN;
   -- a row of a job: first lock its job and advance its revision, as a normal save does (jobs before the row, as the app locks them); a submitted or signed job, or one changed since step 2, gives UPDATE 0: ROLLBACK; and stop.
   ALTER TABLE jobs NO FORCE ROW LEVEL SECURITY;
   UPDATE jobs SET revision = revision + 1, last_change_id = gen_random_uuid(), updated_at = now()
     WHERE (company_id, id) = (<company>, <job id>) AND status NOT IN ('submitted', 'signed')
       AND revision = <its revision as read in step 2>;
   -- (a damaged jobs row itself: set its columns in that same UPDATE, with no second one)
   ALTER TABLE <table> NO FORCE ROW LEVEL SECURITY;
   -- set only the damaged content columns: never copy access or state (a job's field owner, status or archive columns, a member's role) from the copy, so no withdrawn access returns
   UPDATE <table> SET (<columns>) = (<values from the copy>)
     WHERE (<primary key columns>) = (<the row's key>)
       AND (<every column>) IS NOT DISTINCT FROM (<the whole row as read in step 2>);
   -- a row missing on the original: INSERT INTO <table> (<all columns>) VALUES (<the copy's values>);
   -- psql prints UPDATE 1 or INSERT 0 1 for each: on any other count, run ROLLBACK; (someone changed the row since you compared it) and compare again.
   ALTER TABLE <table> FORCE ROW LEVEL SECURITY; ALTER TABLE jobs FORCE ROW LEVEL SECURITY;
   COMMIT;
   ```
   No other session sees the table without `FORCE`: the lock holds until the commit, which puts it back. The job's row lock also holds until the commit, so the job cannot be submitted or signed meanwhile, and its new revision makes a later save or signing that carries the old one stale. Rows written since that minute stay, and so does any edit made since you compared. Then stop the proxy by its process id and remove its directory.
5. Run the records check for each company (operator screen, "Check records"; S8-3 and S8-4).
6. Delete the copy only when you decide to.

## Zone outage

`restore-drill.sh --env live --recovery --lost-instance --point-in-time <UTC time> --zone <another us-central1 zone> --domain <domain>` (both required, with the `TF_VAR_` exports above) makes the copy in that zone (it reads the original's zone from Cloud SQL and stops if it cannot, refuses that zone, and checks where the copy landed), checks it, waits while you apply the data root with `-var sql_instance_override=<the copy>` (the admission only; the services stay on the original), checks that the web app's account logs in to the copy, checks that the serving revision is no newer than the point in time, then has you reconcile access on the copy (below), and only then prints the repoint as one command to paste as it is, with the serving revision and its images recorded. It stops at the first step that fails and moves no traffic before every check before it passed: wait until 15 minutes have passed since the service last changed (the drain rule); apply the app root with the same override; take the fresh revision and check that its `SQL_CONNECTION_NAME` names the copy (a revision made by anything else is not the repoint) and that it runs the recorded images (any other image is a later release the copy may lack migrations for: move no traffic to it; that is an owner decision); tag it `candidate` and check that the tag reaches it; check health at `https://candidate.<host>/api/health`, the load-balanced candidate host (never a `run.app` address: the ingress lock refuses those), reporting database `ok`; move all traffic to it and check that all traffic reaches it; then read health at the serving address. The run prints its result block whether it passes or stops early. **Before any traffic moves, access on the copy is reconciled.** The copy restored every role, membership, invitation, operator grant and homeowner link as it stood at the point in time. On the copy, re-apply every access change made after that minute: a member removed or disabled or a role lowered (`memberships`), an invitation revoked (`invitations`), an operator grant removed (`platform_admins`), a company suspended (`companies.status`), a job assignment ended (`job_assignments`), a field owner transferred (`jobs.field_owner_actor_id`), a job archived (`jobs`), and a homeowner link revoked or its token rotated (`signing_links` and `document_links`), through temporary access of your own as in the damaged-rows steps. This list is kept by hand: anything else that grants or withdraws access counts too. The script prints these steps and prints the repoint only after you type `reconciled` (or `none`, if no access changed after that minute); any other answer stops the run with no repoint. Revoking sessions in the sign-in tenant is no substitute: signing in again reads the role from the copy. Keep the recovered database serving; a return to the original is a separate owner decision (S8-6).

## Restore into another region

Use this when `us-central1` is down. `restore-drill.sh --env live --recovery --salvage [--salvage-region <another US region>]` (default `us-east1`; it accepts only US regions, so the records stay in the US) runs these steps (phase 4) and records the backup's age. The instance and its backups are never deleted. The restored instance is the data copy only: the services run in `us-central1`, so the app stays down until that region returns.

1. List backups at project level, without `--instance` (that flag lists backup runs, which have no name, and fails while the instance's region is down): `gcloud sql backups list --project=<project> --filter=instance=dryscope-<env>-pg --format=json`. Take the newest whose type is `AUTOMATED` (the daily backup, never a later on-demand or final one), whose state is `SUCCESSFUL` and whose location is `us`. Never use one whose location is `us-central1`: backups taken before the location moved stay there and are lost with the region.
2. Restore it into a new instance in another region: `gcloud sql backups restore <backup name> --restore-instance=dryscope-<env>-pg-salvage-<stamp> --region=us-east1 --project=<project>`. Pass the backup name, not the numeric id (an id restores only onto an existing instance).
3. Check it through the Auth Proxy on the restored copy, never the source, as your own account added to the copy with the migrator's role for the check only: `migration_ledger` holds the first migrations of `web/migrations` with their checksums, no gap and nothing unknown (the backup can predate a release), and the row counts per table.
4. Record the copy's name, region, the backup used and its age in the incident record. Leave Terraform alone until the region is back: the data root still names the original. Importing the copy or rebuilding is a separate owner decision.

## Draft sync markers after a Postgres restore

Archive, Restore, Start field work and Move write a job's field drafts through the draft sync (`web/src/lib/jobs/sync-job.ts`), which keeps the version it last wrote on one server-only document per job, `companies/<company id>/draftLifecycle/<job id>` (`{ gen, v, draftIds, skipped }`; `v` is the job's `jobs.field_revision`). Restoring Postgres to an earlier point lowers `field_revision`, so every later sync of that job is refused as older than its marker and the drafts stop following Postgres. Until the operator's generation source exists (draft life-cycle redesign, slice 4; the routes pass generation 0 now), after any Postgres restore that the app serves from, and before it serves requests:

1. In the field database the app uses, set `v` to `0` on every document of each company's `draftLifecycle` collection, and change nothing else on it: keep `gen`, `draftIds` and `skipped` as they are. Do not delete the markers: their `draftIds` are how the next sync finds drafts made after the restore point (which the restored Postgres no longer gives the job) and closes them, archived and naming nobody, their field work kept. Write each one with an update mask of `v` only.
2. List the drafts named in each marker's `skipped.superseded`. Those are held back by a newer legacy revision or a Submit fence the restored Postgres does not know, and only a generation reset writes over them; until slice 4 adds the operator's generation, check each by hand against the restored Postgres (state, field owner, fence) and correct its server keys with an update mask, never its field work.
3. Run the records check for each company. The next request on each job syncs it again from the restored Postgres.

## Field database

The drill (phase 5) restores the latest backup with `gcloud firestore databases restore --source-backup=<backup> --destination-database=dryscope-field-<env>-<stamp> --project=<project>` and compares one draft that has not changed since the backup (`companies/<company id>/drafts/<draft id>`): the draft document, its rooms and its photo references, each by id with its fields, as the app loads them. A restored database is a new database in the same location: it starts with deny-all rules and without its expiry (TTL) policies, and the app never points at it. For real damage, read the damaged documents from the restored copy (or from point-in-time recovery, within 7 days) and write back only those documents. Write only the damaged content fields (an update mask), never ownership, state, fence, job binding or other server-managed fields: those stay as the live document and the server have them, so an older backup cannot undo a transfer. Compare each one with the live document first, and make each write conditional on the live document's `updateTime` as you compared it (a `currentDocument.updateTime` precondition), so an edit a technician saved since then is never reverted. If the precondition fails, read and compare again. A document missing on the live database (a deleted room or photo reference) has no `updateTime`: after checking that it is absent and still belongs to the current draft, create it with a `currentDocument.exists=false` precondition. Then run the records check for each company.

## A deleted file

The evidence bucket keeps versioning and soft delete. An overwritten object: copy its earlier generation back over it (`gcloud storage cp gs://<bucket>/<object>#<generation> gs://<bucket>/<object> --project=<project>`). A deleted earlier version: it is in soft delete for 7 days; restore it with `gcloud storage restore gs://<bucket>/<object>#<generation> --project=<project>`. The drill (phase 6) does both with its own objects under `drill/`, then removes them. Then run the records check for the company. A restore from soft delete makes a new generation (Google's [objects.restore](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/restore)), and the app and the records check open a registered photo or signature only by the generation recorded for it. So a deleted registered file stays unreadable in the app, and the records check reports it, even after its bytes are restored. Making it readable again is an owner decision (signed records are immutable). The drill records both generations, and fails if the bytes differ or the generation is not new. An overwritten file is different: its earlier generation stays readable, so the app is unaffected.
