# CI and the pipeline gate

## Pipeline gate settings

`.no-mistakes.yaml` sets the repo-level no-mistakes gate rules: protected paths (workflow files, `CLAUDE.md`, `AGENTS.md`, `scripts/test-guard.mjs` and `.github/test-guard.json`, plus every test, guard and fixture directory, the test runner configs and `package.json` and `web/package.json`, which automatic fixes must leave for a person: a pipeline auto-fix never changes a test or its limits unattended) and two review auto-fix rounds. Entries must be exact files or literal directory prefixes ending in `/**`, the only forms the matcher honors. Protected paths guard automatic commits only, not commits a person or worker authored, and take effect once this file is on `master`. `npm run lint` runs `scripts/check-protected-tests.mjs` (via `scripts/check_required_docs.js`, tested by `tests/test_protected_tests.ts`), which fails when a `*.test.*`, `*.spec.*` or `*.tftest.hcl` file sits outside the protected paths, so a new test directory must be added to `.no-mistakes.yaml`. The reviewer agent is a global-only setting.

## Test guard

The required `test-guard` check (`.github/workflows/test-guard.yml`, which runs the base branch's `scripts/test-guard.mjs` with rules from the base branch's `.github/test-guard.json`) asks for the owner's `test-change-approved` label only when a pull request can weaken testing: it changes the guard's own files or another protected file (eval and verify scripts, Playwright configs, the `web/` Vitest and Playwright configs, `firestore.rules`, `CODEOWNERS`); deletes a test file or moves it out of the test folders (`tests/`, `web/tests/`, and the Terraform `tests/` folders and `*.tftest.hcl` files under `infra/`); leaves fewer test definitions (including Terraform `run` blocks) or assertion lines than before; adds a skip, only, todo or expected-failure marker; changes or deletes a stored answer in `tests/fixtures/`, `tests/golden/` or the AI eval folders `web/tests/ai-evals/stored/` and `web/tests/ai-evals/data/`; removes a `test` or `test:*` script from `package.json` or `web/package.json`, drops a word from one, or makes one ignore failures; or, in a workflow that runs on pull requests, removes a job, step, trigger, needed job or matrix entry, renames a job (its check name), adds or changes an `if:`, `continue-on-error` or `shell:`, or adds an error-swallowing command such as `|| true` to an existing step. In any workflow it also asks when a change could let a workflow approve itself: write access to pull requests, issues, checks or statuses, a dropped `permissions:` key, a new secret, the label's name, or a new pull request job that reuses an existing check name. New tests, new fixtures, new test scripts and added commands in one, dependency bumps, docs, Dependabot settings and ordinary workflow edits (runners, timeouts, pins, new jobs and steps, edited commands) pass without it. `tests/test_test_guard.ts` covers each case. The root `vitest.config.mjs` test list is not guarded, because new root tests are added to it often.

## CI runners

Every job in `.github/workflows/` (CI, Web app, Test guard, CodeQL and Deploy) runs on `${{ vars.CI_RUNNER || 'dryscope-linux' }}`. With the repository variable `CI_RUNNER` unset, jobs go to the self-hosted pool `dryscope-linux`: [runner-up](https://github.com/kunchenguid/runner-up) on the build server, as systemd service `runner-up` (setup in `/root/.config/runner-up/config.json`). It has three Docker places (2 cores, 6 GB each), starts one fresh container per job from the image `dryscope-ci-runner:1` (GitHub's `actions-runner` image plus `libatomic1`, `xz-utils`, build tools, Java 21 and Playwright's system libraries for Chromium and WebKit), and refuses jobs from fork pull requests. `runner-up status` shows each place and the waiting jobs.

The job container is leaner than GitHub's Ubuntu image: it has no Docker daemon (so no `services:` containers) and no Node, PostgreSQL or `gh`. Each job installs what it needs (setup-node, including in CodeQL for the JavaScript extractor, setup-java, Playwright's `install-deps` through `sudo apt-get`, a pinned `gh` in Deploy), and each install step is skipped or harmless on GitHub's image. In the web `database` job the test harness (`web/tests/db/postgres-harness.ts`) starts the throwaway PostgreSQL 16 servers itself, once per run (a plain one, and one with the roles and a migrated template that each test file copies; test files run in parallel, and a file that changes roles starts a server of its own): the `postgres:16` image where a Docker daemon answers (GitHub's image), otherwise `initdb`/`pg_ctl`. Only when there is no Docker daemon and no PostgreSQL 16 (the self-hosted container) does the job first install the Ubuntu `postgresql-16` package from apt, without creating or starting a cluster.

**GitHub-hosted runners are an owner-only fallback.** The owner has a $0 Actions hard stop, so agents never set or delete the repository variable `CI_RUNNER`, and no agent switches a job to a GitHub-hosted label such as `ubuntu-latest` (those jobs fail to start while the budget stop is on, or spend paid Actions minutes). Only the owner uses it, and only after raising the GitHub Actions budget above $0: set `CI_RUNNER` to `ubuntu-latest` (Settings > Secrets and variables > Actions > Variables, or `gh variable set CI_RUNNER --body ubuntu-latest --repo nnorman100/adr-field-estimator`). Only runs that start afterwards use it; re-run any job still waiting for `dryscope-linux`. The owner deletes it afterwards (`gh variable delete CI_RUNNER --repo nnorman100/adr-field-estimator`), which puts jobs back on `dryscope-linux`. If `CI_RUNNER` is ever found set and the owner did not set it, tell the owner.

**Stop runner-up** (on the build server): `sudo systemctl stop runner-up` stops the coordinator; jobs already running finish in their containers, and new jobs wait on GitHub for a `dryscope-linux` runner until it starts again; if CI must keep running meanwhile, the owner can use the owner-only fallback above. `sudo systemctl disable --now runner-up` keeps it off after a reboot. To end running jobs as well, `docker ps --filter label=runner-up.place` lists their containers; remove them with `docker rm -f <name>`. **Start it again:** `sudo systemctl enable --now runner-up`, then check `runner-up status`.

### Why e2e got slow (2026-11-16)

On PR #414 the two-shard `e2e` job hit its 20-minute limit three times: about 8 minutes passed before the first test, and WebKit field-app specs timed out at 60 seconds only on CI. Findings, from the Actions step timings of 39 `e2e` jobs, their logs, the Actions cache and artifact APIs and the build server's sysstat history:

- **Main cause: CPU steal on the build server.** The VM (8 vCPU) runs the three runner containers and the agents. Steal was 25-50 % from 04:00 to 05:50 UTC on 2026-11-16, exactly when PR #414's WebKit shard failed three times; the same code passed both shards at 13:37-14:20 UTC with 4-8 % steal, although our own CPU use was higher then. Daily average steal rose from 2-3 % (2026-11-08 and 11-09) to 9.3 % on 2026-11-16 (max 49.7 %). **Unresolved:** steal is the hypervisor giving our CPUs to other tenants and is outside our control. Owner options: ask the provider, move the runners to a dedicated or larger VM, or run fewer runners.
- **Playwright ran 4 workers on 2-CPU runners.** Each container is `--cpus 2` (a CFS quota), but `os.cpus()` inside it reports the host's 8 CPUs and Playwright's default is half of that, so every CI log said "Running 268 tests using 4 workers". The `e2e` step now runs `npm run test:e2e -- --workers=2`. Local A/B on the same host (WebKit shard 3/4, 134 tests, `CI=1`, pinned to 2 CPUs with `taskset` so `os.cpus()` still reports 8): 4 workers took 8.8 min wall, per-test median 6.9 s, p90 31.8 s, max 68 s, 134 passed; 2 workers took 10.4 min wall, median 4.6 s, p90 17.3 s, max 69 s, 132 passed and 2 flaky (passed on retry; host load was higher during that arm). Two workers roughly halve the slow tail of single tests, further from the 60-second timeout, for about 18 % more shard wall time, which four shards leave room for.
- **Setup time.** From job start to the first test took 4.4-4.9 min on calm runs (110-150 s of workflow steps, then 144-154 s inside `npm run test:e2e`: firebase-tools fetch about 50 s, `next build` about 80 s, server and emulator start) and 8.0-11.7 min on PR #414's attempts. With two shards the WebKit shard averaged about 18 of its 20 minutes on a normal day.
- **Caches were not the cause.** The npm cache hit on every `e2e` job checked. Actions cache storage is at its 10 GB limit (least recently used entries are evicted), but the hot web npm key is used every run; artifact storage is only 26 MB.
- **Possible follow-ups (not done):** firebase-tools is fetched with `npx --yes` on every run (about 50 s; it could be a pinned dev dependency covered by `npm ci` and its cache). There is no Playwright browser cache, so each job downloads Chromium and WebKit (about 25 s); a cache entry would be about 300-400 MB per branch, into a cache already at its limit.

## Legacy CI retired

The old Python app (`backend/`, `public/`, `tests/` and their tooling) is frozen reference code for the TypeScript rebuild in `web/` and `infra/dryscope/`. Nobody uses it and it is deleted in S8, so as of 2026-11-10 none of its tests run in CI. **Do not change legacy files except through S8**; the old app keeps serving until then, and no check now guards those edits. Run a legacy suite by hand with the commands in `CLAUDE.md` when a legacy change needs one.

The legacy test fixtures (`tests/fakes.py`, `tests/browser_server.py`, `tests/browser/*`, `tests/test_*.py`) carry a real company's identity; S8 deletes them, it does not migrate them.

The jobs `python` (pytest and ruff), `browser` (Playwright) and `firestore-emulator` were removed from `.github/workflows/ci.yml` rather than left reporting a fake success. The owner took those three names off the master ruleset's required checks on 2026-11-10 (it now requires `node`, `audit`, `test-guard` and the Web app checks); a required check with no job would block every pull request. The pricing-oracle Python code (`scripts/pricing_oracle*.py`, `tests/test_pricing_oracle.py`) was deleted too: the owner dropped exact price matching with the old app (each owner sets their own prices). The stored answers in `tests/fixtures/pricing-oracle/` and the TypeScript tests that read them were removed in S4-2 of the pricing plan (`docs/plans/pricing.md`), replaced by the worked-example, clause and property tests in `web/tests/unit/estimate-*.test.ts`. `tests/golden/` stays: only the old Python `tests/test_claims_documents.py` reads it, and it goes in S8.

## Agent stop checks

`.claude/settings.json` runs `scripts/stop-checks.mjs` as a Claude Code Stop hook: before an agent may finish, it runs the fast checks for the files changed since the branch left `master` (plus uncommitted and new files). Root files get Prettier, root ESLint and the root vitest tests related to them; `web/` code gets `npm run typecheck`, ESLint on the changed files and the unit tests related to them (`vitest run --changed`). The slow suites (`test:db`, `test:emu`, `test:e2e`, the image build) stay in CI. A failure blocks the stop and hands the output back to the agent; after three failed attempts in a row the agent may stop, with a warning to the person. A `web/` change takes about a minute (mostly the type check); docs-only changes run nothing. It needs `npm ci` at the root and in `web/` and skips with a notice otherwise; `DRYSCOPE_SKIP_STOP_CHECKS=1` turns it off. `tests/test_stop_checks.ts` covers which checks run.
