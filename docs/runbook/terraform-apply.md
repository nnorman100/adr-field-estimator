# Apply the central Terraform

`infra/dryscope/` holds the Terraform for the rebuilt app's central test and live resources in dedicated project `dryscope` (project number `570228742694`, no Google Cloud organization required), region `us-central1` (`data` and `app` roots; see its [README](../../infra/dryscope/README.md)). It has not been applied. The owner reviews every plan; an agent never runs plan or apply against the project. Everything is new in `dryscope` (`us-central1`); nothing touches the legacy `alert-disaster-field-2026` project (`us-west2` service, `(default)` Firestore database, `alert-disaster-field-2026-evidence` bucket, or `adr-runtime` and `adr-builder` accounts), which stays running unchanged until the new app is live.

1. Run the offline checks: `TERRAFORM=<binary> infra/dryscope/scripts/check.sh` (format, validate, the mocked `terraform test` suites, the closed-set plan check on each mocked plan, and the destroy-guard check, for both roots and both environments). Use Terraform 1.9 or later and below 2.0 (the guard check was proven on 1.12.2 and 1.17.1); it reads `prevent_destroy` from the `.tf` files, so the result does not change with the Terraform version.

   - Create the remote state bucket `gs://dryscope-tfstate` (named in `infra/dryscope/*/envs/backend-*.hcl`) in `us-central1`, private, versioned, with uniform bucket-level access:
     ```bash
     gcloud storage buckets create gs://dryscope-tfstate --project=dryscope --location=us-central1 --uniform-bucket-level-access --public-access-prevention
     ```

     Give only the applying owner identity access.
   - Apply `data` then `app` for **test** first (steps 3–7 below) before touching **live** (step 8); the plan must delete nothing, except the four named IAM grant changes when [re-applying the test data root](#apply-the-central-terraform) below.
3. Start with **test**. (Cloud SQL tiers differ by environment: `infra/dryscope/README.md`.) Each root and environment has its own state, so always initialise with `-reconfigure` and the matching backend file (never migrate state between them): `terraform init -reconfigure -backend-config=envs/backend-<env>.hcl` in `infra/dryscope/data` or `infra/dryscope/app`. In `infra/dryscope/data`: `terraform init -reconfigure -backend-config=envs/backend-test.hcl`, then `terraform plan -var-file=envs/test.tfvars -out=test.tfplan`. Check the saved plan with the closed-set check: `terraform show -json test.tfplan > test.json && node ../scripts/check-plan.js data test test.json` from the root's directory (use `app` for the app root and `live` for live). It exits non-zero on any delete or replacement (other than the four named grant changes in [re-applying the test data root](#apply-the-central-terraform) below), any update (other than adding the new `ALLOWED_ORIGINS` setting to Cloud Run services that are already applied: see [sign-in user role](#sign-in-user-role); or adding the AI settings to them and moving the relay's concurrency to 20 in test: see [AI screening](#ai-screening-and-the-evaluation-account)), any resource or IAM grant outside the table (role, member and exact condition), any resource in another project or with another environment's name, or any weakened protection, and the output goes into the apply record. Then read the plan: on a first apply every line must be a create, and on a re-apply of the test data root the four named IAM grant changes, plus creates of anything added since the first apply (the two sign-in APIs and the `dryscopeIdentityTest` role), are the only lines that are not no-ops. Any other update, replace or destroy line, or any resource whose name is not in the list below (with `<env>` = `test` or `live`), stops the apply:
   - Data root: service accounts `dryscope-api-<env>`, `dryscope-live-<env>`, `dryscope-migrate-<env>`, `dryscope-deploy-<env>`, and in test only for now `dryscope-scheduler-test` (no role; see [scheduled job calls](#scheduled-job-calls)) and `dryscope-eval-test` (see [AI screening](#ai-screening-and-the-evaluation-account)); the Model Armor text template `dryscope-text-<env>` (`us-central1`) and, in test only, the project's Model Armor floor setting; Cloud SQL instance `dryscope-<env>-pg`, its database `dryscope` and its IAM users for the `api`, `live` and `migrate` accounts; Firestore database `dryscope-field-<env>`; bucket `dryscope-evidence-<env>`; Artifact Registry repository `dryscope-<env>`; secrets `dryscope-<env>-*`; API enablement (`google_project_service`) for the twelve listed `*.googleapis.com` services (including `identitytoolkit` and `firebaserules` for sign-in and the field database rules, `cloudscheduler` for the scheduled job calls, and `modelarmor`, already on by hand), which changes nothing when an API is already on; the custom roles `dryscopeGemini<Env>`, `dryscopeIdentity<Env>` (see [sign-in user role](#sign-in-user-role)) and, in test only for now, `dryscopeRulesReleaseTest` (see [field rules release role](#field-rules-release-role)); and `*_iam_member` grants whose member is one of the `dryscope-*-<env>` accounts (or the workload identity principal set from step 9).
   - App root: Cloud Run services `dryscope-api-<env>` and `dryscope-live-<env>` (both get `ALLOWED_ORIGINS`, the environment's own web app address from `allowed_origins` in `envs/<env>.tfvars`; the variable refuses anything but `https://host` origins and the other environment's services); the Cloud Run migration job `dryscope-migrate-<env>` (the web image, `node migrate.mjs`, running as `dryscope-migrate-<env>` over the built-in Cloud SQL connection to `dryscope-<env>-pg`, no secrets; see [Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test)); in test only for now, the Cloud Scheduler job `dryscope-access-projection-test` (see [scheduled job calls](#scheduled-job-calls)); the custom roles `dryscopeDeploy<Env>` (`dryscopeDeployTest` or `dryscopeDeployLive`) and `dryscopeMigrateJob<Env>`; their `*_iam_member` grants; the `DryScope <env> alerts` email channel and `DryScope <env>: ...` alert policies and uptime check; and the `DryScope <env> monthly` budget when a billing account is given.
   **Re-applying a root that is already applied (no `-target` needed).** `check-plan.js` treats a plan with at least one no-op resource as a re-apply: existing resources may be no-op, the provider's full resource paths for IAM member names (buckets, secrets, repositories, Cloud Run services and jobs) are accepted when they resolve to the expected name in `dryscope` / `us-central1`, and only Cloud Run migration jobs, Cloud Scheduler jobs, alert policies, notification channels and custom roles may change in place, with the planned state still held to the table. IAM grants, data stores, secrets and accounts must be no-op; the Cloud Run services and Cloud SQL instance keep their named exceptions. Every delete or replacement is still refused, as is any update in a plan with no existing resource (a first apply). The Cloud Run services ignore the image and traffic a release sets, but not the revision name (`template[0].revision`): Cloud Run cannot change a revision that exists, so after a release a plan clears that name and the apply makes a fresh revision with the release's image and no traffic (settings it adds reach users with the next release). `check-plan.js` accepts that clear (a service no release has named, such as the relay before its first release, already has an empty name, so there is nothing to clear) and refuses a service update that keeps or sets a revision name.
4. `terraform apply test.tfplan`. Cloud SQL takes several minutes. Then add a value to each secret the data root created (`gcloud secrets versions add dryscope-test-<name> --project=dryscope --data-file=-`), never through Terraform or chat.
5. Owner-run database bootstrap, approved by the owner at apply time. A new IAM database user has no database privileges, so before the first migration the owner connects as a privileged Cloud SQL user (the built-in `postgres` user or another `cloudsqlsuperuser` member, set up out of band through the Cloud SQL Auth Proxy, never through Terraform, its password never in git, chat or state) and grants the migrator only what migrations need: `ALTER ROLE "dryscope-migrate-test@dryscope.iam" CREATEROLE;` (so it can create the non-owner runtime role, which it cannot give `BYPASSRLS`) and `GRANT CREATE ON DATABASE dryscope TO "dryscope-migrate-test@dryscope.iam";` (so it can create the schema it then owns), plus `GRANT USAGE, CREATE ON SCHEMA public TO "dryscope-migrate-test@dryscope.iam";` because Postgres 15 and later no longer let every user create tables in `public`, where `0001_foundation` puts its tables. The exact commands are in [Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test), part B. Never grant the migrator `cloudsqlsuperuser` or `BYPASSRLS`. This step grants only; the schema migrator then runs as `dryscope-migrate-test` from the Cloud Run job of the same name, which the app root creates (step 6) and the first release executes, never from the build server (a numbered migration creates the non-owner runtime role with row-level security forced and grants it table rights; Terraform only creates the IAM database users). The files that exist today are the `web/migrations` ledger in [Postgres migrations for the rebuilt app](migrations.md#postgres-migrations-for-the-rebuilt-app). `0001_foundation` creates the ledger and an empty companies table; `0002_identity` adds the sign-in and company-separation tables; `0003_runtime_role` creates the runtime role `dryscope_runtime`, forces row-level security on every table and grants the role to `dryscope-api-<env>@dryscope.iam`; `0004_sign_in_lookup` adds the tenant-to-company lookup the runtime may call before a company is known (`docs/DATA.md`). Terraform creates that IAM database user before the first migration; if it was created after `0003` ran, the API user has no rights until the owner runs `GRANT dryscope_runtime TO "dryscope-api-<env>@dryscope.iam" WITH INHERIT TRUE, SET FALSE;` as the migrator. Check it after the first migration: `SELECT u.rolname AS member, m.inherit_option, m.set_option, m.admin_option FROM pg_auth_members m JOIN pg_roles r ON r.oid = m.roleid JOIN pg_roles u ON u.oid = m.member WHERE r.rolname = 'dryscope_runtime' ORDER BY u.rolname;` must show exactly two rows: `dryscope-api-test@dryscope.iam` with `t`, `f`, `f`, and `dryscope-migrate-test@dryscope.iam` with `f`, `f`, `t`. The second row is PostgreSQL 16's automatic grant to the creator of a role (the migrator created `dryscope_runtime`), so it is expected; any third row, or a different `inherit`, `set` or `admin` value on the API row, is wrong. The owner ran this on 2026-11-11 and saw those two rows; no role is a superuser or bypasses row-level security.

Build and push the first images into the `dryscope-test` Artifact Registry repository (`us-central1-docker.pkg.dev/dryscope/dryscope-test/...`) by digest, then in `infra/dryscope/app` run `terraform init -reconfigure -backend-config=envs/backend-test.hcl` and plan and apply with `-var-file=envs/test.tfvars -var api_image=<digest ref> -var live_image=<digest ref>` and `TF_VAR_alert_email` set in the shell (the address is never in git). In each root, first run `terraform init -reconfigure -backend-config=envs/backend-live.hcl` so live never writes to test state. The `project_iam_member` lines (conditioned Cloud SQL and Firestore access, and the predict-only `dryscopeGemini<Env>` custom role, which holds `aiplatform.endpoints.predict` and nothing else), the unconditional `allUsers` `roles/run.invoker` binding on both Cloud Run services (the app verifies Firebase sign-in itself) and the `dryscopeDeploy<Env>` custom role bound to the deploy account on both services are IAM changes for the owner to review: confirm each in the plan, and that the custom role's permissions are only Cloud Run reads plus `run.services.update`, with no `run.services.delete` or `run.revisions.delete`. 9. For keyless deploys (test commands: [Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test), part A), create a separate GitHub workload identity pool per environment in project `dryscope` (`570228742694`), named `dryscope-test` and `dryscope-live`, never two providers in one pool (the same repository mapping in a shared pool gives both environments the same principal set, so a token the test provider accepts could impersonate the live deploy account). The live pool's provider needs an attribute condition restricting it to the repository owner, the protected branch and the live GitHub environment (`assertion.repository_owner`, `assertion.ref` and `assertion.environment`); the test provider may be looser, because its pool cannot reach live. Then pass `-var workload_identity_principal_set=principalSet://iam.googleapis.com/projects/570228742694/locations/global/workloadIdentityPools/dryscope-<env>/attribute.repository_id/<numeric id>` to the data root, so live is bound only to a principal set from the `dryscope-live` pool. The data root binds that principal set to two accounts: the deploy account (images, Cloud Run and the migration job) and the migrator. Releases sign in as the deploy account only; the migration job runs as the migrator inside Google, so the deploy account never holds a database role. The migrator's binding is no longer used by the release; removing it is a removal for the owner to decide, and leaving `-var workload_identity_principal_set` off would plan to remove both bindings, which the plan check refuses. The variable and the plan check refuse any other pool (a shared one or the other environment's), the pool-wide wildcard and anything not scoped to one repository. For the budget alert, pass `-var billing_account_id=...` to the app root.

**Releases and roll back.** Terraform creates the two Cloud Run services and the migration job with the first image and then ignores their image (and the services' traffic), so a release or rollback never needs an apply (test releases run from `.github/workflows/web-release.yml`; see [Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test)): the deploy account (which cannot run these roots) deploys a new digest with `gcloud run deploy`, and rolls back with `gcloud run services update-traffic <service> --to-revisions=<earlier revision>=100 --region=us-central1`. Passing a different digest to Terraform later changes nothing. The deploy account must never be able to edit its own custom role (`iam.roles.update`), or it could add the delete permission back.

**No resource is deleted by an apply that passes the plan check; the only IAM grants it removes or replaces are the four named in [re-applying the test data root](#apply-the-central-terraform) below.** The old us-west2 service keeps serving until the cutover plan says otherwise. Removing a protected resource is a separate owner operation: lift its protection by hand, with a backup and a recorded reason.

**Re-applying the test data root after the Live relay grants were removed.** The first data table gave the Live relay account (`dryscope-live-<env>`) Cloud SQL connect and login and `roles/datastore.user`, and matched the Firestore grant on the database name only. The current table gives Cloud SQL connect and login to the `api` and `migrate` accounts only, gives `roles/datastore.user` to the `api` account only, and conditions it on the environment's database or any name under it (`resource.name == 'projects/dryscope/databases/dryscope-field-<env>' || resource.name.startsWith('projects/dryscope/databases/dryscope-field-<env>/')`, so its documents are covered and the other environment's database, or a sibling such as a restored copy, is not). An environment applied with the first table (test) therefore plans exactly four IAM changes and, apart from creates of resources added since (the two sign-in APIs and the `dryscopeIdentityTest` role), nothing else: deletes of `google_project_iam_member.sql_client["live"]`, `sql_login["live"]` and `firestore_user["live"]`, and a replacement of `firestore_user["api"]` (the provider cannot change a condition in place). Run the same steps 3 and 4. The plan check accepts those four by name, and only as exactly that change: a delete must remove the Live relay grant with that role and member, and the replacement must keep role and member and move from the earlier exact-name condition to the current one. Any other delete, replacement or update still fails it, and every other plan line must be a no-op. The Live relay's Cloud SQL IAM user stays (removing it would be a delete); without the two roles it cannot connect or log in. Expect the web app's Firestore access to drop for a moment between the delete and the create; nothing in test uses it yet.

<a id="sign-in-user-role"></a>**Sign-in user role (`dryscopeIdentity<Env>`).** The data root creates one custom role per environment holding exactly `firebaseauth.users.get`, `firebaseauth.users.create`, `firebaseauth.users.update` and `firebaseauth.users.sendEmail`: no `users.delete`, no `firebaseauth.configs.*` (project and tenant sign-in settings are shared by test and live and stay owner-run) and no `identitytoolkit.tenants.*`. Terraform binds it nowhere. A binding on the project would reach every tenant, including live's, so the owner binds it on each of the environment's own sign-in tenants only, with `tenants/TENANT_ID:setIamPolicy` naming `projects/dryscope/roles/dryscopeIdentity<Env>` (the data root's `identity_users_role` output) and `serviceAccount:dryscope-api-<env>@dryscope.iam.gserviceaccount.com`. That a tenant-only binding is honoured by the user-management calls is not yet proven (stage S3's real-service check tests it). The plan check refuses a wider role and any project-level grant of it or of a `roles/firebaseauth.*`, `roles/identitytoolkit.*` or `roles/identityplatform.*` role. **App root already applied.** If the Cloud Run services existed before `ALLOWED_ORIGINS` was added, the app plan updates both services in place to add it. The plan check accepts that update only when, apart from that setting (which must be the environment's own web app address), the planned service equals the applied one; output-only fields the provider recomputes are skipped, and any other change, delete or replacement still fails. Apply the data root instead of creating the role by hand: a role created by hand under the same id makes the apply fail until it is imported or deleted.

<a id="field-rules-release-role"></a>**Field rules release role (`dryscopeRulesReleaseTest`).** In test only for now, the data root creates the custom role `dryscopeRulesReleaseTest` holding exactly `firebaserules.rulesets.create`, `firebaserules.rulesets.get`, `firebaserules.releases.get`, `firebaserules.releases.create` and `firebaserules.releases.update` (no delete, list, test or `getExecutable`), and grants it to `dryscope-deploy-test` on the project with no condition. The test release workflow uses it to release `web/firestore.rules` to `cloud.firestore/dryscope-field-test` ([Release the rebuilt app to test](test-release.md#release-the-rebuilt-app-to-test), the deploy job), which replaces the owner's hand release for test. Firebase Rules cannot be scoped below the project: it is not one of the services IAM Conditions recognise resource names for, and its releases carry no IAM policy. So the grant also lets the test deploy account point the live release at a ruleset; only the script and the workflow keep it to test (README, "Accepted risks"). Confirm in the plan that the role holds those five permissions and nothing else, that its one grant names the deploy account, and that the plan check passes. Live rules releases stay owner-run ([owner cloud steps](owner-cloud-steps.md), item 14): the live data root creates no rules release role or grant, and the live wiring comes in a later step.

<a id="scheduled-job-calls"></a>**Scheduled job calls (`dryscope-access-projection-test`).** In test only for now, the app root creates a Cloud Scheduler job in `us-central1` that POSTs every five minutes (UTC) to `https://dryscope-api-test-570228742694.us-central1.run.app/api/internal/access-projection` with an ID token for `dryscope-scheduler-test@dryscope.iam.gserviceaccount.com`, audience `dryscope-test-access-projection`: exactly the caller and audience the route accepts (`web/src/lib/auth/service-caller.ts`). Each call runs one access-records outbox pass (S3-12); a failed call is not retried, the next one runs five minutes later. The scheduler account holds no role, because the web app takes unauthenticated calls and checks the token itself. Cloud Scheduler mints the token through its service agent's automatic `roles/cloudscheduler.serviceAgent` (granted when the API is enabled; only a project that enabled the API before 19 March 2019, or that removed the grant, needs it added by hand), and the person applying the app root needs `iam.serviceAccounts.actAs` on the scheduler account (a project owner has it). Live has no scheduler account or job yet (the live data and app roots create neither, and the plan check refuses them in a live plan); the live wiring comes in a later step. Check after the test apply: `gcloud scheduler jobs run dryscope-access-projection-test --location=us-central1 --project=dryscope`, then the web app's request log shows `POST /api/internal/access-projection` answered 200 (401 or 403 means the token's account or audience does not match). To stop the calls, `gcloud scheduler jobs pause dryscope-access-projection-test --location=us-central1 --project=dryscope`; the next app-root plan then shows the job updated back to running, which the plan check refuses, so resume it before applying.

**Evidence uploads never overwrite.** The web app's `roles/storage.objectCreator` carries no delete, and Google's role table says it does not overwrite, but the evidence bucket keeps object versions and the "no overwrite" rule must not rest on how the role is evaluated against a versioned name. Every evidence upload must create with a does-not-exist precondition, `ifGenerationMatch=0` (the JSON API parameter; `x-goog-if-generation-match: 0` in the XML API, `if_generation_match=0` or the equivalent in a client library), and treat the `412 Precondition Failed` that an existing name returns as a refused write, never retrying it without the precondition. A test for the upload code must show that a second upload to the same name is refused.

## Stage S8 web app maximum instances (S8-2)

Stage S8, step S8-2 (`docs/plans/S8/S8-2.md`). One re-plan and apply of the **app root** per environment, test first. The only change is the web app's maximum instances (`api_scaling.max_instances`): test 3 to 1, live 10 to 7. It keeps the database connection budget within each database's limit: two revisions at the maximum instances, 6 connections each (main pool 3, access renewal 2, health probe 1), plus the migrator and a reserve of 10, is 23 of 25 on test and 95 of 100 on live (`web/src/db/client.ts`, beside `MAIN_POOL_CONNECTIONS`).

**Apply this before the S8-2 code is released.** The code alone does not open more connections: an instance opens 6 before and after (1 + 4 + 1 today, 3 + 2 + 1 with S8-2).

**Then move the serving revision onto the new limits, checked first.** Cloud Run sets the maximum per revision, and this root leaves traffic to the release, so the apply makes a fresh revision (the image already serving, the new maximum) that takes no traffic, while the revision serving traffic keeps the old maximum. As for any release, it reaches users only after it passes the smoke check at a tagged address (S8.md section 3). For each environment, after its apply, test first, with `S=dryscope-api-<env>` and `--region=us-central1 --project=dryscope` on every `gcloud` command:

1. Record what serves now: `gcloud run services describe $S --format=json | jq -r '[.status.traffic[] | select((.percent // 0) > 0) | "\(.revisionName)=\(.percent)"] | join(",")'`. Keep that value as `PREVIOUS`. Read the revision the apply made, `NEW`, from `.status.latestReadyRevisionName` of the same output; it must differ from the serving one.
2. Stage it at a tagged address with no traffic, under the release's own tag (the next release moves it): `gcloud run services update-traffic $S --update-tags=candidate=$NEW`. Its address is the `.url` of the `candidate` entry in `.status.traffic`.
3. Smoke-check that tagged address. Read the commit and version the service URL's `/api/health` reports now (the image is the same). On test: `node web/scripts/smoke-release.ts --url <tagged address> --commit <commit> --version <version> --env test`. On live the smoke script must not run (it sends a signed-out POST): `curl -s <tagged address>/api/health` must print `"status":"ok"`, `"env":"live"`, that commit and version, and `"database":"ok"`. If the check fails, stop: no traffic moved.
4. Move all traffic to exactly that checked revision: `gcloud run services update-traffic $S --to-revisions=$NEW=100`.
5. Check the service URL the same way. If it fails, put the recorded traffic back: `gcloud run services update-traffic $S --to-revisions=$PREVIOUS`.

The next release then waits 15 minutes after the last of these changes before it stages (the drain wait in [the test release](test-release.md), part 3), so the old revision has no idle instance left (Cloud Run keeps one for up to 15 minutes) and every revision that can run during a release is under the new maximum.

Before applying, run `check.sh` and `check-plan.js` on the saved plan as for any apply: the only differences are `max_instance_count` on `dryscope-api-<env>` and the release's revision name being cleared (the `lifecycle` note in `infra/dryscope/app/cloud_run.tf`), with no deletes. The limits of 25 and 100 are Cloud SQL's defaults for `db-f1-micro` and `db-custom-1-3840`.
