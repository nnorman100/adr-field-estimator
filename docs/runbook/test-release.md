# Release the rebuilt app to test

`.github/workflows/web-release.yml` releases `web/` to the **test** environment only, after the Web app workflow passes on `master` (or by hand: `gh workflow run web-release.yml --ref master`). Every job runs on the GitHub-hosted `ubuntu-latest` runner ([CI runners](ci.md#ci-runners)) and needs only Google APIs over HTTPS from it: no job connects to Cloud SQL from the runner (migrations run in a Cloud Run job inside Google). Images are assembled without a Docker daemon, so the build does not depend on the runner image: `web/scripts/build-image.sh` builds the Next.js standalone output with npm and appends it as one root-owned `/app` layer onto the base image pinned in `web/Dockerfile`, with [crane](https://github.com/google/go-containerregistry) (`web/scripts/install-crane.sh`, pinned by version and checksum). One release runs at a time:

1. **build** (as `dryscope-deploy-test`): numbers the release `YYYY.MM.DD-N` (UTC date; N is one more than the highest tag for that date, counting the old app's tags from `deploy.yml`, which used the same scheme; `web/scripts/release-version.ts`), then pushes `us-central1-docker.pkg.dev/dryscope/dryscope-test/web:<commit>` with the commit and that version (`APP_VERSION`) baked in (the image also carries the migrator, `/app/migrate.mjs`, and the ledger, `/app/migrations`), then uses it by digest. A rerun of the same commit reuses the pushed image (tags are immutable) and the version baked into it, and stops before any migration or traffic change if another commit has since been tagged with that version. Until the owner's first app-root apply (part D), it also pushes the Live relay placeholder (`.../live-placeholder:<commit>`, which answers 503 until stage S7) and stops there; the run summary prints both digests.
2. **migrate** (as `dryscope-deploy-test`): sets the release image, by digest, on the Cloud Run job `dryscope-migrate-test` with `gcloud run jobs update --image=<digest>` (only the image changes), checks that the job still runs as `dryscope-migrate-test` with that image, then runs it with `gcloud run jobs execute --wait`. The job runs `node migrate.mjs` as `dryscope-migrate-test` over Cloud Run's built-in Cloud SQL connection with IAM login (no password, no secret), one task, no retries, ten-minute limit. A failed execution fails the release; nothing has moved yet. Migrations `0018_field_revision`, `0019_price_approvals` and `0020_drying_outcomes` wait at most 5 seconds for each table lock, so one blocked by a long-running request fails with nothing applied instead of stalling job requests; run the release again. Its log is the execution's log in the Cloud Run console (the deploy account cannot read logs).
3. **deploy** (as `dryscope-deploy-test`): first releases the field database's browser rules, `web/firestore.rules`, to `dryscope-field-test` with `web/scripts/release-rules.ts` through the Firebase Rules API (role `dryscopeRulesReleaseTest`, [field rules release role](terraform-apply.md#field-rules-release-role)): it reads release `cloud.firestore/dryscope-field-test` and its ruleset, and when they already hold the committed file it creates nothing and prints `unchanged`; otherwise it creates a ruleset from the file (a rules error refuses it and changes nothing), points the release at it (creating the release the first time), reads both back and fails unless they hold exactly the file. A failure there stops the release before any revision or traffic changes. The Web app workflow ran the emulator rules tests on the same commit before this run started. Rules take a few minutes to reach every client. It then waits until 15 minutes after the service last changed (its `updateTime` in the Cloud Run Admin API v2, read with `web/scripts/release-drain.ts`; the summary prints the wait, at most 15 minutes), so a revision that lost its traffic has no idle instance holding database connections when the next one is staged ([S8-2](../plans/S8/S8-2.md): the connection budget counts two revisions). Any change to the service counts, including a rollback or a traffic move by hand. It reads the time again after each wait, so a change during the wait starts the 15 minutes again; after two waits it stops the release with nothing staged. It then records the revisions serving now, runs `gcloud run deploy dryscope-api-test --image=<digest> --no-traffic --tag=candidate` (only the image changes, so Terraform sees no drift), checks the tagged URL with `web/scripts/smoke-release.ts` (`/api/health` answers `ok`, `test`, this commit, this release's version and database `ok`, which it reports only after the revision's own Cloud SQL IAM login succeeded, and answers 503 otherwise; signed-out `GET /api/jobs/current` (not a job id, so no route takes it) and `POST /api/companies` answer 401 or 403), moves 100% of traffic to the new revision, and checks the service URL again. If the move or that last check fails, or the job is cancelled during the move, it puts the recorded traffic back.
4. **record** (the only job that can write to the repository, `contents: write`; docs/plans/TC.md, TC-8): after a release that moved traffic and passed both smoke checks, `web/scripts/release-manifest.ts` writes `manifest.json` (version, commit, image digest, the new revision and the traffic it replaced, the migration level, the newest `infra-test-<root>-*` tag per Terraform root, the AI prompt and model versions, the switch defaults, the minimum phone version once S6-6 adds it, and the rollback command), the job tags the released commit with the version (a tag is never moved: one on another commit stops the record) and publishes a pre-release GitHub Release `<version> (test)` with `manifest.json` attached and the rollback command in its notes. A rerun first checks this version's Release: a complete one (published, a pre-release, with `manifest.json` and that manifest's rollback note in its notes) is kept as it is, whatever the release history; an incomplete one, such as a draft left by an interrupted run, is finished with the rerun's manifest and notes. When a run finds this release's image already serving (a rerun after the record failed past the traffic move, or the first run after part D, whose apply already serves the image), the traffic the deploy job remembered is the release's own, so the rollback target is the revision of the previous published DryScope test release (a non-draft pre-release tagged `YYYY.MM.DD-N`; the old app's releases are not pre-releases and do not count), from its `manifest.json`, never the current traffic. If that release has no usable `manifest.json`, the record stops with nothing tagged or published. If there is no earlier DryScope test release at all, the release is recorded as the first one: its manifest has `firstRelease: true` and `rollback: null`, and its notes say "First recorded release: there is no earlier DryScope release to return to." After any failure past the gate (in build, migrate, deploy or the record itself, including the record job being cancelled), it instead signs in as `dryscope-deploy-test` and writes one line to Cloud Logging, `gcloud logging write dryscope-release '{"env":"test","version":"<version or null>","result":"failed","run":"<run URL>"}' --payload-type=json --severity=ERROR`, for the failed-release alert (TC-11). That write needs `roles/logging.logWriter` for the deploy account, which the data root grants in TC-9; until it is applied, the line fails with a 403 and the run's own failure (GitHub Mobile, C11 A) is the only notice.

Until all three repository variables in part C are set, every run ends with a "Test release skipped" notice and changes nothing. Before part D, a run only pushes the first images. `DRYSCOPE_TEST_MIGRATE_SA` names the account the migration job must run as; the workflow no longer signs in as it. A variable that is set but names anything other than the test pool or the test accounts fails the run. **To pause test releases**, delete `DRYSCOPE_TEST_WIF_PROVIDER` (`gh variable delete DRYSCOPE_TEST_WIF_PROVIDER`). **To roll back by hand:** run the `rollback.command` from the release's `manifest.json` (the first recorded release has none: there is nothing earlier to return to) (also in its GitHub Release notes, `gh release view <version>`), which puts back exactly the traffic that release replaced: `gcloud run services update-traffic dryscope-api-test --to-revisions=<previous revision>=100 --region=us-central1 --project=dryscope`. The database never rolls back: migrations stay applied, and the add-first rule keeps the previous code working against them. **Rollback floor, the draft sync generation:** once the draft sync's generation has been raised the first time (`npm run platform:raise-draft-sync-generation`, [backups runbook](backups.md)), never roll back to a release older than the one that brought draft life-cycle slice 4b, the first that reads the generation: an older version syncs at generation 0, is refused as older than every marker written since, and answers as if its field step were done. **Exception, the rollback floor:** once `0018_field_revision` is applied, never roll back to a release older than `2026.11.19-7`, including with the rollback command recorded in `2026.11.19-7`'s own notes. Code before #482 has a submission worker that locks an expired submission before its job, which deadlocks against Submit once 0018's triggers exist. Judge whether 0018 is applied from the database, not from the serving release's manifest: a release can apply its migrations and then fail to deploy before it publishes a manifest. Before you use any rollback command, including after a failed deployment, confirm it from the `dryscope-migrate-test` job's executions: if the latest execution succeeded with a release that includes 0018, it is applied. Whenever they cannot confirm it either way (the latest execution failed, was cancelled or is missing, since a migration can commit and the job still report failure), read the `migration_ledger` table: `SELECT id FROM migration_ledger WHERE id = '0018_field_revision';` (over part B's connection). A row there means 0018 is applied. Then check `/api/health` reports the earlier version. **Exception, the rollback floor for priced extras (S5b-8):** once any company has `priced_extras` on, never roll back to a release that does not include pull request #520 (commit `764b06bc`, "price custom multipliers and unit and flat additions on approved job proposals"), the first that prices all three additional kinds (#507 brought proposals and approvals, but its release prices only named and hourly approvals): such an older release so it would leave an approved custom multiplier, unit addition or flat addition out of a price, and would not see an unsettled unit or flat row that blocks signing. Judge it from the database, not only from the switch: a company that approved such a row and then turned the switch off still holds the row, and an older release would price it away once the switch is on again. Both tables have forced row-level security, so a connection with no company context sees no rows and would answer "clear" falsely: run both queries as the migrator inside the rolled-back transaction the [backups runbook](backups.md) uses for cross-company reads (Auth Proxy with `--impersonate-service-account=dryscope-migrate-<env>@<project>.iam.gserviceaccount.com`, `psql -X -v HISTFILE=/dev/null`): `BEGIN; ALTER TABLE company_feature_flags NO FORCE ROW LEVEL SECURITY; ALTER TABLE job_price_approvals NO FORCE ROW LEVEL SECURITY; SELECT 1 FROM company_feature_flags WHERE flag = 'priced_extras' AND enabled LIMIT 1; SELECT 1 FROM job_price_approvals WHERE kind IN ('line_multiplier', 'unit', 'flat') LIMIT 1; ROLLBACK;` (any company, approved or not, ended or not). The floor applies when either query returns a row; an `ALTER` that fails means the read is not verified, so do not treat the answer as clear. **While two revisions serve at once** (a release's traffic move, or a rollback): a Start field work answered by the revision before the draft sync (before draft life-cycle redesign slice 3) can name its caller on the job's current draft again after the new revision's sync named a newer owner, when both are at the same coordination revision. It lasts only while the previous revision still serves, and a later Start field work or a Move to the same owner does not repair it on its own (nothing changes in Postgres, so the sync answers `same` without reading the draft). The previous revision's Move writes owners the same way, and its Archive or Restore, paused before Firestore, can reopen a draft that a Submit on the new revision has since recorded. So after the previous revision drains, repair every job, not only those a Start field work was answered on or those Postgres shows changed during the window. A previous-version write can land in the field database after its Postgres commit without moving any Postgres timestamp. Raise every job's field revision by one as the migrator (`UPDATE jobs SET field_revision = field_revision + 1`, with row-level security lifted inside that transaction as in the [backups runbook](backups.md)). The draft sync's repair pass then syncs each of them over the following worker periods, with no request, until the backups runbook's count of jobs still behind is 0. Check them with reads only, never a screen (opening a job writes its locator): the [backups runbook](backups.md)'s count of jobs still behind, as the migrator in a rolled-back transaction, and the field drafts' state and owner read in the console, against the state the draft sync maps Postgres to, as the backups runbook step 5 lists it: every draft names the job's field owner, an archived job's earlier drafts are `submitted` beside its `archived` current draft, and a recorded draft is still `submitted`. **The residual window of the draft sync itself:** the sync reads the job's field revision inside its Firestore transaction, after its reads and before its writes, so a request that read Postgres before a later change writes nothing; a change that commits in the milliseconds between that check and the Firestore commit can still see the older owner written. The sync that wrote it reads the job's versions again after its commit, its last try included, and syncs the job again at once; when its tries are used up with Postgres still ahead it records nothing as synced and answers 503 (the same request again), so a former field owner can reach the draft only until the next sync of that job succeeds (the change's own field step, a retry, or the repair pass). Live has no release workflow yet.

The owner runs parts A to D once, in order, from the repository root on a machine with `gcloud`, `gh`, `terraform`, `node`, `psql` and the [Cloud SQL Auth Proxy](https://cloud.google.com/sql/docs/postgres/sql-proxy) (part B only; [Cloud Shell](https://cloud.google.com/shell) has all of them and reaches the instance from inside Google); no Docker is needed. **First-run order:** the part B grants must be in place before the migration job first executes, which is the first release after part D; a release before part B fails at migrate, before any traffic moves, and is rerun after part B. Agents never run them. Steps 1 to 4 of [Apply the central Terraform](terraform-apply.md#apply-the-central-terraform) come first.

**A. Workload identity pool and provider for test (step 9).** The settings below match the configuration the owner applied on 2026-11-19. The provider requires repository ID `1413863528` (`nnorman100/adr-field-estimator`), owner ID `201970234`, the `master` branch, and the `test` GitHub environment. It also requires the `workflow_ref` of `web-release.yml` or `ai-evals.yml` on `master` and an `event_name` of `workflow_run` or `workflow_dispatch`. [GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc), [Google Cloud Workload Identity Federation for deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)

Without the workflow and event checks, any workflow on `master` with permission to request an OIDC token could get credentials by naming the `test` environment, including workflows triggered by `pull_request_target` or `workflow_run`, which GitHub runs in the context of the default branch. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

```bash
gcloud iam workload-identity-pools create dryscope-test --project=dryscope --location=global \
  --display-name="DryScope test GitHub Actions"
gcloud iam workload-identity-pools providers create-oidc github --project=dryscope --location=global \
  --workload-identity-pool=dryscope-test --display-name="adr-field-estimator master, test" \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository_id=assertion.repository_id,attribute.repository_owner_id=assertion.repository_owner_id,attribute.ref=assertion.ref,attribute.environment=assertion.environment,attribute.workflow_ref=assertion.workflow_ref,attribute.event_name=assertion.event_name" \
  --attribute-condition="assertion.repository_id == '1413863528' && assertion.repository_owner_id == '201970234' && assertion.ref == 'refs/heads/master' && assertion.environment == 'test' && assertion.workflow_ref in ['nnorman100/adr-field-estimator/.github/workflows/web-release.yml@refs/heads/master', 'nnorman100/adr-field-estimator/.github/workflows/ai-evals.yml@refs/heads/master'] && assertion.event_name in ['workflow_run', 'workflow_dispatch']"
```

If a credentialed workflow file is renamed or a new credentialed workflow is added, the owner must update the provider's `workflow_ref` allowlist and this runbook.

Use the same pattern for the planned live pool, with the live environment and only the workflow refs and trigger events the live release requires. See [S8-18](../plans/S8/S8-18.md).

**B. Database bootstrap (step 5).** Set a password for the built-in `postgres` user (typed at the prompt; never stored in git, chat or Terraform), start the proxy as yourself in a second terminal, and grant the migrator only what migrations need:

```bash
gcloud sql users set-password postgres --instance=dryscope-test-pg --project=dryscope --prompt-for-password
gcloud auth application-default login            # the proxy uses your own credentials
cloud-sql-proxy --port=5433 dryscope:us-central1:dryscope-test-pg   # second terminal; stop it afterwards
psql "host=127.0.0.1 port=5433 user=postgres dbname=dryscope"
```

```sql
ALTER ROLE "dryscope-migrate-test@dryscope.iam" CREATEROLE;
GRANT CREATE ON DATABASE dryscope TO "dryscope-migrate-test@dryscope.iam";
GRANT USAGE, CREATE ON SCHEMA public TO "dryscope-migrate-test@dryscope.iam";
```

Never grant the migrator `cloudsqlsuperuser` or `BYPASSRLS`. The first release's migrate job then applies `web/migrations` as the migrator, from the Cloud Run job. Part B needs a direct connection to the instance as the owner: run it from Cloud Shell or any machine that reaches it (the build server does not).

**D. The app root (step 6).** Copy the two references from that run's summary (`api_image` and `live_image`, each ending in `@sha256:<64 hex>`), apply the app root with them, then start a run again; this one releases. The apply also creates the migration job `dryscope-migrate-test` from the `api_image` digest, its `dryscopeMigrateJobTest` role and the deploy account's grant on it. It also creates the Cloud Scheduler job `dryscope-access-projection-test`, which calls the web app's access-projection route every five minutes as `dryscope-scheduler-test` ([scheduled job calls](terraform-apply.md#scheduled-job-calls)); the data root must have created that account and enabled the Cloud Scheduler API first. The scheduler account, the scheduler job and the rules release role are test only for now: a live apply creates none of them, and the live wiring comes in a later step. If the app root is already applied, the same plan shows exactly those creates (the three migration-job resources if they are new, and the scheduler job) and nothing else. Parts A (including `deploy_acts_as["migrate"]`) and B must be done before that run.

```bash
API_IMAGE='us-central1-docker.pkg.dev/dryscope/dryscope-test/web@sha256:<from the run summary>'
LIVE_IMAGE='us-central1-docker.pkg.dev/dryscope/dryscope-test/live-placeholder@sha256:<from the run summary>'
cd infra/dryscope/app
terraform init -reconfigure -backend-config=envs/backend-test.hcl
export TF_VAR_alert_email='<alert address>'      # never in git
terraform plan -var-file=envs/test.tfvars -var api_image="$API_IMAGE" -var live_image="$LIVE_IMAGE" -out=test.tfplan
terraform show -json test.tfplan > test.json && node ../scripts/check-plan.js app test test.json
terraform apply test.tfplan
cd ../../..
gh workflow run web-release.yml --ref master
```

The apply waits for both services to become ready, which needs a version in every `dryscope-test-*` secret (step 4). Creating the job runs nothing. `dryscope-live-test` answers 503 until stage S7 ships the real relay. Check: `curl -s "$(gcloud run services describe dryscope-api-test --region=us-central1 --project=dryscope --format='value(status.url)')/api/health"` prints `{"status":"ok","env":"test","commit":"<COMMIT>","version":"<YYYY.MM.DD-N>","database":"ok"}`.

To build an image by hand instead (Linux or macOS, no Docker): `web/scripts/install-crane.sh ~/.local/bin`, `npm ci` in `web/`, `gcloud auth print-access-token | crane auth login us-central1-docker.pkg.dev -u oauth2accesstoken --password-stdin`, then `web/scripts/build-image.sh web --commit "$(git rev-parse HEAD)" --version <YYYY.MM.DD-N> --tag us-central1-docker.pkg.dev/dryscope/dryscope-test/web:$(git rev-parse HEAD)` and `crane digest` that tag. On macOS set `TAR=gtar` (GNU tar). The CI-built images are preferred: the standalone output then comes from the same Linux build as every release.

After the first release passes, rerun the part D plan with the same variables: it must report no changes, which shows the release changed only what Terraform ignores (the services' and the job's image, and traffic). To rerun only the migrations (for example after part B): `gcloud run jobs execute dryscope-migrate-test --region=us-central1 --project=dryscope --wait`; it applies nothing when the ledger is current.
