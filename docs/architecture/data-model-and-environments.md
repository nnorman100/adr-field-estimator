# Architecture: Data model, S2 skeleton and environments

Part of [Architecture](../ARCHITECTURE.md).

## Data model (high level)

- Signed agreements and evidence are **immutable**. Mutable coordination (assignment, claim details, delivery, readings) lives in **sidecars** beside the job.
- Private collections: `_companies`, `_memberships`, `_platform_admins`, `_invitations`, `_invite_keys`, `_admin_events` (also the support audit log), `_company_retention`, `_retention_state`, `_company_limits`, `_workspace_jobs`, `_workspace_authorizations`, plus others listed in `docs/company-workspaces.md`.
- Drafts autosave to a per-user IndexedDB queue and sync when online; conflicts return 409 and keep local work.

### S2 app skeleton (present, not deployed)
`web/` holds the new TypeScript app beside the current one: Next.js (App Router, TypeScript strict), Tailwind v4 (Safari 16.4+, the iOS baseline) with shadcn/ui, Zod at the sample `POST /api/echo` route, `GET /api/health`, a typed config module (`web/src/lib/config.ts`) checked once at server start by `web/src/instrumentation.ts`, so the server refuses to start with missing or invalid environment, Vitest unit tests and Playwright browser tests (a smoke test, the sign-in screens against the Auth emulator, the second-step screens, the operator screens, and the team screens) in Chromium and WebKit.
Postgres schema changes are numbered SQL files in `web/migrations`, applied by `npm run db:migrate` and recorded in `migration_ledger`.
The first file creates that ledger and an empty `companies` table (`id`, `created_at`);
`0002_identity` adds the sign-in and company-separation tables (`docs/DATA.md`), which `GET /api/me` reads;
`0003_runtime_role` adds the runtime role and forced row-level security on every table, and `withCompany` (`web/src/db/tenant.ts`) is the only way the runtime sees a company's rows;
`0004_sign_in_lookup` adds `sign_in_company(tenant)`, the one lookup before a company is known.
`0005_access_projection` adds the outbox worker's one lookup across companies and an index for one actor's outbox rows,
`0006_platform_operator` the platform operator's sign-in lookup and its cross-company rights inside `withOperator`,
`0007_sign_in_address` the company sign-in page's lookup by address,
and `0008_feature_flag_writes` the operator's write path on `company_feature_flags`,
`0009_price_tables` the company price tables (`price_table_versions`, `price_table_working_copies`; S4-5, read and written by the Prices API, S4-6, `web/src/lib/prices/`, routes in `docs/ACCESS.md`),
and `0010_core_job_tables` the job header, customer, claim and evidence registry tables plus the company profile columns (`jobs`, `job_customers`, `job_claims`, `evidence_objects`; S5a-2),
and `0011_submissions_agreements` the submission, price pin, estimate and agreement tables with the worker's lookup across companies (`job_submissions`, `job_price_pins`, `job_estimates`, `agreements`, `job_submission_due_companies`; S5a-7; the submission routes and the estimate routes, S5a-8 and S5a-9, `web/src/lib/estimates/`, use them, and `docs/ACCESS.md` "Estimate and review" owns their rules),
and `0012_ai_live_tables` every AI and Live table of stage S7 with the sweeper's lookup across companies (`company_ai_settings`, `ai_ledger`, `ai_results`, `live_sessions`, `live_usage`, `live_turns`, `voice_notes`, `member_voice_settings`, `live_session_due_companies`; S7-3, Drizzle view `web/src/db/ai-schema.ts`, code default ceilings `web/src/lib/ai/ceilings.ts`, no route uses them yet),
and `0013_company_documents` the letterhead lines and the document settings on `companies` (S5a-4b: five one-line columns and `profile_documents`, a `jsonb` object under 64 KiB whose shape the Zod schema in `web/src/lib/profile/settings.ts` checks at write and read; the column grant and 0010's trigger split cover them),
and `0014_signing_links` the remote signing link and the document links (`signing_links`, `document_links`, the link id and signer role on `agreements`, and the two token-hash lookups across companies; S5a-11b; routes in `web/src/lib/links/`, the token-in-a-header `linkRoute` rule in `web/src/lib/auth/route.ts`, rules in `docs/ACCESS.md` "Signing links and document links"),
and `0015_office_jobs` the estimator assignments, the office notes and the corrections after signing (`job_assignments`, `job_coordination`, `agreement_corrections`; S5b-1; routes in `web/src/lib/jobs/office.ts`, rules in `docs/ACCESS.md` "Jobs routes"),
and `0016_job_drafts` the claim of each field draft id for one job (`job_drafts`; security audit F1; `claimDraft` in `web/src/lib/jobs/access.ts`),
and `0017_definer_search_path` the search path `pg_catalog, pg_temp` on every `SECURITY DEFINER` function, so a caller's temporary type cannot stand in for one the function uses (security audit F4),
and `0018_field_revision` each job's field revision, raised by triggers on every input of its drafts' life cycle, with the sync's watermark, the copy source and the repair worker's lookup across companies (`jobs.field_revision`, `field_synced_revision`, `field_changed_at`, `copied_from_job_id`, `job_field_sync_due_companies`; draft life-cycle redesign slice 1; Copy records the copy source, and the sync that reads them comes later),
and `0019_price_approvals` the proposals and approvals on a job (`job_price_approvals`: named adjustments, custom multipliers and hourly, unit and flat additions, each bound to the job's submission, revision and price hash; S5b-8; no route uses it yet) and the submission and agreement kind `revision` (S5b-9),
and `0020_drying_outcomes` the drying log, the job close and the estimate history (`drying_readings`: client-made ids, raw readings that never change and a void set once; `job_closes`: append-only close versions bound to the job's agreement; `estimate_history`: one insert-only sample per signed agreement) and the drying watch's decisions (`job_coordination.drying_watch`); S5b-10 slice 10A; the drying log routes use `drying_readings` (slice 10B), no route uses the others yet (`docs/DATA.md`).
The jobs routes (S5a-3, `web/src/lib/jobs/`, `docs/ACCESS.md` "Jobs routes") create a job from a job id and a first draft id made on the phone (the Postgres row first, then its Firestore field draft; a retry makes whichever is missing), list the company's or the caller's own jobs, read a job, and save its customer, property address and claim with a revision and a change id so a retry after a lost response is no conflict; every job route goes through one job-access function.
The photo routes (S5a-5, `web/src/lib/photos/`, `docs/ACCESS.md` "Photo routes") take a photo or its full-size original as a raw image through the app server, store it in the evidence bucket (`EVIDENCE_BUCKET`) create-only and register it once with its SHA-256, refuse a new photo once the field draft is no longer being edited, and stream it back to anyone who may see the job with `no-store`; the bucket is a seam, replaced by a fake in CI.
The company profile routes and the Company settings screen (S5a-4, `web/src/lib/profile/`, `/sign-in/{address}/company`; `docs/ACCESS.md` "Company profile API") let the owner read and save the address, phone, email, licence and sign-off the documents print, on the company's own row (no new migration), and since S5a-4b the letterhead lines and the document settings (migration 0013; a save that leaves those out keeps them); a save names the revision it was based on, and the engine's setup check (`web/src/engine/company-setup.ts`) lists what is still missing.
The AI spend ledger (S7-4, `web/src/lib/ai/budget.ts`) is the AI boundary's budget and quota store over migration 0012's `ai_ledger` and `company_ai_settings`: each company's reservations run one at a time under a transaction-scoped advisory lock, so parallel calls cannot pass the company's daily or monthly ceiling ($10 and $200 by default, V5 B) or a person's daily quota for a feature; settlement is once per call id, and a hold is released only by a settlement with a known cost.
The owner reads the AI used today and this month on Company settings (`GET /api/companies/{id}/ai-usage`, key `ai_usage_read`), and only the platform operator sets a company's ceilings (`PUT /api/platform/companies/{companyId}/ai-settings`, one audit row).
On Cloud Run the app reaches Cloud SQL over the `/cloudsql` socket as its own IAM database user (`SQL_CONNECTION_NAME`, `SQL_DATABASE_NAME`, `SQL_IAM_USER` from Terraform), with a metadata-server access token as the password (`web/src/db/client.ts`); the release migrator (the Cloud Run job `dryscope-migrate-<env>`, `web/src/db/job.ts`) logs in the same way as `dryscope-migrate-<env>`; local work uses `DATABASE_URL`. Every connection the app opens there (the main pool, the access-renewal pool and the health probe) carries time limits (security audit F5): the server ends a statement after 30 seconds, a lock wait after 10 seconds (the access-renewal run raises its own to 15) and a transaction left idle for 30 seconds (every transaction that waits on Firestore or Identity Platform while open raises its own to 300 seconds, `holdAcrossOutsideCall` in `web/src/db/tenant.ts`, which lists them), and a transaction that waits more than 10 seconds for a free connection is refused instead of waiting (the sign-in check of member routes, the public sign-in lookup and the scheduled worker pass answer 503; a company sign-in page, or a screen under its address, shows "busy, try again shortly" on the same address, with the framework's 500 status, since a server-rendered page cannot set its own). Team invitations make the invitee's sign-in account with no transaction open. The migration runner keeps its own settings (`web/src/db/migrate.ts`).
Request identity (`web/src/lib/auth/`, S3-7) checks a Firebase ID token with firebase-admin on the project (signature, audience, issuer and expiry; the tenant it reads is signed), finds the company from that tenant, checks the token again with the revocation check on that tenant's client, requires a verified email, and loads the actor and active membership of an active company inside `withCompany`; a company id in the URL, a header or the body is never read.
The company's feature flags (`web/src/lib/flags/`, S3-11a; a fixed list, all off unless stored on) are read in the same transaction and decide the price capabilities; `requireFlag` answers 404 for a switched-off feature.
Only the platform operator changes a flag, through `POST /api/platform/companies/{companyId}/flags` (S3-11b, `0008_feature_flag_writes`; no company role can, an owner included); it writes the flag and one audit row together and refuses an unknown flag name.
Every route handler is wrapped in an access rule (`publicRoute`, `memberRoute`, `accountRoute`, `requireFlag`, `operatorRoute` for the platform operator routes under `/api/platform/` (S3-9, `web/src/lib/platform/`), or `serviceRoute` for internal job routes only the scheduler service account may call), and `web/tests/unit/route-rules.test.ts` finds every route file and fails on one that is not.
`GET /api/me` returns the signed-in member's company, role, capabilities and the company switches the screens read (`features`, an allowlist: `readiness` today; see [Ready to review?](../access/readiness.md)).
Second-step and session rules (`web/src/lib/auth/policy.ts`, S3-8) run inside that same check: an owner (and later the platform operator) must have signed in with an authenticator app (`firebase.sign_in_second_factor` is `totp`; a text message does not count, and the accepted list is fixed in code with no setting), or is refused with `second_step_required` on every route except one that declares itself the enrolment route (`memberRoute(handler, { secondStep: 'enrolment' })`); since 2026-11-14 (D-030) office staff must too, and estimators may opt in.
A sign-in (`auth_time`) older than the role allows, operator 12 hours, owner and office 14 days, estimator 30 days, is refused with `sign_in_again`, as is one older than 15 minutes on a route that declares `{ freshSignIn: true }` (team and second-step changes, and the operator's company status, tenant binding, feature flag and AI ceiling changes, D-030).
The team and invitation routes (S3-10, `web/src/lib/team/`) declare `{ freshSignIn: true }` on every team change; nothing calls the enrolment option yet.
Under `/api/companies/{companyId}/` the owner lists the team (an office user gets only active estimators), invites (estimator or office, 7 days, a link to copy: no email service is set up), resends, cancels and clears invitations, switches a member between estimator and office, and disables (revoking their sessions before answering) or re-enables a member; the owner membership cannot be changed there, and a path company that is not the caller's own answers 404.
`accountRoute` admits a verified account of the company that is not yet a member, for `GET /api/invitations/{id}` and `POST /api/invitations/{id}/accept`: an invitation for another email reads as not found, and accepting creates the actor and one membership once, under the session rules of the role accepted.
Inviting makes a password-less, unverified account for the email in the company's tenant (firebase-admin, the narrow `dryscopeIdentity<Env>` role).
Every change writes an audit row and every membership change an `access_projection_outbox` row in its transaction.
A throwaway Postgres runs those files from empty in `.github/workflows/web.yml`.
An emulator harness (`npm run test:emu`, `web/firebase.json`, `web/tests/emu/`) runs the Firebase Auth and Firestore emulators in that workflow under a `demo-` project id only and refuses any other; it checks that a token carries its tenant and records that the Auth emulator refuses authenticator-app (TOTP) enrolment, so TOTP is proved only against a real test environment.
The field database rules (`web/firestore.rules`, loaded by that emulator) deny by default and allow only a draft and its `rooms` and `photos` documents under `companies/{companyId}/drafts/...`, when the token's sign-in tenant is the company's and the caller holds an unexpired server-written access record: the company's owner and office read every draft and an estimator only their own, and only the draft's field owner changes its `field` data (and deletes a room document, S5a-6), while the draft is `editing`, with each key's type and size checked against field map v2 (`web/src/lib/field/`, S5a-1 and S5a-10; `docs/DATA.md`).
`web/tests/emu/rules/` checks them with two tenants.
The server writes the access records through the outbox in `web/src/lib/projection/` (see `docs/DATA.md`): each team change projects its member after it commits, and `POST /api/internal/access-projection` (scheduler service account only) runs the pass across companies; the test release workflow releases the rules to `dryscope-field-test` (live stays owner-run; `docs/runbook/test-release.md`).
It has its own `package.json`, ESLint config (`max-lines` 1,000) and CI workflow (time-limited jobs).
It also holds the S4 pricing engine in `web/src/engine/` (a TypeScript calculator, clauses and canonical bytes, with the `PriceTableV3` Zod schema in `table.ts`; its stable entry `priceEstimate` and publish check `checkTable` in `estimate.ts` are checked by hand-worked examples, exact clause text and property tests in `web/tests/unit/estimate-*.test.ts`); the Prices API calls it for the publish check and preview, and the estimate routes (`web/src/lib/estimates/`, S5a-9) price a job's submitted record with it.
The company roles and capability table are ported to `web/src/lib/access/` (deny by default; `prices_read` and `prices_manage` exist only when the price-books flag is passed in as on) and checked against `docs/ACCESS.md`.
The company sign-in screens (S3-13a, `web/src/app/(auth)/sign-in/[address]/`) sign in in the browser with the Firebase JS SDK (`web/src/lib/firebase-client.ts`) to the tenant of the company named by the sign-in address, one Firebase app instance per tenant so each company's saved sign-in stays apart, and decide what to show from `GET /api/me`; the company's name and tenant come from the public `GET /api/sign-in/{address}` (`web/src/lib/sign-in/`), which the database answers through `sign_in_company_page` (`0007_sign_in_address`, S3-13b; `docs/DATA.md`) and answers 404 for an unknown, inactive, tenant-less or malformed address.
The second-step screens (S3-14, `web/src/app/(auth)/second-step/`, the Firebase calls in the same `firebase-client.ts`) are states of that page: a person whose role needs the authenticator-app second step and has none sees only its setup (a QR code drawn in the browser by `qrcode-generator`, the same key to type, a code from the app to prove it), with no way on to the app; a password or Google sign-in of an enrolled person asks for the app's code before any session exists; a signed-in person can add another authenticator app; and the setup screen says the second step was reset when this phone remembers one that is gone (a marker held only on the phone).
The Auth emulator cannot do authenticator-app enrolment, so their browser tests answer Identity Platform's second-step calls at the network boundary (`web/tests/e2e/second-step/fake-totp.ts`), and the real flow is proved on a `test` tenant in S3-18.
The platform operator screens (S3-15, `web/src/app/operator/[tenantId]/`, calls in `web/src/lib/operator/`) sit at `/operator/{operator tenant id}`, sign in to that tenant and call only the `/api/platform/` routes: Companies (list, create), Company administration (status, owner, second-step reset) and a read-only team view, with no screen for customer data; who may open them and what they leave out are in `docs/ACCESS.md` and `docs/plans/S3.md`.
The owner's team and invitation screens (S3-16) are "Team and invitations" at `/sign-in/{address}/team` (invite by email and role and copy the link, resend, cancel and clear invitations, switch a member between estimator and office, turn a member off and on; the screen asks the server who is signed in and requests the team only for a role holding `team_manage`, and the server refuses everyone else again) and "Accept invitation" on the invitation link, which shows the invitation only to the account it is addressed to and, when the server refuses an owner or office invitation for a missing second step, shows the authenticator-app setup and then tries again (or asks for a sign-in with the app's code).
Against the Auth emulator the team records and the owner's second step are stood in for by the same `LOCAL_SIGN_IN_FIXTURE` file (`web/src/lib/team/local-team.ts`), as the emulator cannot do the second step.
Its one other product screen is the field shell `/field` (S6-2, `web/src/app/field/`): prerendered and data-free, it starts in the browser from the `ds-me` row the sign-in page saves, shows the job screens (S5a-6, `web/src/app/field/field-app.tsx`, `web/src/lib/field/`: Jobs, New job, Check Scope, Customer and claim, Photos, and from S5b-1 Job coordination for the owner and office (notes, Assign estimator, Start field work and the owner's move of the field work, `docs/access/jobs.md`), each a view of `/field` chosen by the address's query, read in the browser after sign-in; `docs/plans/S5.md`), opens with no signal through the worker `web/sw/sw.js` (built to `/sw.js` after `next build` by `web/scripts/build-sw.ts`, and checked against the files the page loads), and shows the "No signal", "Not saved on this phone" and Home Screen install notices (`docs/plans/S6.md`).
`web/src/proxy.ts` refuses every `/api` route outside a four-route public list (health, the echo sample, that sign-in lookup and the browser error reports, `POST /api/client-errors`, TC-2) with 401 when signed out, and passes `/api/me`, the team and invitation routes and the Prices routes (`memberApiPaths` in `web/src/lib/public-api.ts`, one uuid per `:id` segment) on to their own sign-in check, and the internal job routes (`serviceApiPaths`) on to their own service-token check.
`web/scripts/build-image.sh` assembles the standalone production image without a Docker daemon (crane appends one root-owned `/app` layer onto the Node base pinned in `web/Dockerfile`; the app runs as the unprivileged `node` user, with its commit and release version baked in and reported by `/api/health`, which answers 503 when a configured database refuses the service's login).
`.github/workflows/web-release.yml` releases it to the **test** environment in project `dryscope` only, keylessly: image by digest, migrations as the migrator before traffic, a 0% tagged revision smoke-checked by `web/scripts/smoke-release.ts`, then all traffic, with rollback, then a release record: a `YYYY.MM.DD-N` tag and a pre-release GitHub Release carrying `manifest.json` and the rollback command, or one failed-release line in Cloud Logging (`docs/runbook/test-release.md`).
It skips until the owner's setup is done.
`live-relay-placeholder/` is a 503 stand-in image the app root needs for the Live service until S7.
The app is not built into the Python service, and changes no hosting or deploy.
The Python backend and `public/` app are untouched.
Run commands are in `README.md`.

## Environments

The current Python app runs in `alert-disaster-field-2026`, where releases are staged on a tagged Cloud Run revision at 0% traffic, checked, then promoted, then Hosting is deployed (`docs/runbook/releases.md`). The TypeScript rebuild is a clean start in dedicated Google Cloud project `dryscope` (project number `570228742694`), which holds the `test` environment in `us-central1`, defined in `infra/dryscope/` (Cloud SQL tiers per environment: `infra/dryscope/README.md`). Technology Standard 2.7 gives every environment its own Google Cloud project (D-018): the `live` project is created before S8 (it has no resources yet, so nothing moves), and `dryscope` is not split. Until then, `infra/dryscope/` still defines separate `test` and `live` resources, and App Check enforcement, Model Armor floor settings, sign-in settings, spend caps and quotas are project-wide, so the owner approves each change before the live project exists. `alert-disaster-field-2026` stays running unchanged until the rebuilt app is live.
