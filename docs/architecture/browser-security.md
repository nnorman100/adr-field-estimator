# Architecture: Browser security headers and App Check

Part of [Architecture](../ARCHITECTURE.md).

### Browser security headers (F7)
Every `web/` page and API answer carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=31536000` (this host only: no subdomains, no preload), and an enforced `Content-Security-Policy` of exactly `frame-ancestors 'none'; object-src 'none'; base-uri 'self'`. Nothing in it names a source Google serves, so it cannot break sign-in. One exception: the photo download (`/api/jobs/{jobId}/photos/{photoId}`, photo and original) gets no app-wide policy and keeps its own stricter `default-src 'none'; sandbox`, because Next drops a route's own header when the configuration already set one of that name; it still gets the other four headers. A full script/connect policy now runs alongside it as `Content-Security-Policy-Report-Only`, with native reports sent to the existing capped `/api/client-errors` intake. Its runtime sources, static-shell nonce limitation, Zod no-eval setup, report privacy and automated coverage are recorded in [CSP observation](../security-csp.md). Enforcement remains a later change after a test-environment phone run with real Google sign-in, the authenticator-app step, App Check/reCAPTCHA and offline reconnect. Code: `web/src/lib/security-headers.ts`, `web/next.config.ts`; tests: `web/tests/unit/security-headers.test.ts`, `web/tests/db/photos-api.test.ts`, `web/tests/e2e/security-headers.spec.ts`.

### App Check, monitor mode (TC-5)
The browser starts App Check (reCAPTCHA Enterprise provider, automatic refresh) on each company's Firebase app instance before its Auth is used, only when the server gives it both `FIREBASE_APP_ID` and `APP_CHECK_SITE_KEY` (public values; either missing or empty means App Check is off and the app behaves as before). Firebase Auth and Firestore wait for an App Check token before every request, and neither the SDK's reCAPTCHA loader nor its IndexedDB token cache has a time limit, so each attestation is cut off after 3 seconds (the SDK then retries later) and the token Auth and Firestore read answers within 3 seconds, empty when none came in time (they then send no App Check header and do not wait again while that request is still running). Every `/api` call adds `X-Firebase-AppCheck` when a token comes within 3 seconds, and otherwise goes without it (and does not wait again while that request is still running). The debug token (`self.FIREBASE_APPCHECK_DEBUG_TOKEN`) is honoured on `localhost` and `127.0.0.1` only. The sign-in screens show Google's "This site is protected by reCAPTCHA." line and the badge is hidden. On the server, `APP_CHECK_MODE` is `monitor` (default) or `off`; `enforce` stops the server at start-up until TC-13. In monitor mode every browser-facing route wrapper (not `serviceRoute`) checks the token with the Admin SDK (2-second limit, no replay protection) and writes one `App Check` line: `outcome` (`valid`, `missing`, `invalid`, `unverified`), `method`, `route` (the pattern, ids replaced by parameter names) and `status`. It never refuses a call or changes its answer. The field database's per-person app instances (`field-db.ts`) start App Check the same way before their Auth and Firestore are used, keeping each person's cache apart; the sync-gate token step and its offline tests are TC-7. Terraform sets `APP_CHECK_MODE=monitor` on both services through the app root's `common_env`, and `FIREBASE_APP_ID` and `APP_CHECK_SITE_KEY` only once both are passed (`firebase_app_id`, `app_check_site_key`; empty by default, so App Check stays off until TC-11's apply passes them). Code: `web/src/lib/app-check-client.ts`, `web/src/lib/app-check.ts`, `web/src/lib/auth/route.ts`; tests: `web/tests/unit/app-check*.test.ts`, `web/tests/e2e/app-check.spec.ts`, `web/tests/e2e/app-check-screens.spec.ts`.
