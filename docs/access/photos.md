# Access matrix: Photo routes

Part of [Access matrix](../ACCESS.md).

## Photo routes (rebuilt app, S5a-5)

`web/src/lib/photos/`, two handlers on one path, `/api/jobs/{id}/photos/{photoId}`, both `memberRoute` and both through the job-access function above. No new capability key. The bytes pass through the app server; no browser ever holds a bucket address or a signing key.

| Route                                                                 | Who                                                  | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUT /api/jobs/{id}/photos/{photoId}?kind=photo`                      | `photos` (owner, estimator)                          | The raw image as the body (JPEG, PNG or WebP, told by its own first bytes, at most 30 MiB, under Cloud Run's 32 MiB request limit; 415 and 413 otherwise). A new photo needs a job still on its draft and a field draft being edited: while it is `submitting` or after it is `submitted`, or once the job is signed, it is 409 `draft_locked`. A draft already holding `MAX_PHOTO_REFS` (300) photo references takes no new photo: 409 `photo_limit`, and the phone stops offering Take photo at that count. The server computes the SHA-256, creates the object with a create-only precondition (`ifGenerationMatch=0`, so bytes are never overwritten) and registers it once. 201 and the receipt (photo id, kind, hash, size, type, time) the first time, 200 and the same receipt for the same bytes again, 409 `photo_conflict` for other bytes under the same id. A photo already registered answers its receipt even after the draft is locked, so a lost answer is always settled by sending again. The phone then writes the photo's reference document. |
| `PUT /api/jobs/{id}/photos/{photoId}?kind=original`                   | `photos` (owner, estimator)                          | The full-size original of a photo the job already holds, sent with `X-Photo-Sha256`: the hash of that registered photo (409 `photo_missing` when there is none, 409 `photo_conflict` when the hash is another). It may arrive after the job is signed and the draft locked, and changes nothing in the record. Same receipt rules as a photo.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `PUT /api/jobs/{id}/photos/{photoId}?kind=signature`                  | `sign` (owner, estimator)                            | The customer's signature image (S5a-11), sent before the agreement under an id made on the phone. A new signature needs a current unsigned estimate: the job submitted, not signed, and its current record priced at its current pin (409 `not_ready_to_sign` otherwise, checked again under the job's row lock when the registry row is made). Stored create-only under `companies/{c}/jobs/{j}/signatures/{id}`; the same bytes again answer the same receipt (also after signing, for a lost answer), other bytes under that id 409 `photo_conflict`. One audit row `signature_received`.                                                                                                                                                                                                                                                                                                         |
| `GET /api/jobs/{id}/photos/{photoId}?kind=photo\|original\|signature` | `jobs_read` (everyone with the job, office included) | Streams the stored bytes with the stored type, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and a sandboxing content security policy. No kind means the photo. 404 for a photo or original that is not registered.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

A job another estimator owns, or another company's, is 404 on both (never a hint that it exists), an archived job is 410, and office sending a photo is 403. The job id in the path never grants anything: the registry row is looked up in the caller's own company only, so another company's photo id on the caller's own job is as missing as on its own. Every new row adds one audit row with the job id, the kind and the size only. Object names are `companies/{company}/jobs/{job}/photos/{photoId}` and `.../originals/{photoId}`: ids only, no hash, type or person in the name, so one photo id is one object and a second upload of it meets the precondition whatever its bytes.
