## Overview

```
Phone browser (static app, public/*.js, installable PWA, offline queue in IndexedDB)
   │  Firebase ID token                          ┌─► Vertex AI (Gemini Live relay, audit/OCR models)
   ▼                                             │
Firebase Hosting (alert-disaster) ── /api/** ──► Cloud Run: alert-disaster-field-estimator (Python, us-west2)
                                                 ├─► Firestore (default) — private, deny-all to browsers
                                                 ├─► Private evidence bucket (photos, signed evidence)
                                                 ├─► Secret Manager (Maps key, SMTP, etc.)
                                                 └─► Email (Gmail SMTP today; see docs/roadmap.md risks)
```

The diagram shows the current Python app, which lives in Google Cloud / Firebase project `alert-disaster-field-2026`; the rebuild is in project `dryscope` (see Environments). Peer sites and shared databases are never touched.

## Two engines

1. **Live walkthrough** — authenticated WebSocket relay; 16 kHz audio and a 640 px frame every 2 s; coaching and meter-photo reading.
2. **Claims engine** — `POST /api/audit`: transcript + photos + facts → four documents. The server applies prices and mandatory wording; the model drafts only.
   Models are set by `AUDIT_MODEL`, `OCR_MODEL`, `LIVE_MODEL`.

## Data model (high level)

- Signed agreements and evidence are **immutable**. Mutable coordination (assignment, claim details, delivery, readings) lives in **sidecars** beside the job.
- Private collections: `_companies`, `_memberships`, `_platform_admins`, `_invitations`, `_invite_keys`, `_admin_events` (also the support audit log), `_company_retention`, `_retention_state`, `_company_limits`, `_workspace_jobs`, `_workspace_authorizations`, plus others listed in `docs/company-workspaces.md`.
- Drafts autosave to a per-user IndexedDB queue and sync when online; conflicts return 409 and keep local work.

### S2 app skeleton (present, not deployed)
`web/` holds the new TypeScript app beside the current one: Next.js (App Router, TypeScript strict), Tailwind v4 (Safari 16.4+, the iOS baseline) with shadcn/ui, Zod at the sample `POST /api/echo` route, `GET /api/health`, a typed config module (`web/src/lib/config.ts`) checked once at server start by `web/src/instrumentation.ts`, so the server refuses to start with missing or invalid environment, Vitest unit tests and Playwright browser tests (a smoke test, the sign-in screens against the Auth emulator, the second-step screens, the operator screens, and the team screens) in Chromium and WebKit. Postgres schema changes are numbered SQL files in `web/migrations`, applied by `npm run db:migrate` and recorded in `migration_ledger`. The first file creates that ledger and an empty `companies` table (`id`, `created_at`); `0002_identity` adds the sign-in and company-separation tables (`docs/DATA.md`), which `GET /api/me` reads; `0003_runtime_role` adds the runtime role and forced row-level security on every table, and `withCompany` (`web/src/db/tenant.ts`) is the only way the runtime sees a company's rows; `0004_sign_in_lookup` adds `sign_in_company(tenant)`, the one lookup before a company is known. `0005_access_projection` adds the outbox worker's one lookup across companies and an index for one actor's outbox rows, `0006_platform_operator` the platform operator's sign-in lookup and its cross-company rights inside `withOperator`, `0007_sign_in_address` the company sign-in page's lookup by address, and `0008_feature_flag_writes` the operator's write path on `company_feature_flags`, `0009_price_tables` the company price tables (`price_table_versions`, `price_table_working_copies`; S4-5, read and written by the Prices API, S4-6, `web/src/lib/prices/`, routes in `docs/ACCESS.md`), and `0010_core_job_tables` the job header, customer, claim and evidence registry tables plus the company profile columns (`jobs`, `job_customers`, `job_claims`, `evidence_objects`; S5a-2) (`docs/DATA.md`). The jobs routes (S5a-3, `web/src/lib/jobs/`, `docs/ACCESS.md` "Jobs routes") create a job from a job id and a first draft id made on the phone (the Postgres row first, then its Firestore field draft; a retry makes whichever is missing), list the company's or the caller's own jobs, read a job, and save its customer, property address and claim with a revision and a change id so a retry after a lost response is no conflict; every job route goes through one job-access function. The photo routes (S5a-5, `web/src/lib/photos/`, `docs/ACCESS.md` "Photo routes") take a photo or its full-size original as a raw image through the app server, store it in the evidence bucket (`EVIDENCE_BUCKET`) create-only and register it once with its SHA-256, refuse a new photo once the field draft is no longer being edited, and stream it back to anyone who may see the job with `no-store`; the bucket is a seam, replaced by a fake in CI. On Cloud Run the app reaches Cloud SQL over the `/cloudsql` socket as its own IAM database user (`SQL_CONNECTION_NAME`, `SQL_DATABASE_NAME`, `SQL_IAM_USER` from Terraform), with a metadata-server access token as the password (`web/src/db/client.ts`); the release migrator (the Cloud Run job `dryscope-migrate-<env>`, `web/src/db/job.ts`) logs in the same way as `dryscope-migrate-<env>`; local work uses `DATABASE_URL`. Request identity (`web/src/lib/auth/`, S3-7) checks a Firebase ID token with firebase-admin on the project (signature, audience, issuer and expiry; the tenant it reads is signed), finds the company from that tenant, checks the token again with the revocation check on that tenant's client, requires a verified email, and loads the actor and active membership of an active company inside `withCompany`; a company id in the URL, a header or the body is never read. The company's feature flags (`web/src/lib/flags/`, S3-11a; a fixed list, all off unless stored on) are read in the same transaction and decide the price capabilities; `requireFlag` answers 404 for a switched-off feature. Only the platform operator changes a flag, through `POST /api/platform/companies/{companyId}/flags` (S3-11b, `0008_feature_flag_writes`; no company role can, an owner included); it writes the flag and one audit row together and refuses an unknown flag name. Every route handler is wrapped in an access rule (`publicRoute`, `memberRoute`, `accountRoute`, `requireFlag`, `operatorRoute` for the platform operator routes under `/api/platform/` (S3-9, `web/src/lib/platform/`), or `serviceRoute` for internal job routes only the scheduler service account may call), and `web/tests/unit/route-rules.test.ts` finds every route file and fails on one that is not. `GET /api/me` returns the signed-in member's company, role and capabilities. Second-step and session rules (`web/src/lib/auth/policy.ts`, S3-8) run inside that same check: an owner (and later the platform operator) must have signed in with an authenticator app (`firebase.sign_in_second_factor` is `totp`; a text message does not count, and the accepted list is fixed in code with no setting), or is refused with `second_step_required` on every route except one that declares itself the enrolment route (`memberRoute(handler, { secondStep: 'enrolment' })`); office staff and estimators may opt in. A sign-in (`auth_time`) older than the role allows, operator 12 hours, owner and office 14 days, estimator 30 days, is refused with `sign_in_again`, as is one older than 15 minutes on a route that declares `{ freshSignIn: true }` (team and second-step changes). The team and invitation routes (S3-10, `web/src/lib/team/`) declare `{ freshSignIn: true }` on every team change; nothing calls the enrolment option yet. Under `/api/companies/{companyId}/` the owner lists the team (an office user gets only active estimators), invites (estimator or office, 7 days, a link to copy: no email service is set up), resends, cancels and clears invitations, switches a member between estimator and office, and disables (revoking their sessions before answering) or re-enables a member; the owner membership cannot be changed there, and a path company that is not the caller's own answers 404. `accountRoute` admits a verified account of the company that is not yet a member, for `GET /api/invitations/{id}` and `POST /api/invitations/{id}/accept`: an invitation for another email reads as not found, and accepting creates the actor and one membership once, under the session rules of the role accepted. Inviting makes a password-less, unverified account for the email in the company's tenant (firebase-admin, the narrow `dryscopeIdentity<Env>` role). Every change writes an audit row and every membership change an `access_projection_outbox` row in its transaction. A throwaway Postgres runs those files from empty in `.github/workflows/web.yml`. An emulator harness (`npm run test:emu`, `web/firebase.json`, `web/tests/emu/`) runs the Firebase Auth and Firestore emulators in that workflow under a `demo-` project id only and refuses any other; it checks that a token carries its tenant and records that the Auth emulator refuses authenticator-app (TOTP) enrolment, so TOTP is proved only against a real test environment. The field database rules (`web/firestore.rules`, loaded by that emulator) deny by default and allow only a draft and its `rooms` and `photos` documents under `companies/{companyId}/drafts/...`, when the token's sign-in tenant is the company's and the caller holds an unexpired server-written access record: the company's owner and office read every draft and an estimator only their own, and only the draft's field owner changes its `field` data, while the draft is `editing`, with each key's type and size checked against field map v1 (`web/src/lib/field/`, S5a-1; `docs/DATA.md`). `web/tests/emu/rules/` checks them with two tenants. The server writes the access records through the outbox in `web/src/lib/projection/` (see `docs/DATA.md`): each team change projects its member after it commits, and `POST /api/internal/access-projection` (scheduler service account only) runs the pass across companies; the test release workflow releases the rules to `dryscope-field-test` (live stays owner-run; `docs/runbook/test-release.md`). It has its own `package.json`, ESLint config (`max-lines` 1,000) and CI workflow (time-limited jobs). It also holds the S4 pricing engine in `web/src/engine/` (a TypeScript calculator, clauses and canonical bytes, with the `PriceTableV3` Zod schema in `table.ts`; its stable entry `priceEstimate` and publish check `checkTable` in `estimate.ts` are checked by hand-worked examples, exact clause text and property tests in `web/tests/unit/estimate-*.test.ts`); only the Prices API calls it (publish check and preview), no estimate route yet. The company roles and capability table are ported to `web/src/lib/access/` (deny by default; `prices_read` and `prices_manage` exist only when the price-books flag is passed in as on) and checked against `docs/ACCESS.md`. The company sign-in screens (S3-13a, `web/src/app/(auth)/sign-in/[address]/`) sign in in the browser with the Firebase JS SDK (`web/src/lib/firebase-client.ts`) to the tenant of the company named by the sign-in address, one Firebase app instance per tenant so each company's saved sign-in stays apart, and decide what to show from `GET /api/me`; the company's name and tenant come from the public `GET /api/sign-in/{address}` (`web/src/lib/sign-in/`), which the database answers through `sign_in_company_page` (`0007_sign_in_address`, S3-13b; `docs/DATA.md`) and answers 404 for an unknown, inactive, tenant-less or malformed address. The second-step screens (S3-14, `web/src/app/(auth)/second-step/`, the Firebase calls in the same `firebase-client.ts`) are states of that page: a person whose role needs the authenticator-app second step and has none sees only its setup (a QR code drawn in the browser by `qrcode-generator`, the same key to type, a code from the app to prove it), with no way on to the app; a password or Google sign-in of an enrolled person asks for the app's code before any session exists; a signed-in person can add another authenticator app; and the setup screen says the second step was reset when this phone remembers one that is gone (a marker held only on the phone). The Auth emulator cannot do authenticator-app enrolment, so their browser tests answer Identity Platform's second-step calls at the network boundary (`web/tests/e2e/second-step/fake-totp.ts`), and the real flow is proved on a `test` tenant in S3-18. The platform operator screens (S3-15, `web/src/app/operator/[tenantId]/`, calls in `web/src/lib/operator/`) sit at `/operator/{operator tenant id}`, sign in to that tenant and call only the `/api/platform/` routes: Companies (list, create), Company administration (status, owner, second-step reset) and a read-only team view, with no screen for customer data; who may open them and what they leave out are in `docs/ACCESS.md` and `docs/plans/S3.md`. The owner's team and invitation screens (S3-16) are "Team and invitations" at `/sign-in/{address}/team` (invite by email and role and copy the link, resend, cancel and clear invitations, switch a member between estimator and office, turn a member off and on; the screen asks the server who is signed in and requests the team only for a role holding `team_manage`, and the server refuses everyone else again) and "Accept invitation" on the invitation link, which shows the invitation only to the account it is addressed to. Against the Auth emulator the team records and the owner's second step are stood in for by the same `LOCAL_SIGN_IN_FIXTURE` file (`web/src/lib/team/local-team.ts`), as the emulator cannot do the second step. It has no other product screens. `web/src/proxy.ts` refuses every `/api` route outside a three-route public list (health, the echo sample and that sign-in lookup) with 401 when signed out, and passes `/api/me`, the team and invitation routes and the Prices routes (`memberApiPaths` in `web/src/lib/public-api.ts`, one uuid per `:id` segment) on to their own sign-in check, and the internal job routes (`serviceApiPaths`) on to their own service-token check. `web/scripts/build-image.sh` assembles the standalone production image without a Docker daemon (crane appends one root-owned `/app` layer onto the Node base pinned in `web/Dockerfile`; the app runs as the unprivileged `node` user, with its commit baked in and reported by `/api/health`, which answers 503 when a configured database refuses the service's login). `.github/workflows/web-release.yml` releases it to the **test** environment in project `dryscope` only, keylessly: image by digest, migrations as the migrator before traffic, a 0% tagged revision smoke-checked by `web/scripts/smoke-release.ts`, then all traffic, with rollback (`docs/runbook/test-release.md`). It skips until the owner's setup is done. `live-relay-placeholder/` is a 503 stand-in image the app root needs for the Live service until S7. The app is not built into the Python service, and changes no hosting or deploy. The Python backend and `public/` app are untouched. Run commands are in `README.md`.

- **ADR License**: California State License Board (CSLB) **#950983**

### 2. Claims engine and live walkthrough

- The old engines (the Python Cloud Run `POST /api/audit` service and WebSocket Live relay, configured by `AUDIT_MODEL`, `OCR_MODEL` and `LIVE_MODEL`) belong to the retired old app. The rebuild's claims engine is TypeScript in `web/src/engine/` (`makeDocuments` in `documents.ts`). The real-time walkthrough relay is not built in `web/` yet (S7; see `docs/ARCHITECTURE.md`).
- Output is the 4-document claims hub:
  1. Official proposal, headed "[Company] · Official proposal" ("Proposal" tab; sheet-derived low–high estimate + e-signature).
  2. Itemized claim (ADR scope codes, not Xactimate codes) with waste factors.
  3. Formal IICRC S500 / S520 insurance claim defense letter.
  4. Photo Moisture Audit Log.
- Pricing and mandatory wording are server calculations, never model output.
- Bind audits and signatures to a saved revision and proposal hash. Pending/failed OCR is unverified; unpriced work blocks signing. Show the customer estimate range alongside the itemized base-rate calculation. Use ADR internal scope codes and JSON export without ESX compatibility claims.

### 4. California Regulatory & Compliance Rules

#### A. The 1978 Pre-Test Rule (Title 8 & EPA RRP)
- **If Year Built < 1978**:
  - The proposal **must** include the explicit notice: *(this does not include the pretest for lead/asbestos)*.
  - Findings must state: *"Due to property age ({yearBuilt}), California State Law requires third-party lead and asbestos testing prior to destructive demolition."*
- **If Year Built >= 1978**:
  - Findings state no pre-testing is required.

#### B. Standard ADR Scoping Disclaimers
Agents must preserve the exact standard estimate clauses in `web/src/engine/documents.ts` (checked by `web/tests/unit/estimate-documents.test.ts`), taken from ADR's real estimates: the pre-1978 testing paragraph, the IICRC/EPA protective-equipment and containment sentence, the additional-materials sentence, the reconstruction/collateral-damage/testing exclusions, insurance repricing and 30-day validity. Clauses that name the company use the issuing company's name. Crawl spaces, countertops and water heaters have no fixed wording or form flag; technicians describe them in notes or the walkthrough. Documents describe the work as proposed.

#### B. Cloud Run

#### C. Security & Credentials
- Do not commit Google Cloud service account keys or raw API keys into git.
- Cloud Run services use Google Cloud Application Default Credentials (ADC) with the per-environment runtime accounts defined in `infra/dryscope/` (`infra/dryscope/README.md`). Database rules do not constrain server SDK access through IAM.

#### D. Private Database
- The official records are in Cloud SQL Postgres with row-level security (project `dryscope`); drafts live in the named Firestore field database, whose browser access is limited to what `web/firestore.rules` allows. Evidence and signed records are written only server-side after identity, company membership and job-access checks.
- Field-database rules are released by the release workflow's deploy job (`docs/runbook/test-release.md`), not by hand. Read `docs/runbook/` and `infra/dryscope/README.md` before cloud changes. Never enable demo fallbacks in production.

### 6. Company workspaces

- For authorization, invitations, company documents, offline queues or workspace rollout, read `docs/ACCESS.md` and the stage plan in `docs/plans/` (`S3.md`) before changing the implementation or cloud state.
- Preserve company isolation on every business endpoint, evidence download and Live recheck. Superadmin privileges alone grant account management plus audited read-only support access to any company and its listed support actions; editing customer jobs requires an active company membership.
- Archiving is a soft, audited status change, never a delete: owners archive unsigned drafts (the source record stays, and its photos stay until the company's record-retention period for them has passed once that deletion is switched on; the job leaves lists and returns 410) and restore them from Archived drafts; superadmin support can archive or restore an unsigned draft in any company, suspended ones included, as an audited support action; and a superadmin archives a suspended company. Signed jobs cannot be archived. A phone holding unsynced work for an archived draft keeps it and offers Save as new draft or Discard.
- Keep signed source records and evidence paths immutable. Migration and mutable assignment/coordination use private sidecars. ADR's exact notices remain the ADR defaults; other California companies use their own identity and their own published prices.
