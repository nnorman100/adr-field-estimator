## Overview

```
Phone browser (static app, public/*.js, installable PWA, offline queue in IndexedDB)
   │  Firebase ID token                          ┌─► Vertex AI (Gemini Live relay, audit/OCR models)
   ▼                                             │
Firebase Hosting (alert-disaster) ── /api/** ──► Cloud Run: alert-disaster-field-estimator (Python, us-west2)
                                                 ├─► Firestore (default) — private, deny-all to browsers
                                                 ├─► Private evidence bucket (photos, signed evidence)
                                                 ├─► Secret Manager (Maps key, SMTP, etc.)
                                                 └─► Email (Gmail SMTP today; see docs/roadmap.md risks)
```

The diagram shows the current Python app, which lives in Google Cloud / Firebase project `alert-disaster-field-2026`; the rebuild's test environment is in project `dryscope` (see Environments). Peer sites and shared databases are never touched.

## Two engines

1. **Live walkthrough** — authenticated WebSocket relay; 16 kHz audio and a 640 px frame every 2 s; coaching and meter-photo reading.
2. **Claims engine** — `POST /api/audit`: transcript + photos + facts → four documents. The server applies prices and mandatory wording; the model drafts only.
   Models are set by `AUDIT_MODEL`, `OCR_MODEL`, `LIVE_MODEL`.

## Data model (high level)

- Signed agreements and evidence are **immutable**. Mutable coordination (assignment, claim details, delivery, readings) lives in **sidecars** beside the job.
- Private collections: `_companies`, `_memberships`, `_platform_admins`, `_invitations`, `_invite_keys`, `_admin_events` (also the support audit log), `_company_retention`, `_retention_state`, `_company_limits`, `_workspace_jobs`, `_workspace_authorizations`, plus others listed in `docs/company-workspaces.md`.
- Drafts autosave to a per-user IndexedDB queue and sync when online; conflicts return 409 and keep local work.

### S2 app skeleton (present, not deployed)
`web/` holds the new TypeScript app beside the current one: Next.js (App Router, TypeScript strict), Tailwind v4 (Safari 16.4+, the iOS baseline) with shadcn/ui, Zod at the sample `POST /api/echo` route, `GET /api/health`, a typed config module (`web/src/lib/config.ts`) checked once at server start by `web/src/instrumentation.ts`, so the server refuses to start with missing or invalid environment, Vitest unit tests and Playwright browser tests (a smoke test, the sign-in screens against the Auth emulator, the second-step screens, the operator screens, and the team screens) in Chromium and WebKit. Postgres schema changes are numbered SQL files in `web/migrations`, applied by `npm run db:migrate` and recorded in `migration_ledger`. The first file creates that ledger and an empty `companies` table (`id`, `created_at`); `0002_identity` adds the sign-in and company-separation tables (`docs/DATA.md`), which `GET /api/me` reads; `0003_runtime_role` adds the runtime role and forced row-level security on every table, and `withCompany` (`web/src/db/tenant.ts`) is the only way the runtime sees a company's rows; `0004_sign_in_lookup` adds `sign_in_company(tenant)`, the one lookup before a company is known. `0005_access_projection` adds the outbox worker's one lookup across companies and an index for one actor's outbox rows, `0006_platform_operator` the platform operator's sign-in lookup and its cross-company rights inside `withOperator`, `0007_sign_in_address` the company sign-in page's lookup by address, and `0008_feature_flag_writes` the operator's write path on `company_feature_flags`, `0009_price_tables` the company price tables (`price_table_versions`, `price_table_working_copies`; S4-5, read and written by the Prices API, S4-6, `web/src/lib/prices/`, routes in `docs/ACCESS.md`), and `0010_core_job_tables` the job header, customer, claim and evidence registry tables plus the company profile columns (`jobs`, `job_customers`, `job_claims`, `evidence_objects`; S5a-2), and `0011_submissions_agreements` the submission, price pin, estimate and agreement tables with the worker's lookup across companies (`job_submissions`, `job_price_pins`, `job_estimates`, `agreements`, `job_submission_due_companies`; S5a-7; the submission routes and the estimate routes, S5a-8 and S5a-9, `web/src/lib/estimates/`, use them, and `docs/ACCESS.md` "Estimate and review" owns their rules), and `0012_ai_live_tables` every AI and Live table of stage S7 with the sweeper's lookup across companies (`company_ai_settings`, `ai_ledger`, `ai_results`, `live_sessions`, `live_usage`, `live_turns`, `voice_notes`, `member_voice_settings`, `live_session_due_companies`; S7-3, Drizzle view `web/src/db/ai-schema.ts`, code default ceilings `web/src/lib/ai/ceilings.ts`, no route uses them yet), and `0013_company_documents` the letterhead lines and the document settings on `companies` (S5a-4b: five one-line columns and `profile_documents`, a `jsonb` object under 64 KiB whose shape the Zod schema in `web/src/lib/profile/settings.ts` checks at write and read; the column grant and 0010's trigger split cover them) (`docs/DATA.md`). The jobs routes (S5a-3, `web/src/lib/jobs/`, `docs/ACCESS.md` "Jobs routes") create a job from a job id and a first draft id made on the phone (the Postgres row first, then its Firestore field draft; a retry makes whichever is missing), list the company's or the caller's own jobs, read a job, and save its customer, property address and claim with a revision and a change id so a retry after a lost response is no conflict; every job route goes through one job-access function. The photo routes (S5a-5, `web/src/lib/photos/`, `docs/ACCESS.md` "Photo routes") take a photo or its full-size original as a raw image through the app server, store it in the evidence bucket (`EVIDENCE_BUCKET`) create-only and register it once with its SHA-256, refuse a new photo once the field draft is no longer being edited, and stream it back to anyone who may see the job with `no-store`; the bucket is a seam, replaced by a fake in CI. The company profile routes and the Company settings screen (S5a-4, `web/src/lib/profile/`, `/sign-in/{address}/company`; `docs/ACCESS.md` "Company profile API") let the owner read and save the address, phone, email, licence and sign-off the documents print, on the company's own row (no new migration), and since S5a-4b the letterhead lines and the document settings (migration 0013; a save that leaves those out keeps them); a save names the revision it was based on, and the engine's setup check (`web/src/engine/company-setup.ts`) lists what is still missing. The AI spend ledger (S7-4, `web/src/lib/ai/budget.ts`) is the AI boundary's budget and quota store over migration 0012's `ai_ledger` and `company_ai_settings`: each company's reservations run one at a time under a transaction-scoped advisory lock, so parallel calls cannot pass the company's daily or monthly ceiling ($10 and $200 by default, V5 B) or a person's daily quota for a feature; settlement is once per call id, and a hold is released only by a settlement with a known cost. The owner reads the AI used today and this month on Company settings (`GET /api/companies/{id}/ai-usage`, key `ai_usage_read`), and only the platform operator sets a company's ceilings (`PUT /api/platform/companies/{companyId}/ai-settings`, one audit row). On Cloud Run the app reaches Cloud SQL over the `/cloudsql` socket as its own IAM database user (`SQL_CONNECTION_NAME`, `SQL_DATABASE_NAME`, `SQL_IAM_USER` from Terraform), with a metadata-server access token as the password (`web/src/db/client.ts`); the release migrator (the Cloud Run job `dryscope-migrate-<env>`, `web/src/db/job.ts`) logs in the same way as `dryscope-migrate-<env>`; local work uses `DATABASE_URL`. Request identity (`web/src/lib/auth/`, S3-7) checks a Firebase ID token with firebase-admin on the project (signature, audience, issuer and expiry; the tenant it reads is signed), finds the company from that tenant, checks the token again with the revocation check on that tenant's client, requires a verified email, and loads the actor and active membership of an active company inside `withCompany`; a company id in the URL, a header or the body is never read. The company's feature flags (`web/src/lib/flags/`, S3-11a; a fixed list, all off unless stored on) are read in the same transaction and decide the price capabilities; `requireFlag` answers 404 for a switched-off feature. Only the platform operator changes a flag, through `POST /api/platform/companies/{companyId}/flags` (S3-11b, `0008_feature_flag_writes`; no company role can, an owner included); it writes the flag and one audit row together and refuses an unknown flag name. Every route handler is wrapped in an access rule (`publicRoute`, `memberRoute`, `accountRoute`, `requireFlag`, `operatorRoute` for the platform operator routes under `/api/platform/` (S3-9, `web/src/lib/platform/`), or `serviceRoute` for internal job routes only the scheduler service account may call), and `web/tests/unit/route-rules.test.ts` finds every route file and fails on one that is not. `GET /api/me` returns the signed-in member's company, role and capabilities. Second-step and session rules (`web/src/lib/auth/policy.ts`, S3-8) run inside that same check: an owner (and later the platform operator) must have signed in with an authenticator app (`firebase.sign_in_second_factor` is `totp`; a text message does not count, and the accepted list is fixed in code with no setting), or is refused with `second_step_required` on every route except one that declares itself the enrolment route (`memberRoute(handler, { secondStep: 'enrolment' })`); since 2026-11-14 (D-030) office staff must too, and estimators may opt in. A sign-in (`auth_time`) older than the role allows, operator 12 hours, owner and office 14 days, estimator 30 days, is refused with `sign_in_again`, as is one older than 15 minutes on a route that declares `{ freshSignIn: true }` (team and second-step changes, and the operator's company status, tenant binding, feature flag and AI ceiling changes, D-030). The team and invitation routes (S3-10, `web/src/lib/team/`) declare `{ freshSignIn: true }` on every team change; nothing calls the enrolment option yet. Under `/api/companies/{companyId}/` the owner lists the team (an office user gets only active estimators), invites (estimator or office, 7 days, a link to copy: no email service is set up), resends, cancels and clears invitations, switches a member between estimator and office, and disables (revoking their sessions before answering) or re-enables a member; the owner membership cannot be changed there, and a path company that is not the caller's own answers 404. `accountRoute` admits a verified account of the company that is not yet a member, for `GET /api/invitations/{id}` and `POST /api/invitations/{id}/accept`: an invitation for another email reads as not found, and accepting creates the actor and one membership once, under the session rules of the role accepted. Inviting makes a password-less, unverified account for the email in the company's tenant (firebase-admin, the narrow `dryscopeIdentity<Env>` role). Every change writes an audit row and every membership change an `access_projection_outbox` row in its transaction. A throwaway Postgres runs those files from empty in `.github/workflows/web.yml`. An emulator harness (`npm run test:emu`, `web/firebase.json`, `web/tests/emu/`) runs the Firebase Auth and Firestore emulators in that workflow under a `demo-` project id only and refuses any other; it checks that a token carries its tenant and records that the Auth emulator refuses authenticator-app (TOTP) enrolment, so TOTP is proved only against a real test environment. The field database rules (`web/firestore.rules`, loaded by that emulator) deny by default and allow only a draft and its `rooms` and `photos` documents under `companies/{companyId}/drafts/...`, when the token's sign-in tenant is the company's and the caller holds an unexpired server-written access record: the company's owner and office read every draft and an estimator only their own, and only the draft's field owner changes its `field` data (and deletes a room document, S5a-6), while the draft is `editing`, with each key's type and size checked against field map v1 (`web/src/lib/field/`, S5a-1; `docs/DATA.md`). `web/tests/emu/rules/` checks them with two tenants. The server writes the access records through the outbox in `web/src/lib/projection/` (see `docs/DATA.md`): each team change projects its member after it commits, and `POST /api/internal/access-projection` (scheduler service account only) runs the pass across companies; the test release workflow releases the rules to `dryscope-field-test` (live stays owner-run; `docs/runbook/test-release.md`). It has its own `package.json`, ESLint config (`max-lines` 1,000) and CI workflow (time-limited jobs). It also holds the S4 pricing engine in `web/src/engine/` (a TypeScript calculator, clauses and canonical bytes, with the `PriceTableV3` Zod schema in `table.ts`; its stable entry `priceEstimate` and publish check `checkTable` in `estimate.ts` are checked by hand-worked examples, exact clause text and property tests in `web/tests/unit/estimate-*.test.ts`); the Prices API calls it for the publish check and preview, and the estimate routes (`web/src/lib/estimates/`, S5a-9) price a job's submitted record with it. The company roles and capability table are ported to `web/src/lib/access/` (deny by default; `prices_read` and `prices_manage` exist only when the price-books flag is passed in as on) and checked against `docs/ACCESS.md`. The company sign-in screens (S3-13a, `web/src/app/(auth)/sign-in/[address]/`) sign in in the browser with the Firebase JS SDK (`web/src/lib/firebase-client.ts`) to the tenant of the company named by the sign-in address, one Firebase app instance per tenant so each company's saved sign-in stays apart, and decide what to show from `GET /api/me`; the company's name and tenant come from the public `GET /api/sign-in/{address}` (`web/src/lib/sign-in/`), which the database answers through `sign_in_company_page` (`0007_sign_in_address`, S3-13b; `docs/DATA.md`) and answers 404 for an unknown, inactive, tenant-less or malformed address. The second-step screens (S3-14, `web/src/app/(auth)/second-step/`, the Firebase calls in the same `firebase-client.ts`) are states of that page: a person whose role needs the authenticator-app second step and has none sees only its setup (a QR code drawn in the browser by `qrcode-generator`, the same key to type, a code from the app to prove it), with no way on to the app; a password or Google sign-in of an enrolled person asks for the app's code before any session exists; a signed-in person can add another authenticator app; and the setup screen says the second step was reset when this phone remembers one that is gone (a marker held only on the phone). The Auth emulator cannot do authenticator-app enrolment, so their browser tests answer Identity Platform's second-step calls at the network boundary (`web/tests/e2e/second-step/fake-totp.ts`), and the real flow is proved on a `test` tenant in S3-18. The platform operator screens (S3-15, `web/src/app/operator/[tenantId]/`, calls in `web/src/lib/operator/`) sit at `/operator/{operator tenant id}`, sign in to that tenant and call only the `/api/platform/` routes: Companies (list, create), Company administration (status, owner, second-step reset) and a read-only team view, with no screen for customer data; who may open them and what they leave out are in `docs/ACCESS.md` and `docs/plans/S3.md`. The owner's team and invitation screens (S3-16) are "Team and invitations" at `/sign-in/{address}/team` (invite by email and role and copy the link, resend, cancel and clear invitations, switch a member between estimator and office, turn a member off and on; the screen asks the server who is signed in and requests the team only for a role holding `team_manage`, and the server refuses everyone else again) and "Accept invitation" on the invitation link, which shows the invitation only to the account it is addressed to and, when the server refuses an owner or office invitation for a missing second step, shows the authenticator-app setup and then tries again (or asks for a sign-in with the app's code). Against the Auth emulator the team records and the owner's second step are stood in for by the same `LOCAL_SIGN_IN_FIXTURE` file (`web/src/lib/team/local-team.ts`), as the emulator cannot do the second step. Its one other product screen is the field shell `/field` (S6-2, `web/src/app/field/`): prerendered and data-free, it starts in the browser from the `ds-me` row the sign-in page saves, shows the job screens (S5a-6, `web/src/app/field/field-app.tsx`, `web/src/lib/field/`: Jobs, New job, Check Scope, Customer and claim, Photos, each a view of `/field` chosen by the address's query, read in the browser after sign-in; `docs/plans/S5.md`), opens with no signal through the worker `web/sw/sw.js` (built to `/sw.js` after `next build` by `web/scripts/build-sw.ts`, and checked against the files the page loads), and shows the "No signal", "Not saved on this phone" and Home Screen install notices (`docs/plans/S6.md`). `web/src/proxy.ts` refuses every `/api` route outside a four-route public list (health, the echo sample, that sign-in lookup and the browser error reports, `POST /api/client-errors`, TC-2) with 401 when signed out, and passes `/api/me`, the team and invitation routes and the Prices routes (`memberApiPaths` in `web/src/lib/public-api.ts`, one uuid per `:id` segment) on to their own sign-in check, and the internal job routes (`serviceApiPaths`) on to their own service-token check. `web/scripts/build-image.sh` assembles the standalone production image without a Docker daemon (crane appends one root-owned `/app` layer onto the Node base pinned in `web/Dockerfile`; the app runs as the unprivileged `node` user, with its commit and release version baked in and reported by `/api/health`, which answers 503 when a configured database refuses the service's login). `.github/workflows/web-release.yml` releases it to the **test** environment in project `dryscope` only, keylessly: image by digest, migrations as the migrator before traffic, a 0% tagged revision smoke-checked by `web/scripts/smoke-release.ts`, then all traffic, with rollback, then a release record: a `YYYY.MM.DD-N` tag and a pre-release GitHub Release carrying `manifest.json` and the rollback command, or one failed-release line in Cloud Logging (`docs/runbook/test-release.md`). It skips until the owner's setup is done. `live-relay-placeholder/` is a 503 stand-in image the app root needs for the Live service until S7. The app is not built into the Python service, and changes no hosting or deploy. The Python backend and `public/` app are untouched. Run commands are in `README.md`.

### Browser security headers (F7)
Every `web/` page and API answer carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=31536000` (this host only: no subdomains, no preload), and an enforced `Content-Security-Policy` of exactly `frame-ancestors 'none'; object-src 'none'; base-uri 'self'`. Nothing in it names a source Google serves, so it cannot break sign-in. One exception: the photo download (`/api/jobs/{jobId}/photos/{photoId}`, photo and original) gets no app-wide policy and keeps its own stricter `default-src 'none'; sandbox`, because Next drops a route's own header when the configuration already set one of that name; it still gets the other four headers. Follow-up: a full script/connect CSP (what the app loads: this site, Identity Platform, Firestore, App Check, reCAPTCHA), proved first on a test-environment phone run with Google sign-in, the authenticator-app step and offline reconnect. Code: `web/src/lib/security-headers.ts`, `web/next.config.ts`; tests: `web/tests/unit/security-headers.test.ts`, `web/tests/db/photos-api.test.ts`, `web/tests/e2e/security-headers.spec.ts`.

### App Check, monitor mode (TC-5)
The browser starts App Check (reCAPTCHA Enterprise provider, automatic refresh) on each company's Firebase app instance before its Auth is used, only when the server gives it both `FIREBASE_APP_ID` and `APP_CHECK_SITE_KEY` (public values; either missing or empty means App Check is off and the app behaves as before). Each attestation is cut off after 3 seconds, because Firebase Auth waits for an App Check token before every sign-in request and the SDK's reCAPTCHA loader has no time limit; the SDK then lets Auth go ahead and retries later. Every `/api` call adds `X-Firebase-AppCheck` when a token comes within 3 seconds, and otherwise goes without it (and does not wait again while that request is still running). The debug token (`self.FIREBASE_APPCHECK_DEBUG_TOKEN`) is honoured on `localhost` and `127.0.0.1` only. The sign-in screens show Google's "This site is protected by reCAPTCHA." line and the badge is hidden. On the server, `APP_CHECK_MODE` is `monitor` (default) or `off`; `enforce` stops the server at start-up until TC-13. In monitor mode every browser-facing route wrapper (not `serviceRoute`) checks the token with the Admin SDK (2-second limit, no replay protection) and writes one `App Check` line: `outcome` (`valid`, `missing`, `invalid`, `unverified`), `method`, `route` (the pattern, ids replaced by parameter names) and `status`. It never refuses a call or changes its answer. The field database's per-person app instances (`field-db.ts`) start App Check the same way before their Auth and Firestore are used, keeping each person's cache apart; the sync-gate token step and its offline tests are TC-7. Terraform sets `APP_CHECK_MODE=monitor` on both services through the app root's `common_env`, and `FIREBASE_APP_ID` and `APP_CHECK_SITE_KEY` only once both are passed (`firebase_app_id`, `app_check_site_key`; empty by default, so App Check stays off until TC-11's apply passes them). Code: `web/src/lib/app-check-client.ts`, `web/src/lib/app-check.ts`, `web/src/lib/auth/route.ts`; tests: `web/tests/unit/app-check*.test.ts`, `web/tests/e2e/app-check.spec.ts`.

### 4. California Regulatory & Compliance Rules

#### A. The 1978 Pre-Test Rule (Title 8 & EPA RRP)
- **If Year Built < 1978**:
  - The proposal **must** include the explicit notice: *(this does not include the pretest for lead/asbestos)*.
  - Findings must state: *"Due to property age ({yearBuilt}), California State Law requires third-party lead and asbestos testing prior to destructive demolition."*
- **If Year Built >= 1978**:
  - Findings state no pre-testing is required.

#### B. Standard ADR Scoping Disclaimers
Agents must preserve the exact standard estimate clauses in `web/src/engine/documents.ts` (checked by `web/tests/unit/estimate-documents.test.ts`), taken from ADR's real estimates: the pre-1978 testing paragraph, the IICRC/EPA protective-equipment and containment sentence, the additional-materials sentence, the reconstruction/collateral-damage/testing exclusions, insurance repricing and 30-day validity. Clauses that name the company use the issuing company's name. Crawl spaces, countertops and water heaters have no fixed wording or form flag; technicians describe them in notes or the walkthrough. Documents describe the work as proposed.

#### C. Wording held for lawyer review
The owner takes these questions to a lawyer. Until the owner records an answer, the text in A and B above and in `web/src/engine/documents.ts` stays exactly as it is, and DryScope ships no wording of its own for items 3 and 4 (a company may enter its own in its start-work authorization text, `docs/plans/S5.md` S5a-11). Added 2026-11-13 from a review of a restoration company's real estimates (`docs/plans/S5.md`, section 12).
1. **Pre-1978 Findings sentence (W1).** The reviewed estimates print "The home was built in {year}. Before any disturbance to building materials, lead and asbestos testing must be conducted prior to the start of work." instead of the mandated sentence in A. Does either satisfy the rule, and which should DryScope print? Only the owner changes A.
2. **Licence label (W4).** The engine prints "CSLB #{licence}"; company letterheads also use "CA License #{licence}". Which label is required or allowed on a proposal and a signed agreement?
3. **California right to cancel.** A customer who signs at home, on the technician's phone or through a signing link, may be signing a home solicitation or home improvement contract with a right to cancel (three business days, longer for senior citizens and for repairs after a declared disaster): Civil Code §1689.6 and §1689.7, Business and Professions Code §7159. Bills in the 2025–26 session (SB 784, AB 1327) change these periods, so the lawyer checks current law. Questions: does the notice apply to mitigation and remediation work, what text and form, where on the signed page, and does a remote link signing change it.
4. **Emergency-repair waiver.** Civil Code §1689.13 lifts the right to cancel for emergency or immediately necessary repairs when the buyer (or the buyer's agent or insurance representative) started the contract and the buyer gives a separate dated, signed statement that describes the emergency and waives the right. Questions: the waiver wording, whether a signature on a phone or a link satisfies it, and whether work may start before the cancellation period ends.
5. Also with the lawyer, listed in `docs/plans/S7.md` (owner step J): the terms lines on AI processing, the AI notice wording (V11) and any future recording (V8 B).
