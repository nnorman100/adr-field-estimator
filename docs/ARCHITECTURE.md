## Overview

```
Phone browser (static app, public/*.js, installable PWA, offline queue in IndexedDB)
   │  Firebase ID token                          ┌─► Vertex AI (Gemini Live relay, audit/OCR models)
   ▼                                             │
Firebase Hosting (alert-disaster) ── /api/** ──► Cloud Run: alert-disaster-field-estimator (Python, us-west2)
                                                 ├─► Firestore (default) — private, deny-all to browsers
                                                 ├─► Private evidence bucket (photos, signed evidence)
                                                 ├─► Secret Manager (Maps key, SMTP, etc.)
                                                 └─► Email (Gmail SMTP today; see docs/roadmap.md risks)
```

The diagram shows the current Python app, which lives in Google Cloud / Firebase project `alert-disaster-field-2026`; the rebuild is in project `dryscope` (see Environments). Peer sites and shared databases are never touched.

## Two engines

1. **Live walkthrough** — authenticated WebSocket relay; 16 kHz audio and a 640 px frame every 2 s; coaching and meter-photo reading.
2. **Claims engine** — `POST /api/audit`: transcript + photos + facts → four documents. The server applies prices and mandatory wording; the model drafts only.
   Models are set by `AUDIT_MODEL`, `OCR_MODEL`, `LIVE_MODEL`.

## Data model (high level)

- Signed agreements and evidence are **immutable**. Mutable coordination (assignment, claim details, delivery, readings) lives in **sidecars** beside the job.
- Private collections: `_companies`, `_memberships`, `_platform_admins`, `_invitations`, `_invite_keys`, `_admin_events` (also the support audit log), `_company_retention`, `_retention_state`, `_company_limits`, `_workspace_jobs`, `_workspace_authorizations`, plus others listed in `docs/company-workspaces.md`.
- Drafts autosave to a per-user IndexedDB queue and sync when online; conflicts return 409 and keep local work.

### S2 app skeleton (present, not deployed)
`web/` holds the new TypeScript app beside the current one: Next.js (App Router, TypeScript strict), Tailwind v4 (Safari 16.4+, the iOS baseline) with shadcn/ui, Zod at the sample `POST /api/echo` route, `GET /api/health`, a typed config module (`web/src/lib/config.ts`) checked once at server start by `web/src/instrumentation.ts`, so the server refuses to start with missing or invalid environment, Vitest unit tests and a Playwright smoke test in Chromium and WebKit. Postgres schema changes are numbered SQL files in `web/migrations`, applied by `npm run db:migrate` and recorded in `migration_ledger`. The first file creates that ledger and an empty `companies` table (`id`, `created_at`); `0002_identity` adds the sign-in and company-separation tables (`docs/DATA.md`), which `GET /api/me` reads; `0003_runtime_role` adds the runtime role and forced row-level security on every table, and `withCompany` (`web/src/db/tenant.ts`) is the only way the runtime sees a company's rows; `0004_sign_in_lookup` adds `sign_in_company(tenant)`, the one lookup before a company is known. On Cloud Run the app reaches Cloud SQL over the `/cloudsql` socket as its own IAM database user (`SQL_CONNECTION_NAME`, `SQL_DATABASE_NAME`, `SQL_IAM_USER` from Terraform), with a metadata-server access token as the password (`web/src/db/client.ts`); the release migrator (the Cloud Run job `dryscope-migrate-<env>`, `web/src/db/job.ts`) logs in the same way as `dryscope-migrate-<env>`; local work uses `DATABASE_URL`. Request identity (`web/src/lib/auth/`, S3-7) checks a Firebase ID token with firebase-admin on the project (signature, audience, issuer and expiry; the tenant it reads is signed), finds the company from that tenant, checks the token again with the revocation check on that tenant's client, requires a verified email, and loads the actor and active membership of an active company inside `withCompany`; a company id in the URL, a header or the body is never read. Every route handler is wrapped in an access rule (`publicRoute` or `memberRoute`), and `web/tests/unit/route-rules.test.ts` finds every route file and fails on one that is not. `GET /api/me` returns the signed-in member's company, role and capabilities. Second-step and session rules (`web/src/lib/auth/policy.ts`, S3-8) run inside that same check: an owner (and later the platform operator) must have signed in with an authenticator app (`firebase.sign_in_second_factor` is `totp`; a text message does not count, and the accepted list is fixed in code with no setting), or is refused with `second_step_required` on every route except one that declares itself the enrolment route (`memberRoute(handler, { secondStep: 'enrolment' })`); office staff and estimators may opt in. A sign-in (`auth_time`) older than the role allows, operator 12 hours, owner and office 14 days, estimator 30 days, is refused with `sign_in_again`, as is one older than 15 minutes on a route that declares `{ freshSignIn: true }` (team and second-step changes). Nothing calls those two route options yet. A throwaway Postgres runs those files from empty in `.github/workflows/web.yml`. An emulator harness (`npm run test:emu`, `web/firebase.json`, `web/tests/emu/`) runs the Firebase Auth and Firestore emulators in that workflow under a `demo-` project id only and refuses any other; it checks that a token carries its tenant and records that the Auth emulator refuses authenticator-app (TOTP) enrolment, so TOTP is proved only against a real test environment. The field database rules (`web/firestore.rules`, loaded by that emulator) deny by default and allow only `companies/{companyId}/drafts/...`, when the token's sign-in tenant is the company's and the caller holds an unexpired server-written access record: the company's owner and office read every draft and an estimator only their own, and only the draft's field owner changes its `field` data, while the draft is `editing`. `web/tests/emu/rules/` checks them with two tenants. Nothing writes the access records yet, and the rules are not deployed. It has its own `package.json`, ESLint config (`max-lines` 1,000) and CI workflow (time-limited jobs). It also holds the S4 pricing engine in `web/src/engine/` (a port of the Python calculator, clauses and canonical bytes, proved against `tests/fixtures/pricing-oracle/`, see its README); nothing calls it yet. The company roles and capability table are ported to `web/src/lib/access/` (deny by default; `prices_read` and `prices_manage` exist only when the price-books flag is passed in as on) and checked against `docs/ACCESS.md`. It has no product screens or sign-in screens. `web/src/proxy.ts` refuses every `/api` route outside a two-route public list (health and the echo sample) with 401 when signed out, and passes `/api/me` on to its own sign-in check. `web/scripts/build-image.sh` assembles the standalone production image without a Docker daemon (crane appends one root-owned `/app` layer onto the Node base pinned in `web/Dockerfile`; the app runs as the unprivileged `node` user, with its commit baked in and reported by `/api/health`, which answers 503 when a configured database refuses the service's login). `.github/workflows/web-release.yml` releases it to the **test** environment in project `dryscope` only, keylessly: image by digest, migrations as the migrator before traffic, a 0% tagged revision smoke-checked by `web/scripts/smoke-release.ts`, then all traffic, with rollback (`docs/runbook/test-release.md`). It skips until the owner's setup is done. `live-relay-placeholder/` is a 503 stand-in image the app root needs for the Live service until S7. The app is not built into the Python service, and changes no hosting or deploy. The Python backend and `public/` app are untouched. Run commands are in `README.md`.

## Environments

The current Python app runs in `alert-disaster-field-2026`, where releases are staged on a tagged Cloud Run revision at 0% traffic, checked, then promoted, then Hosting is deployed (`docs/runbook/releases.md`). The TypeScript rebuild is a clean start in dedicated Google Cloud project `dryscope` (project number `570228742694`), with separate `test` and `live` resources in `us-central1` defined in `infra/dryscope/` (Cloud SQL tiers per environment: `infra/dryscope/README.md`); `alert-disaster-field-2026` stays running unchanged until the rebuilt app is live.
