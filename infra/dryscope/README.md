# DryScope Terraform

Infrastructure for the rebuilt DryScope in dedicated project `dryscope` (project number `570228742694`), region `us-central1`. Written and checked offline. **Nothing here has been applied.** The owner reviews and applies it (steps in [docs/runbook/terraform-apply.md](../../docs/runbook/terraform-apply.md)).

```
infra/dryscope/
  modules/naming   one place for every name, account and secret-to-service rule
  data/            Cloud SQL, named Firestore database, evidence bucket, secrets,
                   image repository, runtime and deploy accounts and their grants, sign-in
                   APIs, the unbound sign-in user role, the Model Armor text template and
                   sanitize grants, the stage TC bundle (APIs, the web app's trace writing,
                   container scanning, the App Check reCAPTCHA key and registration, the
                   35-day backup window), and (test only for now) the scheduler account, the
                   field rules release role, the project's Model Armor floor setting, the AI
                   evaluation account, the deploy account's log writing and the synthetic
                   monitor's account and password secret
  app/             Cloud Run (web app, Live relay, migration job), (test only for now) the Cloud
                   Scheduler job that calls the internal access-projection route, alerts, uptime
                   check, budget stub
  scripts/check.sh offline checks (format, validate, mocked tests)
```

Each root has `envs/test.tfvars`, `envs/live.tfvars` and a matching `envs/backend-<env>.hcl` (bucket `dryscope-tfstate`), so test and live never share state. Apply `data` before `app`; the app root derives data names from the shared naming module and does not read the data root's state. Test uses the shared-core `db-f1-micro` Cloud SQL tier (`ENTERPRISE` edition, zonal, 10 GB SSD — about $10/month; no uptime guarantee, fine for test), while live keeps the dedicated `db-custom-1-3840` tier (1 vCPU, 3.75 GiB, `ENTERPRISE` edition, zonal, 20 GB SSD).

## What it will not do

- Touch the legacy `alert-disaster-field-2026` project or anything in `us-west2`: the legacy Cloud Run service, the `(default)` Firestore database, the old `alert-disaster-field-2026-evidence` bucket, or `adr-runtime` and `adr-builder`. The legacy app keeps serving unchanged until cutover; these roots refuse any project other than `dryscope` and any region other than `us-central1` at plan time.
- Destroy anything through Terraform. Cloud SQL, the Firestore database, the bucket, secrets, the image repository, the Cloud Run services and the migration job all set `prevent_destroy`, and SQL databases, SQL users and Firestore set `deletion_policy = "ABANDON"`. There is no variable to switch protection off. Only Cloud SQL (`deletion_protection_enabled`) and Firestore (`delete_protection_state`) also carry Google-side protection; Cloud Run's `deletion_protection` and every `prevent_destroy` stop Terraform only, not a direct API delete. Against that, no account created here can delete a Cloud Run service, revision, job or execution: the deploy account holds the custom role `dryscopeDeploy<Env>` (Cloud Run reads plus `run.services.update`, no delete) instead of `roles/run.developer`, and on the migration job only `dryscopeMigrateJob<Env>` (`run.jobs.get`, `run.operations.get`, `run.executions.get`, `run.executions.list`, `run.tasks.get` and `run.tasks.list` to read the job, its operations, executions and tasks; `run.jobs.update` and `run.jobs.run`; no create, delete, run with overrides or cancel), the evidence roles carry no object delete, and `dryscopeRulesReleaseTest` deletes no ruleset or release.
- Hold a secret. Secrets are created empty, by name. No password user exists; the database is reached with IAM database authentication.
- Replace existing IAM. Only `*_iam_member` resources, from a short list of roles; the only grants an apply removes or replaces are the four named in the plan check's table for re-applying test (see Checks). The Firestore grant is conditioned on the environment's database or a name under it (its documents), with a trailing slash so neither the other environment's database nor a sibling matches.

## Checks

```
TERRAFORM=/path/to/terraform infra/dryscope/scripts/check.sh      # format, validate, mocked tests, plan check
npx vitest run tests/test_terraform_plan_check.js                  # the plan check itself, on fixtures
```

`terraform test` runs with mock providers, mostly `command = plan` and, for the destroy-guard check only, a mocked apply; it needs no credentials. The suites in `data/tests` and `app/tests` assert region, environment-scoped names, protection settings, IAM-only database users, the reviewed role on every grant, the deploy role's lack of delete permissions, invocation-only public access, and that the legacy project, region, accounts, database, bucket and service are refused or never managed. `scripts/check-plan.js` reads the whole mocked plan of each root and environment and requires every resource (its project and name), every IAM grant (role, member and exact condition) and every protection setting to match a fixed table, so a grant nobody listed, a resource pointed at another environment, a wider condition, a shared-core tier in live (or the wrong tier for the environment) or a delete or replacement fails even though no test names it. The only deletes and replacements it accepts are named in its table for re-applying test over the first grants: removing the Live relay's three data grants and moving the web app's Firestore grant to the current condition (`docs/runbook/terraform-apply.md`). The only in-place updates it accepts are three: adding or setting `ALLOWED_ORIGINS` and the AI settings on an already-applied Cloud Run service, to the table's values for the environment (with, on the relay, its request concurrency moving to the table's value: 20 in test, 10 in live, and on the web app, its maximum instances moving to the value the database connection budget fits: 1 in test, 7 in live, S8-2); moving an already-applied Cloud SQL instance's backups from a regional location to the US multi-region (`us`); and stage TC's settings added to the already-applied evidence bucket (its lifecycle rule and soft delete) and image repository (its scanning setting), each with every other attribute unchanged; the table also requires those values on every plan, and requires backup location `us` on the instance. The stage TC part of the table is in `scripts/check-plan-tc.js`: it requires the 35-day backup window (D-023: one lifecycle rule deleting noncurrent versions after 28 days, 7 days of soft delete, at most 30 Cloud SQL backups, a daily Firestore backup kept 14 days), the reCAPTCHA key's score-only, one-host settings, and accepts keyless sign-in by numeric repository id only (D-024). The owner runs the same script on the saved plan before an apply (`docs/runbook/terraform-apply.md`). Against existing state the provider returns an IAM member's bucket, secret and repository as full paths (`b/<name>`, `projects/dryscope/secrets/<name>`, `projects/dryscope/locations/us-central1/repositories/<name>`); the script accepts those forms only when they resolve to exactly the expected name in project `dryscope`, and refuses any other project, location or name. `prevent_destroy` is not in plan JSON, so `scripts/check-guards.js` reads the root's `.tf` files and requires `lifecycle { prevent_destroy = true }` on every protected resource (SQL instance, Firestore database, bucket, repository, the four secrets and the test synthetic monitor's password secret, the Model Armor text template and floor setting, the App Check reCAPTCHA key, both Cloud Run services and the migration job); a guard that is removed, false, commented out or in a nested block fails. This does not depend on the Terraform version. `guards/guards.tftest.hcl` also applies each root against the mock provider, and the check requires that run to pass; where Terraform prints its own teardown refusal ("Instance cannot be destroyed", seen on 1.12) it must name every protected resource too. Terraform 1.17 prints no such refusal, which is why the configuration is read directly. **Supported Terraform:** 1.9 up to (not including) 2.0, as `required_version` says; the destroy-guard check was proven to fail on each removed guard and to pass with all present on 1.12.2 and 1.17.1. The same file also plans a different image digest after the mocked create and requires the planned image of both services and the migration job to stay put, which covers the `ignore_changes` that leaves releases to `gcloud`. Removing or falsifying a guard, or that `ignore_changes`, fails `check.sh`; the refusal of every delete action in the plan check stands behind both. The check script never plans against, applies to, or imports from the real project. CI does not run `check.sh` yet: adding Terraform to a workflow is a protected-path change for the owner.

**Settings contract.** `web/src/lib/settings-contract.ts` is the one list of runtime settings the app reads and Terraform sets, per service (`api`, `live`, `migrate`). `web/tests/unit/settings-contract.test.ts` reads the env names Terraform plans for every Cloud Run service and job in the committed mocked plans (`fixtures/app-<env>.plan.json`, Secret Manager references included) and fails when Terraform sets a name the list does not give that service, leaves one out, sets a developer-machine setting, or plans a container for a service the list lacks; it also fails when `web/src/lib/config.ts` reads a name the list does not mark as read by the web app, or the list marks one it does not read. `scripts/check.sh` fails when a fresh export of the app plan differs from the committed fixture, so regenerate it (`node scripts/check-plan.js export`) with any Terraform change. Rename or add a setting in the list, `web/src/lib/config.ts` and the Terraform in the same change.

## Accepted risks

- **The deploy account is as powerful as the runtime it deploys.** It may act as the web app and relay accounts and update their services, and act as the migrator and set the migration job's image and run it, so any code it ships runs with that environment's data and secrets, and image code it puts in the job runs with the migrator's database rights (Cloud Run requires `iam.serviceAccounts.actAs` to update a job that runs as another account). GitHub environment protection, the principal set's repository scope and a separate workload identity pool per environment (`dryscope-test`, `dryscope-live`; the variable refuses any other pool) are the real controls; it must never be given `iam.roles.update` on its own custom role. The same repository-scoped principal set may also act as the migrator directly (`migrate_workload_identity`); the release no longer uses that binding, and removing it is an owner decision. The deploy account itself holds no database role; it reaches the database only through the migration job, which runs the release's own image (by digest) with `node migrate.mjs`.
- **The web app and migrator can delete rows and documents in their own environment** (`roles/datastore.user` for the web app, SQL grants for both). Point-in-time recovery on both stores is the backstop. The Live relay holds neither: no Cloud SQL connect or login and no Firestore role until a named need. Its Cloud SQL IAM user exists but cannot connect without those roles.
- **Evidence "no overwrite" is enforced by the upload code, not only the role.** The web app's `roles/storage.objectCreator` carries no delete, but the bucket keeps object versions, so the rule must not rest on how the role is evaluated against an existing name. Every evidence upload must create with a does-not-exist precondition (`ifGenerationMatch=0`) and treat `412 Precondition Failed` as a refused write ([runbook](../../docs/runbook/terraform-apply.md)).
- **The sign-in user role is bound per tenant, by hand.** `dryscopeIdentity<Env>` holds `firebaseauth.users.get`, `create`, `update` and `sendEmail` only (no delete, no `configs.*`, no `tenants.*`), and Terraform binds it nowhere: while live shares project `dryscope` with test (until the separate live project `dryscope-live` of the S8 plan exists) they share Identity Platform, and a project binding would let the test web app change live users; in its own project, live has its own Identity Platform and the binding stays per tenant. The owner binds it on each of the environment's own tenants ([runbook](../../docs/runbook/terraform-apply.md#sign-in-user-role)). Whether user-management calls honour a tenant-only binding is not proven yet.
- **Gemini calls need a project-level role.** Vertex AI cannot be scoped to one environment; the custom role holds `aiplatform.endpoints.predict` only.
- **The field rules release role reaches both environments' rules.** The test release workflow releases `web/firestore.rules` to `dryscope-field-test` as the deploy account, which holds `dryscopeRulesReleaseTest`: `firebaserules.rulesets.create`, `rulesets.get`, `releases.get`, `releases.create` and `releases.update` (no delete, list, test or `getExecutable`). Firebase Rules is not among the services IAM Conditions can scope by resource name ([resource attributes](https://cloud.google.com/iam/docs/conditions-resource-attributes)) and a release holds no IAM policy of its own, so the grant is project-wide: the test deploy account could also point `cloud.firestore/dryscope-field-live` (or any other release in the project) at a ruleset it created. Only `web/scripts/release-rules.ts`, which derives the release from `--env test` and refuses live, and the workflow, which passes `test`, keep it to test; the same GitHub environment, branch and pool controls as every other deploy permission stand behind them. The plan check requires the grant to carry no condition, because one would look narrower than it is. Separate projects per environment are the only full fix. The role and its grant are test only for now: the live data root creates neither, so live rules releases stay owner-run until the live wiring, in a later step.
- **The scheduler account holds no role.** `dryscope-scheduler-test` exists only so Cloud Scheduler can mint its ID token (the Cloud Scheduler service agent's automatic `roles/cloudscheduler.serviceAgent` covers that); the web app already takes unauthenticated calls, and its `serviceRoute` accepts only that account's Google-signed token with the job's audience (`dryscope-test-access-projection`). The account and its job are test only for now; live gets them with the live wiring, in a later step. If a front door later makes the service private, the account will need `roles/run.invoker` on the web app only. In test the five-minute schedule wakes the scale-to-zero service for each pass (request-based billing, so seconds of CPU per call).

- **Model Armor sanitize access is project-wide.** `roles/modelarmor.user` (sanitize calls only: no template create, update, delete or list, no floor-setting access) is granted to the web app, the relay and the test evaluation account with no condition, because Model Armor is not among the services IAM Conditions can scope by resource name ([resource attributes](https://cloud.google.com/iam/docs/conditions-resource-attributes)). A test service can therefore screen text against the live template; that only reads the template and returns a verdict. The plan check requires the grants to carry no condition, because one would look narrower than it is.
- **The relay's roles.** `dryscope-live-<env>` holds the predict-only Gemini role, `roles/modelarmor.user` and the `link-signing-key` secret, and nothing in Cloud SQL or Firestore (V13 A: it reaches data only through the web app's relay routes). Whether predict covers Live's `BidiGenerateContent` is S7-0's question (a); the smallest extra permission, if one is needed, is added after that probe, not here.
- **The evaluation account shares the release's principal set.** `dryscope-eval-test` takes `workload_identity_principal_set`, the same repository-scoped principal set from test's own pool that the deploy account and the migrator take, because the pool maps no attribute that tells one workflow from another. So any workflow run the test provider admits (this repository, `master`, GitHub environment `test`) can act as the evaluation account, and the evaluation workflow could act as the deploy account. The evaluation account holds only predict and sanitize; telling workflows apart would need the owner to map `job_workflow_ref` in the test provider and a narrower principal set.
- **Model Armor's own logging is off.** Template `log_sanitize_operations` and `log_template_operations` and the floor setting's `enable_cloud_logging` would write whole prompts and responses to Cloud Logging (hard rule 6), so all three are `false` and the plan check refuses any other value. The floor setting is the fail-open baseline for Agent Platform calls (Model Armor skips it when unavailable); the control is the app's own sanitize calls, which fail closed.

- **Trace writing is project-wide.** `roles/telemetry.tracesWriter` (`telemetry.traces.write` only) is granted to `dryscope-api-<env>` on the project with no condition: neither the Telemetry API nor Cloud Trace is among the services IAM Conditions can scope by resource ([resource attributes](https://cloud.google.com/iam/docs/conditions-resource-attributes)), and a condition naming a resource such a service does not report never grants, so it would silently drop every span. The test web app can therefore write spans into the same project trace store as live; it cannot read them. The plan check requires the grant to carry no condition (owner decision A, 2026-11-14).
- **The test deploy account can write any log entry in the project.** `roles/logging.logWriter` (`logging.logEntries.create` and `route`, no read) lets `dryscope-deploy-test` write the failed-release line (TC-8). A log entry has no IAM resource of its own for a condition to scope by ([resource attributes](https://cloud.google.com/iam/docs/conditions-resource-attributes)), so the grant is project-wide with no condition, and the plan check requires it to carry none (owner decision A, 2026-11-14). A forged line could raise a false failed-release alert; it cannot read or delete logs. Test only for now.
- **The synthetic monitor's password is a real sign-in for a test technician.** `roles/secretmanager.secretAccessor` lets `dryscope-synthetic-test` read only `dryscope-test-synthetic-password`: it is granted on that one secret (resource-level IAM), which already limits it to that secret, so a condition would add nothing ([resource attributes](https://cloud.google.com/iam/docs/conditions-resource-attributes)) and the plan check requires the grant to carry none (owner decision A, 2026-11-14). The technician belongs to test company A only, with fake data. Live has neither.

The provider (7.46.2) has no image-modality field on `google_model_armor_template` and no spend-cap field on `google_billing_budget`, so these two stay owner commands (`docs/plans/S7.md`, section 7 steps D and F):

- **Image template** `dryscope-image-<env>` in the `us` multi-region (V3 C; image screening is only in `us`, `eu` and `global`), with the same filters, both logging flags off and the same pinned filter version. The command is in the S7-2 pull request; its runbook entry lands with S7-8, the first step that uses the template.
- **Spend cap**: a Cloud Billing budget on project `dryscope`, service Agent Platform (Vertex AI API), $150 a month (V5 B), with spend-cap enforcement. It needs Billing Account Administrator (or the project-scoped budget permissions), and enforcement uses estimated costs and is not instant.
